## 1. 总览：MVCC 的整体结构
```
      写事务 (INSERT / UPDATE / DELETE)                    读事务 (普通 SELECT, 即快照读)
            │                                                        │
            │ ① 先把「修改前镜像」写入 undo log                        │ ④ 生成/复用 ReadView
            ▼    (trx0rec.cc:2105 trx_undo_report_row_operation)     │    (trx0trx.cc:2259 trx_assign_read_view)
┌───────────────────────────┐                                       ▼
│ 聚簇索引记录 (就地更新)      │   ③ 沿 DB_ROLL_PTR 逐版本回溯   ┌────────────────────────┐
│  DB_TRX_ID    (6字节)      │◀──────────────────────────────│ 可见性判断               │
│  DB_ROLL_PTR  (7字节)──────┼──▶ undo(旧值) ──▶ undo(更旧)   │ ReadView::changes_visible│
└───────────────────────────┘        ② 隐藏列把版本串成链      │ (read0types.h:162)      │
                                                            └────────────────────────┘
 ①②=写路径(§3)   ③④=读路径(§6/§7)   可见→直接读当前记录；不可见→回溯 undo 重建历史版本返回
```

## 2. 隐藏列：行上携带的版本信息

### 2.1 三个隐藏列
&nbsp;&nbsp;InnoDB 为每行记录添加系统列，定义于 `innobase/dict/dict0dict.cc:1149-1160`（`dict_mem_table_add_col`）:

| 隐藏列 | 大小 | 常量定义 | 作用 |
|---|---|---|---|
| DB_ROW_ID | 6B | `data0type.h:175` (`DATA_ROW_ID=0`) | 表无主键且无非空唯一索引时充当聚簇索引键（`dict0dict.cc:3061`） |
| DB_TRX_ID | 6B | `data0type.h:181` (`DATA_TRX_ID=1`) | 最后插入/更新该行的事务ID |
| DB_ROLL_PTR | 7B | `data0type.h:187` (`DATA_ROLL_PTR=2`) | 回滚指针，指向 undo log 中的上一版本 |

```
聚簇索引记录布局 (Compact 格式示意):
┌────────────┬────────────────────┬────────────┬─────────────┐
│ 变长/NULL等 │  用户定义列 + 主键   │ DB_TRX_ID  │ DB_ROLL_PTR │
│  记录头信息 │      (数据)        │   6 bytes  │   7 bytes   │
└────────────┴────────────────────┴────────────┴─────────────┘
```
> 源码有编译期断言保护: `data0type.h:534`(`DATA_TRX_ID_LEN==6`)、`data0type.h:536`(`DATA_ROLL_PTR_LEN==7`)；从记录中取 trx id 的函数是 `rem0rec.h:664 rec_get_trx_id`。

### 2.2 DB_ROLL_PTR 的 56 位布局
&nbsp;&nbsp;roll_ptr 共 7 字节(56 bit)，由 `trx0undo.ic:44-56` 编码、`trx0undo.ic:59-75` 解码:

```
 55          54      48 47                          16 15               0
┌───────────────┬───────────┬────────────────────────────┬───────────────────┐
│  is_insert    │  rseg_id  │         page_no            │      offset       │
│   1 bit       │   7 bit   │   32 bit (undo 页号)        │ 16 bit (页内偏移)  │
└───────────────┴───────────┴────────────────────────────┴───────────────────┘
```
```cpp
// include/trx0undo.ic:44  构造 roll_ptr
inline roll_ptr_t trx_undo_build_roll_ptr(bool is_insert, space_id_t space_id,
                                          page_no_t page_no, ulint offset) {
  ...
  roll_ptr = (roll_ptr_t)is_insert << 55 | (roll_ptr_t)id << 48 |
             (roll_ptr_t)page_no << 16 | offset;            // ← 56bit 四段拼接
  return (roll_ptr);
}
// include/trx0undo.ic:59  解码 roll_ptr（读路径用它定位 undo 记录）
inline void trx_undo_decode_roll_ptr(roll_ptr_t roll_ptr, bool *is_insert,
                                     ulint *rseg_id, page_no_t *page_no, ulint *offset) {
  *offset = (ulint)roll_ptr & 0xFFFF;        // 低16位: 页内偏移
  roll_ptr >>= 16;
  *page_no = (ulint)roll_ptr & 0xFFFFFFFF;   // 32位: undo 页号
  roll_ptr >>= 32;
  *rseg_id = (ulint)roll_ptr & 0x7F;         // 7位: 回滚段id
  roll_ptr >>= 7;
  *is_insert = roll_ptr;                     // 最高位: insert undo 还是 update undo
}
```
> 写入页面用 `trx_write_roll_ptr`（`trx0undo.ic:98-103`，内部 `mach_write_to_7`，固定写 7 字节）。

## 3. 写路径：版本链如何生长
&nbsp;&nbsp;**核心: 任何修改聚簇索引记录的操作，都先把「修改前镜像」写入 undo log，再就地改记录。**

```
UPDATE t SET a=5 WHERE id=1;      (当前写事务, trx_id=400)
        │
        ▼
┌─────────────────────────────────────────────────────────────────┐
│ ① 先写 undo: trx_undo_report_row_operation(TRX_UNDO_MODIFY_OP)  │
│     定义: trx/trx0rec.cc:2105                                   │
│     调用点: btr/btr0cur.cc:3121、btr/btr0cur.cc:4278 (update/delete)│
│     把「旧值镜像」写入 undo 页, 返回指向该 undo 记录的 roll_ptr     │
├─────────────────────────────────────────────────────────────────┤
│ ② 就地更新聚簇索引记录:                                          │
│     DB_TRX_ID    ← 400                                          │
│     DB_ROLL_PTR  ← ①返回的 roll_ptr (指向 a=旧值 的镜像)          │
└─────────────────────────────────────────────────────────────────┘
```
&nbsp;&nbsp;多次修改后，隐藏列就像链表的 next 指针，把各版本串起来：
```
   id=1, a=5          ← 聚簇索引当前记录, DB_TRX_ID=400
   DB_ROLL_PTR ───┐
                  ▼
   undo: id=1, a=2    (trx 300 修改前的镜像, 记录在 trx300 的 update undo 中)
        (其修改者 trx300 又指向更早版本)
                  ▼
   undo: id=1, a=1    (trx 200 修改前的镜像)
```
### 3.1 insert undo 与 update undo 的区别
| 类型 | 何时产生 | 何时可释放 | 源码依据 |
|---|---|---|---|
| insert undo | INSERT 产生（只有回滚需要） | 事务提交后立即丢弃 | `trx0rec.cc:2195-2207`(`TRX_UNDO_INSERT_OP` 分支)；`trx0undo.ic:79 trx_undo_roll_ptr_is_insert` |
| update undo | UPDATE/DELETE 产生 | 提交后挂入 history list，等 purge 确认无快照需要才能删 | `trx0rec.cc:2212-2217`；`trx0purge.cc:317 trx_purge_add_update_undo_to_history` |

> insert 产生的版本"对其他事务不可见"的原因也在这里：**别的事务回溯版本链时一旦走到 insert undo，就说明该行在快照时还不存在**，见 §7 的 `prev_version == nullptr` 分支。
> 《MySQL技术内幕：InnoDB存储引擎》第7章 7.2 对这两类 undo 有成段讲解（见文末参考资料⑤）。

### 4.2 ReadView 结构与可见性判定
&nbsp;&nbsp;`ReadView` 类定义于 `include/read0types.h:47`。**可见性判断只有一个函数**（62-182行，纯内存二分查找，无锁）:
```cpp
// include/read0types.h:162-182
[[nodiscard]] bool changes_visible(trx_id_t id, const table_name_t &name) const {
  ut_ad(id > 0);
  if (id < m_up_limit_id || id == m_creator_trx_id) {   // ① 比低水位小 / 自己改的 → 可见
    return (true);
  }
  check_trx_id_sanity(id, name);
  if (id >= m_low_limit_id) {                           // ② 达到高水位(视图创建后才开启的事务) → 不可见
    return (false);
  } else if (m_ids.empty()) {                           // ③ 介于两水位间且无活跃事务 → 可见
    return (true);
  }
  const ids_t::value_type *p = m_ids.data();
  return (!std::binary_search(p, p + m_ids.size(), id)); // ④ 在活跃列表中 → 不可见(未提交)；不在 → 可见
}
```
```
                 待判断的版本 DB_TRX_ID = id
                          │
        ┌─────────────────┴──────────────────┐
        ▼                                    ▼
 id < m_up_limit_id ?                  id >= m_low_limit_id ?
 (或 id == m_creator_trx_id)                 │
   │是          │否                   │是          │否
   ▼            ▼                     ▼            ▼
 可见 ✓      m_ids 为空?          不可见 ✗    m_ids 中二分查找 id
              │是   │否                        │找到    │没找到
              ▼     ▼                          ▼        ▼
            可见 ✓ 可见 ✓                  不可见 ✗   可见 ✓
            (此时介于两水位间必可见)         (生成快照时该事务活跃=未提交)
```
> 另有快速判断 `sees()`（`read0types.h:187`）：`id < m_up_limit_id`，用于二级索引的粗判（§6.3）。

### 4.3 快照是如何"拍"下来的
&nbsp;&nbsp;`ReadView::prepare`（`read/read0read.cc:446-470`）在 **trx_sys->mutex 保护下** 一次性采集四个字段：

&nbsp;&nbsp;活跃事务列表 `trx_sys->rw_trx_ids`（`include/trx0sys.h:551`）的维护点：
- **加入**：事务获得 trx id 时 `trx->id = trx_sys_allocate_trx_id()`（`trx0trx.cc:1234、1352`，ID 来自全局计数器 `next_trx_id_or_no`，`trx0sys.h:494`），随后 `push_back`（`trx0trx.cc:1236、1354`）

## 5. ReadView 的创建与销毁：RR 与 RC 的本质差异

```
REPEATABLE READ（事务级快照）                     READ COMMITTED（语句级快照）
──────────────────────────────                  ──────────────────────────────
BEGIN;                                          BEGIN;
  │                                               │
SELECT① ─▶ row_search_mvcc (row0sel.cc:4363)    SELECT① ─▶ 创建 ReadView ─▶ 读 ─▶ 语句结束:
          │ 首次快照读, trx_assign_read_view                external_lock(F_UNLCK) 中
          │ (row0sel.cc:4772 → trx0trx.cc:2259)             view_close 关闭视图
          │ 视图不存在 → MVCC::view_open                     (handler/ha_innodb.cc:18839-18845)
          │ (read0read.cc:528) → ReadView::prepare          store_lock 中再兜底关闭一次
          ▼                                                 (ha_innodb.cc:19432-19441)
SELECT② ─▶ 视图仍活跃 → 直接复用 ★               SELECT② ─▶ 重新创建 ReadView
          │ (trx0trx.cc:2268-2270 的判断)                    → 能读到 SELECT② 之前已提交的数据
          ▼
读到的数据与 SELECT① 一致                         每条语句看到各自时刻的最新已提交数据
  │                                                │
COMMIT; ─▶ trx_erase_lists (trx0trx.cc:1774)     每条语句一个快照 → 不可重复读/幻读
          └▶ mvcc->view_close (trx0trx.cc:1791)
```

**关键源码点**：
1. **RR 复用视图**：`trx_assign_read_view`（`trx/trx0trx.cc:2259-2273`）——已有活跃视图就不再创建，这是"可重复读"的实现根基：
```cpp

ReadView *trx_assign_read_view(trx_t *trx) {
  ...
  } else if (!MVCC::is_view_active(trx->read_view)) {
    trx_sys->mvcc->view_open(trx->read_view, trx);   // 仅当无活跃视图时才新建
  }
  return (trx->read_view);
}
```
2. **RC 每语句重开视图**：`external_lock` 在语句结束时关闭视图（`handler/ha_innodb.cc:18839-18845`）；`store_lock` 在语句开始前兜底关闭（`ha_innodb.cc:19432-19441`，注释原文 *"At low transaction isolation levels we let each consistent read set its own snapshot"*）
3. **`START TRANSACTION WITH CONSISTENT SNAPSHOT`**：注册于 `ha_innodb.cc:5140`，实现在 `ha_innodb.cc:5687-5736`；**仅 RR 生效**，事务开始立即拍快照（`ha_innodb.cc:5712-5722`），RR 下其他情况都是"第一条快照读时"才懒创建（`row0sel.cc:4772`）
4. **AC-NL-RO 优化**（autocommit 只读事务）：不进事务列表、视图用完即标记关闭并复用——`read0read.cc:533-556`（view_open 复用判断）、`read0read.cc:725-734`（view_close 用指针最低位 1bit 标记 closed，避免加 mutex）

## 6. 读路径：快照读的完整执行流程
&nbsp;&nbsp;普通 SELECT 的所有行级判断都在 `row_search_mvcc`（`row/row0sel.cc:4363`）中，**每取一条记录**执行一遍：

```

     │

          │     └─▶ 不做任何判断, 直接读最新记录 (row0sel.cc:5253-5256)
          │
          ├─ 记录来自【聚簇索引】?
          │     └─▶ lock_clust_rec_cons_read_sees (lock0lock.cc:229-255)
          │           │ 252行: row_get_rec_trx_id 取出 DB_TRX_ID
          │           │ 254行: view->changes_visible(trx_id)
          │           │
          │      可见 ─┴─ 不可见

          │
          └─ 记录来自【二级索引】?
                └─▶ lock_sec_rec_cons_read_sees (lock0lock.cc:266-295)
                      用【页头】PAGE_MAX_TRX_ID 粗判: view->sees(max_trx_id) (290-294行)

> **为什么二级索引不能就地回溯？** 二级索引记录不存储 DB_TRX_ID/DB_ROLL_PTR（只有聚簇索引有隐藏列），且二级索引的更新方式是"旧记录打删除标记+插入新记录"而非就地更新，因此只能回聚簇索引取正确版本。二级索引与 MVCC 的关系详见 [013.InnoDB Multi-Versioning.md](../013.存储引擎内核/000.InnoDB/013.InnoDB%20Multi-Versioning.md) 的 *Multi-Versioning and Secondary Indexes* 一节。

## 7. 版本回溯：row_vers_build_for_consistent_read
&nbsp;&nbsp;当前记录不可见时，从聚簇记录出发**沿 undo 逐版本重建**，直到找到 ReadView 可见的版本（`row/row0vers.cc:1249-1342`）：

```
version = 当前记录 (row0vers.cc:1279)
        │

### 7.1 半一致性读（Semi-consistent read, RC 下的 UPDATE 特有）
&nbsp;&nbsp;RC 隔离级别执行 UPDATE 时，被其他事务锁住的行**不等待**，而是退化为读"最后已提交版本"参与 WHERE 判断：
- 入口: `row0sel.cc:5175-5219`（`use_semi_consistent`）、`row0sel.cc:743`（`row_sel_build_committed_vers_for_mysql`）
- 实现: `row_vers_build_for_semi_consistent_read`（`row0vers.cc:1359`）
- **与一致性读的区别**：它不看 ReadView，只看版本的修改事务是否还活跃——`trx_rw_is_active(version_trx_id)`（`row0vers.cc:1387`），找到第一个"已不在活跃列表"的版本即返回

## 8. purge：历史版本何时被清理
&nbsp;&nbsp;版本链不能无限增长——purge 线程负责把"不再被任何快照需要"的 update undo 清掉：
```
COMMIT (带 update undo)
   │ trx0purge.cc:317 trx_purge_add_update_undo_to_history
   ▼
rollback segment 的 history list (长度: trx0sys.h:476 rseg_history_len)
   │
   ▼  purge 线程周期运行 (trx0purge.cc:2577 trx_purge_run)
┌──────────────────────────────────────────────────────────────┐
│ 取系统中最老的 ReadView 做清理基准:                            │
│   MVCC::clone_oldest_view (read0read.cc:673-694)             │
│   → purge_sys->view (include/trx0purge.h:1018)               │
│                                                              │
│ 对 history list 中每条 undo:                                  │
│   该 trx 对最老快照可见吗? (purge_sys->view.changes_visible)   │
│   可见   → 所有快照都不再需要它 → 可清理                       │
│            trx_purge_truncate_history (trx0purge.cc:1596)    │
│   不可见 → 有长事务快照仍可能回溯到它 → 必须保留               │
└──────────────────────────────────────────────────────────────┘
```
- 清理边界记录在 `m_low_limit_no`（`read0types.h:301`；`reduce_low_limit` 见 `read0types.h:213-219`）
- 读路径与 purge 的衔接：回溯 undo 前会先用 purge 视图确认 undo 还在——`trx0rec.cc:2419`（`missing_history = purge_sys->view.changes_visible(trx_id, name)`），已被清理则返回 `DB_MISSING_HISTORY`（`row0vers.cc:1297`）
- **长事务的危害**：最老 ReadView 一直不推进 → history list 堆积 → undo 表空间膨胀、所有读的回溯链变长。这也是"事务要尽快提交"的底层原因（配置调优见官方手册 *Purge Configuration*，文末参考资料②）

## 9. 端到端示例（双会话时序）
&nbsp;&nbsp;初始：表 t 有 id=1, a=1（由 trx 10 提交写入）。
```
Session A (REPEATABLE READ)                     Session B (任意隔离级别)
─────────────────────────────                   ─────────────────────────
BEGIN;
SELECT a FROM t WHERE id=1;
   │ 首次快照读 → 创建 ReadView:
   │   m_creator_trx_id = 100 (A自己)
   │   m_low_limit_id  = 100  (下一个将分配的ID)
   │   m_ids = {}             (无活跃读写事务)
   │   m_up_limit_id  = 100
   │ 判断记录 DB_TRX_ID=10: 10 < 100 → 可见
   ▼ 返回 a=1
                                                BEGIN;
                                                UPDATE t SET a=2 WHERE id=1;
                                                   │ 先写 undo(a=1 的镜像)
                                                   │ 记录变为: DB_TRX_ID=100,
                                                   │           roll_ptr→a=1镜像
                                                   │ (trx 100 未提交)
SELECT a FROM t WHERE id=1;
   │ 复用同一 ReadView ★RR关键
   │ 判断 DB_TRX_ID=100:
   │   100 >= m_low_limit_id(100) → 不可见
   │   → 回溯 undo → 取 a=1 → 可见 ✓
   ▼ 返回 a=1   (可重复读)
                                                COMMIT;   (trx 100 提交)
SELECT a FROM t WHERE id=1;
   │ 仍复用 ReadView → a=1  ← RR 下提交与否不影响
   ▼ 返回 a=1
```
- 若 Session A 是 **RC**：B 提交后，A 的下一条 SELECT 会先关闭旧视图（`ha_innodb.cc:18839`）再新建——新视图 `m_low_limit_id=101`，则 `10、100 < 101 且不在 m_ids` → 可见 → 返回 **a=2**
- 若 B 的事务在 A 建视图**之前**就已活跃：其 id 会进入 `m_ids`，A 读到它改的行时走"二分查找命中 → 不可见 → 回溯"路径（`read0types.h:181`）
- 幻读与当前读（`FOR UPDATE` 等）不在快照读范畴，见 [001.InnoDB中的事务隔离级别和锁的关系](./001.InnoDB中的事务隔离级别和锁的关系.md)、[004.一致性锁定读](./004.一致性锁定读.md)

## 12. 一句话总结
&nbsp;&nbsp;**写**：改行前先把旧镜像写进 undo（`trx0rec.cc:2105`），记录上的 `DB_TRX_ID/DB_ROLL_PTR` 始终指向"当前值+上一版本"；
**读**：拿 ReadView（`trx0trx.cc:2259`）对每个版本的 `DB_TRX_ID` 做 `changes_visible` 判定（`read0types.h:162`），不可见就沿 roll_ptr 回溯 undo 重建（`row0vers.cc:1249`）；
**回收**：purge 用全系统最老的 ReadView（`read0read.cc:673`）决定 undo 何时可删（`trx0purge.cc:1596`）。RR/RC 的全部差异只在于 **ReadView 何时创建、何时销毁**（§5）。
