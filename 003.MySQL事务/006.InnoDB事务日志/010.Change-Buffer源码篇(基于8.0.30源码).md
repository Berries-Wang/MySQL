# Change Buffer 源码篇（基于 MySQL 8.0.30 GA）
&nbsp;&nbsp;**对二级索引的修改，若目标页不在 Buffer Pool，先把它缓存进 change buffer（一棵位于系统表空间的 B-tree），把「随机读盘」推迟/合并，等页被读入时再合并（merge）。**
> 概念篇(参数/适用场景/为什么唯一索引用不了): [006.Change-Buffer.md](./006.Change-Buffer.md) · 缓冲池: [002.InnoDB缓冲池.md](./002.InnoDB缓冲池.md)

`ibuf/ibuf0ibuf.cc`(全部主逻辑)、`btr/btr0cur.cc`(插入入口)、`buf/buf0buf.cc`(读页时 merge)。

## 1. 总图：写时缓存、读时合并
```
        INSERT/UPDATE/DELETE 影响二级索引
                     │
                     ▼
   btr_cur_search_to_nth_level (btr0cur.cc:618)
   定位二级索引目标叶页 —— buf_page_get_gen(..., Page_fetch::IF_IN_POOL)
                     │
        ┌──── 页在 Buffer Pool? ────┐
        │是                         │否 ★
        ▼                           ▼
   直接修改该页页             ibuf_insert (btr0cur.cc:980/992/1008)
   (正常路径)                  │ ibuf0ibuf.cc:3274
                               ▼
                    ┌────────────────────────────┐
                    │ ①条件检查: ibuf op 类型      │
                    │   /innodb_change_buffering  │
                    │   /必须是非聚簇索引           │
                    │ ②ibuf_insert_low(:2969)     │
                    │   查该页所在 extent 的       │
                    │   IBUF bitmap 页            │
                    │   → 有空位则把 (space,page_no│
                    │   ,op,记录内容) 写进         │
                    │   change buffer B-tree      │
                    │ ③更新 bitmap 的 BUFFERED 位  │
                    └────────────────────────────┘
                               │ (之后某时刻目标页被读入内存)
                               ▼
                  读盘完成/首次访问该页时:
   buf0buf.cc:3810-3816 ─▶ ibuf_merge_or_delete_for_page (ibuf0ibuf.cc:3959)
                    从 change buffer 取出该页全部缓存操作, 逐条应用到页上
                    → 页恢复正常, bitmap 的 BUFFERED 位清零
```
> **本质**：change buffer 不是"日志"，而是一棵真实 B-tree 里缓存的"待应用的二级索引修改"。merge 之后它与直接修改的结果完全一致。

## 2. 数据落在哪：change buffer B-tree 与 bitmap 页
| 结构 | 位置 | 源码 |
|---|---|---|
| change buffer 主 B-tree | 系统表空间（`IBUF_SPACE_ID=0`，`include/ibuf0types.h:37`）；头页 3 号、B-tree 根页 4 号（`include/fsp0types.h:163,167`） | 源码注释明言 ibuf 树在系统表空间（`ibuf/ibuf0ibuf.cc:90`），根页访问见 `:381`；B-tree 上的记录即一条条缓存的操作 |
| 每 16384 个 extent 一张 bitmap 页 | 页类型 `FIL_PAGE_IBUF_BITMAP=5`（`include/fil0fil.h:1213`），位段从 `FSP_IBUF_BITMAP_OFFSET`（`include/fsp0types.h:157`） | bitmap 页中每页占 4 bit：`IBUF_BITMAP_FREE`(:241, 2bit 剩余空间)、`IBUF_BITMAP_BUFFERED`(:243, 是否有缓存操作)、`IBUF_BITMAP_IBUF`(:246)，均定义于 `ibuf/ibuf0ibuf.cc:51-246` |
| 操作类型枚举 | `include/ibuf0ibuf.h:52-58` | `IBUF_OP_INSERT=0 / IBUF_OP_DELETE_MARK / IBUF_OP_DELETE` |

bitmap 的作用：ibuf_insert 前先看目标页"还有没有空位"（FREE），避免缓存了操作后页在 merge 时放不下；BUFFERED 位记录"这个页在 change buffer 里有欠账"。

## 3. 写路径源码：ibuf_insert
```cpp
// btr/btr0cur.cc:618 btr_cur_search_to_nth_level —— 对二级索引的定位
//   :961  buf_page_get_gen(..., Page_fetch::IF_IN_POOL) 只"尝试"取页, 不读盘
//   :980  取不到(页不在内存) →
if (ibuf_insert(IBUF_OP_INSERT, tuple, index, page_id, page_size, cursor->thr)) {
  cursor->flag = BTR_CUR_INSERT_TO_IBUF;    // 本条修改已进 change buffer, 返回
  goto func_exit;                           // :992 IBUF_OP_DELETE_MARK  :1008 IBUF_OP_DELETE
}
// ibuf/ibuf0ibuf.cc:3274 ibuf_insert —— 按参数决定哪些操作允许缓存
bool ibuf_insert(ibuf_op_t op, const dtuple_t *entry, dict_index_t *index, ...) {
  ibuf_use_t use = static_cast<ibuf_use_t>(innodb_change_buffering);
  ut_a(!index->is_clustered());               // ★只可能是二级索引
  switch (op) {
    case IBUF_OP_INSERT:
      switch (use) {
        case IBUF_USE_NONE: ... return false; // innodb_change_buffering=OFF
        case IBUF_USE_INSERT: ... goto check_watch;   // 允许缓存 insert
      }
  ...
}
// ibuf/ibuf0ibuf.cc:2969 ibuf_insert_low —— bitmap 检查 + 写 ibuf B-tree
// ibuf/ibuf0ibuf.cc:3378/3382 —— insert_low 的乐观/悲观(BTR_MODIFY_TREE)两种调用
```
**为什么只对二级索引、且唯一索引不行**（概念篇详述，源码佐证）：
- 聚簇索引记录即数据、必有约束与回滚语义，绕不开 → `ut_a(!index->is_clustered())`
- 唯一二级索引插入前必须先做重复检查（`row_ins_scan_sec_index_for_duplicate`），检查本身就要读页——目标页因此已进 Buffer Pool，change buffer 的免读盘收益不存在。重复检查完成后的插入用 `BTR_INSERT_IGNORE_UNIQUE_OP`（`btr0cur.cc:977`），它与 `BTR_INSERT_OP` 一样允许在页恰不在内存时走 `ibuf_insert`（`btr0cur.cc:976-981`）

## 4. 读路径源码：merge
```
① 被动 merge(最常见): 页因查询被读入 Buffer Pool
   buf0buf.cc 读页+解压后, 首次访问时:
   :3810  if (!recv_no_ibuf_operations) {
   :3816    ibuf_merge_or_delete_for_page(block, m_page_id, &m_page_size, true);
            // ibuf0ibuf.cc:3959 —— 取出该页在 change buffer 中的全部记录逐条应用
② 主动 merge(后台): 
   master 线程: srv_master_do_active_tasks(srv0srv.cc:2288 起, :2317 调用) 与
   srv_master_do_idle_tasks(:2362 起, :2385 调用) → ibuf_merge_in_background() (ibuf0ibuf.cc:2392)
   插入导致 change buffer 过大时主动收缩:
   ibuf0ibuf.cc:2441 ibuf_contract_after_insert → :2379 ibuf_contract
   (读若干页回来做 merge, :2229 ibuf_merge_pages; :2290 ibuf_merge_space 整空间)
```
> merge 时才需要锁与 undo：merge 产生的页修改同样走 mtr→redo（change buffer 的内容本身也在 redo 保护之下，恢复时 change buffer 页和普通页一样被重放）。

## 5. 参数与观测
| 参数 | 源码 | 说明 |
|---|---|---|
| `innodb_change_buffering` | `handler/ha_innodb.cc:22873`（`MYSQL_SYSVAR_ENUM`，默认 `IBUF_USE_ALL`） | none/inserts/deletes/changes/purges/all，控制哪些操作允许缓存 |
| `innodb_change_buffer_max_size` | `handler/ha_innodb.cc:22884`，默认 `CHANGE_BUFFER_DEFAULT_SIZE=25`（`include/ibuf0ibuf.h:46`） | change buffer 最大占 buffer pool 百分比 |
| 观测 | `SHOW ENGINE INNODB STATUS` 中 `INSERT BUFFER AND ADAPTIVE HASH INDEX` 段；`Ibuf: size 1, free list len ...` | size 即当前缓存的未 merge 操作数 |

**收益与代价**（帮助建立直觉）：
- 收益 = 省下的随机读 IO（写密集 + 二级索引页命中率低时显著）
- 代价 = merge 时要读页并执行多条操作（读放大的推迟）、change buffer 占用 buffer pool、崩溃恢复时多一层依赖
- 所以官方默认 `all` 但实际收益高度依赖负载——写少读多、二级索引页常驻的 OLTP 库里反而可能负优化（这也是后续版本弱化它的原因）
