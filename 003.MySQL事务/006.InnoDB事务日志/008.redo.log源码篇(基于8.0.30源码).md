## 2. redo 记录的生成：mini-transaction (mtr)
&nbsp;&nbsp;InnoDB 不在 SQL 层记录 redo，而是把「对页的一次原子修改」包在 mtr 里。mtr 执行期间把每一步物理修改写成 `MLOG_*` 记录，缓存在 `m_impl.m_log`：

| 源码 | 作用 |
|---|---|
| `mtr/mtr0mtr.cc:576` `mtr_t::start` | 开始一个 mtr |
| `include/mtr0types.h:62-69` `enum mlog_id_t` | redo 记录类型：`MLOG_1BYTE=1`、`MLOG_2BYTES`、`MLOG_4BYTES`、`MLOG_8BYTES`、`MLOG_REC_*`、`MLOG_PAGE_REORGANIZE`… |
| `mtr/mtr0log.cc:255` `mlog_write_ulint` | 改页内字段的同时生成一条对应类型 redo |
| `mtr/mtr0mtr.cc:772` `Command::prepare_write` | 把 m_log 整理成可写的字节流 |
| `mtr/mtr0mtr.cc:674` `mtr_t::commit` | 提交：`cmd.execute()` 走日志路径，无修改则只释放锁 |

```
mtr 生命周期:
mtr_t::start ──▶ 修改页(btr_cur 等底层, 每步产生 MLOG 记录) ──▶ mtr_t::commit
  │                                                        │
  持有页 latch / 链表 latch                                 ① redo 进 log buffer
  (memo 栈管理)                                            ② 脏页按 LSN 排上 flush list
                                                           ③ 释放所有 latch
```
> mtr 是 redo 的「事务」：一个 SQL 语句 = 许多 mtr；一个 mtr = 若干页的原子修改（崩溃恢复重放时不允许半个 mtr）。

## 3. 写入 log buffer：LSN 的分配
&nbsp;&nbsp;`log_buffer_reserve`（`log/log0buf.cc:858`）原子地分配一段连续 LSN 区间，返回 `Log_handle{start_lsn, end_lsn}`；随后 mtr 的记录被逐块拷入（`log0buf.cc:921 log_buffer_write`），完成后 `log_buffer_write_completed`(:1060) / `log_buffer_close`(:1141) 发布这段数据，让 writer 线程可见。

```
                    log buffer (innodb_log_buffer_size)
 ┌──────────────────────────────────────────────────────────────┐
 │ ...已写入区块...  │ mtr-A [5000,5600) │ mtr-B [5600,6100) │ ...
 └──────────────────────────────────────────────────────────────┘
        write_lsn ▲                        ▲ available_for_write
 LSN: 全局单调递增的字节偏移（log0log.cc:434 log_sys 全局对象统一管理）
```
- 缓冲区满时的背压：`log_wait_for_space_in_log_recent_closed`（mtr0mtr.cc:879 调用）与 `log_buffer_flush_to_disk`（log0buf.cc:1192）——先推动 redo 落盘腾出空间
- 临时表空间的 mtr 显式切换为 `MTR_LOG_NO_REDO`（`trx0rec.cc:2180 set_log_mode`），`mtr_t::commit` 据此跳过写日志（`mtr0mtr.cc:685`）

## 4. 后台线程管线：writer / flusher / notifier
```
 log buffer ──log_writer──▶ OS page cache(redo 文件) ──log_flusher──▶ 磁盘(fsync)
   (log0write.cc:2225)          (:2122 log_writer_write_buffer)   (:2490/:2416)
        │                                                            │
        └─ log_write_notifier (:2627)      log_flush_notifier (:2749)─┘
           通知"已写到 LSN"                   通知"已刷到 LSN"
```
| 线程 | 定义 | 职责 |
|---|---|---|
| log_writer | `log0write.cc:2225` | 把 log buffer 中已提交的区块 `pwrite` 到 redo 文件（:2122） |
| log_flusher | `log0write.cc:2490` | 对已写入部分 `fsync`（:2416，`SRV_UNIX_O_DSYNC` 时可免）；推进 `log.flushed_to_disk_lsn` |
| log_write_notifier / log_flush_notifier | `log0write.cc:2627 / 2749` | 唤醒等待写/刷完成的用户线程 |

&nbsp;&nbsp;**同步等待入口** `log_write_up_to`（`log0write.cc:1084`）——「把 redo 写并(可选)刷到 end_lsn，完成前等待」，是提交路径与刷页路径共用的核心函数。多个线程同时等待同一段 LSN 时只会被合并为一组 IO（这就是 redo 侧的 group commit，详见 [005.group-commit.md](./005.group-commit.md)）。

## 5. 事务提交：innodb_flush_log_at_trx_commit 的代码体现
```cpp
// trx/trx0trx.cc:1699  按 innodb_flush_log_at_trx_commit 决定提交时刷多远
static void trx_flush_log_if_needed_low(lsn_t lsn) {
  bool flush = srv_unix_file_flush_method != SRV_UNIX_NOSYNC;
  switch (srv_flush_log_at_trx_commit) {
    case 2:
      flush = false;                      // 只 write 到 OS cache, 不 fsync
      [[fallthrough]];
    case 1:
      log_write_up_to(*log_sys, lsn, flush);  // ★=1: write + fsync 后才返回
      return;
    case 0:
      return;                             // 什么都不做, 靠每秒后台刷
  }
}
// trx/trx0trx.cc:1730 trx_flush_log_if_needed（DDL 强制 sync）
// 调用点: trx0trx.cc:2449 trx_flush_log_if_needed(trx->commit_lsn, trx) —— 提交时
```
```
 innodb_flush_log_at_trx_commit
  0 : 提交不等日志 ──▶ 每秒后台刷(可能丢约1秒事务)
  1 : 提交 = redo fsync 完成 ──▶ 不丢已确认事务(默认)
  2 : 提交 = redo 写到 OS cache ──▶ 进程挂不丢, OS 挂丢
```
> 这就是「Force Log at Commit」：保证持久性的不是"数据页落盘"，而是"redo 先落盘"。

## 6. WAL 强制点：刷数据页之前先刷 redo
&nbsp;&nbsp;脏页可以慢慢刷，但有一条铁律——**页在写盘前，它的所有修改的 redo 必须已经在磁盘上**（否则崩后该页新内容 + 旧 redo，恢复出不存在的状态）。强制点就在刷页函数里：
```cpp
// buf/buf0flu.cc:1171 buf_flush_write_block_low（被 buf_flush_page :1281 调用）
  /* Force the log to the disk before writing the modified block */
  if (!srv_read_only_mode) {
    const lsn_t flush_to_lsn = bpage->get_newest_lsn();     // 页上最新修改的 LSN
    if (log_sys->flushed_to_disk_lsn.load() < flush_to_lsn) {
      wait_stats = log_write_up_to(*log_sys, flush_to_lsn, true); // ★先等 redo 落盘
    }
  }
  ...                                                       // 然后才真正写页
```
```
时间轴:  修改页(LSN=500) ───────────────────────▶ 刷页(要求 flushed_to_disk_lsn>=500)
              │                                        ▲
              └── redo: buffer ─▶ 文件 ─▶ fsync(500) ───┘  (WAL: 日志先行)
```
- 页与 LSN 的关联：mtr 提交时 `add_dirty_blocks_to_flush_list`（mtr0mtr.cc:883）把 `oldest_modification/newest_modification` 写到页上，flush list 因此按 LSN 有序
- `log_free_check()`（`include/log0chkp.h:310`，等待逻辑 `log0chkp.cc:1243 log_free_check_wait`）：每条语句/每个 mtr 开始前检查「redo 可用空间」，不够就主动推动 checkpoint——防止 write pos 追上 checkpoint 后无日志可写。调用点遍布行操作：`row/row0ins.cc:3085、3120、3187、3211`（注释 69-74 专门解释了为什么持锁时不能调用它）

## 7. checkpoint：redo 空间的循环复用
```
 redo 文件(环形):
 ┌─────────────────────────────────────────────────────────┐
 │ ... │ ██████ 已刷盘可覆盖 ██████ │ ▓▓ 已写未刷 ▓▓ │ 空闲 │
 └─────────────────────────────────────────────────────────┘
       ▲ last_checkpoint_lsn            ▲ write_lsn      ▲ capacity
       checkpoint_age = write_lsn - last_checkpoint_lsn ≤ 容量(log0files_capacity.cc)
```
- **checkpointer 线程**（`log/log0chkp.cc:976`）：周期/被请求时调用 `log_consider_sync_flush` 推刷脏页，让 `last_checkpoint_lsn` 前进
- **checkpoint 持久化**：`log_checkpoint`（`log0chkp.cc:454`）→ `log_files_write_checkpoint_low`（:437）把 LSN 写到 **首个 redo 文件头部的 LOG_CHECKPOINT_1/2 两个交替槽位**（`include/log0constants.h:160,166`：`LOG_CHECKPOINT_1=512`、`LOG_CHECKPOINT_2=1536`，交替逻辑 `log0chkp.cc:427`）
- 请求推进：`log_request_checkpoint`（`log0chkp.cc:593`）——由 free check、容量压力、DDL 等触发

## 8. 崩溃恢复：重放 redo
```
启动 ──▶ 读 LOG_CHECKPOINT_1/2 取最大合法 checkpoint (log0recv.cc)
     ──▶ recv_recovery_from_checkpoint_start (log0recv.cc:3845)
     ──▶ 从 checkpoint_lsn 起顺序扫描 redo 文件, 记录进 hash 按页分组
     ──▶ 重放: 把变更应用到页(先 dblwr 抢救坏页, 见 011 篇), 页变脏
     ──▶ 之后由正常刷页机制落盘; MVCC 需要的 undo 保留, 走事务回滚(trx0roll.cc)
```
> 恢复为什么快：redo 是**物理日志**（记录"页内某偏移改成某值"），重放是幂等覆盖；不像逻辑日志需要重新执行 SQL。
