# 为什么数据库写操作不直接落盘？预写日志WAL提升数据库性能原理（基于 MySQL 8.0.30 源码）
&nbsp;&nbsp;**WAL(Write-Ahead Logging)：先顺序写一份"做了什么"的小日志并保证其落盘，数据页本身的随机写则可以推迟、合并、甚至丢了重来。用"顺序小 IO + 可重放"换掉"随机大 IO"。**

## 1. 为什么写操作不直接落盘（对比图）
```
【不用 WAL: 每笔修改直接写 .ibd】
  UPDATE 一行 ──▶ 找到 16KB 页 ──▶ 读入内存改几个字节 ──▶ 整页写回磁盘
                  随机 IO(热页可能省读)                        × 每笔事务
  ⇒ 每秒几千次事务 = 每秒几千次 16KB 随机写, 磁盘寻道成为瓶颈, 且必须同步等写完

【用 WAL: 修改先记小日志】
  UPDATE 一行 ──▶ 改 Buffer Pool 中的页(内存, 微秒级)
              └─▶ 顺序追加几十~几百字节 redo ──▶ 顺序写+fsync  ← 唯一必须等的 IO
  脏页 ──▶ 之后由后台 page cleaner 批量、排序、合并地刷盘(可延迟几秒)
  ⇒ 崩溃? 从 checkpoint 重放 redo 即可把页追平 ⇒ 数据页"丢了也不怕"
```
**WAL 性能收益的本质**：
1. 随机写 → 顺序写（磁盘/SSD 上顺序吞吐远高于随机 IOPS）
2. 每事务整页 IO → 小日志 IO（修改 16 字节只需记 ~50B 日志）
3. 必须同步的 IO 只剩一次顺序 fsync；页的随机刷盘被推迟并批量合并
4. 多事务的日志在同一批 fsync 中合并落盘（group commit，[005.group-commit.md](./005.group-commit.md)）

> MySQL 有两套 WAL：**InnoDB redo log**（物理日志，保证崩溃安全）与 **binlog**（Server 层逻辑日志，主备复制/PITR 依赖，同样"先写日志"）。本文聚焦 redo 这套实现。

## 2. WAL 的三条铁律与源码实现
```
铁律①: 先记日志、后改页面在磁盘上的次序 —— 日志先行
铁律②: 事务提交前, 它的 redo 必须已 fsync (innodb_flush_log_at_trx_commit=1)
铁律③: 数据页刷盘前, 该页所有修改的 redo 必须已 fsync —— WAL 强制点
```

### 铁律①：先记日志，再产生脏页
&nbsp;&nbsp;页的修改被包进 mtr：`mtr_t::commit`（`mtr0mtr.cc:674`）→ `Command::execute`（`mtr0mtr.cc:858`）。**先**把 redo 拷进 log buffer 分配好 LSN，**然后**才把脏页挂上 flush list：
```cpp
// mtr/mtr0mtr.cc:858 (节选, 顺序即铁律①)
auto handle = log_buffer_reserve(*log_sys, len);      // ① 先分配 redo 的 LSN 区间
m_impl->m_log.for_each_block(write_log);              // ② 把 redo 记录拷入 log buffer
log_wait_for_space_in_log_recent_closed(*log_sys, handle.start_lsn);
add_dirty_blocks_to_flush_list(handle.start_lsn, handle.end_lsn);  // ③ 之后页才成为"脏"
log_buffer_close(*log_sys, handle);
```

### 铁律②：提交前 redo 落盘
```cpp
// trx/trx0trx.cc:1699  —— innodb_flush_log_at_trx_commit 的代码本体
static void trx_flush_log_if_needed_low(lsn_t lsn) {
  switch (srv_flush_log_at_trx_commit) {
    case 2:  flush = false;  [[fallthrough]];         // 只写 OS cache
    case 1:  log_write_up_to(*log_sys, lsn, flush);   // ★=1: fsync 完成才返回
             return;
    case 0:  return;                                  // 不等, 交后台每秒刷
  }
}
// 调用: trx0trx.cc:2449 trx_flush_log_if_needed(trx->commit_lsn, trx) ← COMMIT 时
// log_write_up_to 定义: log/log0write.cc:1084
```
```
COMMIT 时序(=1):  redo 进 buffer ─▶ log_writer pwrite ─▶ log_flusher fsync
                     (log0write.cc:2225/2122)      (:2490/2416)
                  ─▶ flushed_to_disk_lsn ≥ commit_lsn ─▶ 返回客户端 OK
                  之后: binlog(2PC, 见 §5) ─▶ 存储引擎 commit 完成
```

### 铁律③：刷页前 redo 落盘（WAL 强制点）
```cpp
// buf/buf0flu.cc:1171 buf_flush_write_block_low —— page cleaner 刷脏页必经
  /* Force the log to the disk before writing the modified block */
  const lsn_t flush_to_lsn = bpage->get_newest_lsn();          // 页最新修改的 LSN
  if (log_sys->flushed_to_disk_lsn.load() < flush_to_lsn) {
    log_write_up_to(*log_sys, flush_to_lsn, true);             // ★先等 redo 落盘
  }
  ... // 然后才写 16KB 页到 .ibd
```
> 这条铁律也反过来解释了 redo 空间管理：页刷得越慢，checkpoint 之前的 redo 越不能覆盖。日志写满前由 `log_free_check()`（`include/log0chkp.h:310`，等待在 `log0chkp.cc:1243`）主动推 checkpoint，调用点如 `row/row0ins.cc:3085`。

## 3. WAL 全景管线（8.0.30 新 redo 框架）
```
 用户线程                         后台线程
 ────────                        ────────────────────────────────────────
 mtr_t::commit
   │ log_buffer_reserve (log0buf.cc:858, 分配LSN)
   │ 拷入 log buffer
   ▼
 脏页上 flush list ──────┐       log_writer ─▶ pwrite 到 redo 文件 (log0write.cc:2225)
                         │           │
 COMMIT: trx_flush_log_  │       log_flusher ─▶ fsync (log0write.cc:2490)
 if_needed 等到落盘 ◀────┤           │
                         │       log_checkpointer ─▶ 推进 checkpoint,
 page cleaner ───────────┘       写 LOG_CHECKPOINT_1/2 (log0chkp.cc:976/454)
   刷页前 log_write_up_to            让 redo 环形空间可复用
   (buf0flu.cc:1201-1213, 铁律③)

 崩溃恢复: 读 checkpoint → 从 checkpoint_lsn 重放 redo → 页追平 → 回滚未提交事务
          (log/log0recv.cc:3845 recv_recovery_from_checkpoint_start)
```

## 4. LSN / checkpoint：redo 为什么能循环写
```
 redo 文件(环形复用):
 ┌───────────────────────────────────────────────────────────┐
 │ ✓✓✓ checkpoint 前的旧日志(可覆盖) ✓✓✓│▓▓ 未刷日志 ▓▓│ 空闲 │
 └───────────────────────────────────────────────────────────┘
   ▲ last_checkpoint_lsn              ▲ write_lsn
   checkpoint_age = write_lsn - last_checkpoint_lsn, 上限=redo容量
   推进方式 = 把足够老的脏页刷盘(checkpointer 调 page cleaner) → 打 checkpoint
```
- checkpoint 持久化到 redo 文件头部两个交替槽位：`include/log0constants.h:160,166`（`LOG_CHECKPOINT_1=512`、`LOG_CHECKPOINT_2=1536`，HEADER_1/HEADER_2 交替写入 `log0chkp.cc:427 log_next_checkpoint_header`），写入函数 `log/log0chkp.cc:437 log_files_write_checkpoint_low`
- 恢复只从 checkpoint_lsn 开始重放——**checkpoint 越新，恢复越快，但刷页压力越大**（WAL 的内在权衡）

## 5. redo 与 binlog 的配合：内部 XA 两阶段提交
&nbsp;&nbsp;binlog 也是 WAL，但它是 Server 层逻辑日志。两者必须原子（否则主库/从库不一致），靠 2PC 串起来：
```
COMMIT:
 ① InnoDB prepare:  trx_prepare (trx0trx.cc:2945) → redo 记 prepare, fsync
 ② binlog   write:  server 写 binlog + fsync  (binlog group commit)
 ③ InnoDB commit:   trx_commit → trx_flush_log_if_needed(trx->commit_lsn)
                    (trx0trx.cc:2449) + 写 binlog 协调者信息
 崩溃恢复: binlog 有 X → 重放该事务; 无 X → 回滚 InnoDB 中 prepared 的事务
```
> 概念与截图参考 006 目录 README 的"内部XA事务"一节；binlog 组提交机制见 [005.group-commit.md](./005.group-commit.md)。

## 7. 一句话总结
&nbsp;&nbsp;**MySQL 写操作从不直接等"数据落盘"，只等"日志落盘"**：修改先进 Buffer Pool（`mtr0mtr.cc:858` 先记 redo 后挂脏页），COMMIT 等 redo fsync（`trx0trx.cc:1699`），页的刷盘由后台异步批量进行且必须晚于对应 redo（`buf0flu.cc:1201-1213`），checkpoint 负责回收 redo 空间并决定恢复速度（`log0chkp.cc:976`）。这就是 WAL：把昂贵的随机页写变成廉价的顺序日志写，把"不丢数据"的负担从页转移到了日志。
