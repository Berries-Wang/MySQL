# 优化器选择不使用索引的情况
&nbsp;&nbsp;**核心认知：优化器不是"有索引就用"，而是基于代价在「索引访问」与「全表扫描」之间做选择。** 二级索引访问 = 索引区间扫描 + **逐行回表（随机 IO）**；全表扫描 = 顺序读整个聚簇索引。当回表成本高过顺序扫描时，"不用索引"反而是最优解。
> 代价决策入口: `Optimize_table_order::best_access_path`（`sql/sql_planner.cc:980`）；InnoDB 上报的成本：
> - 二级索引访问 → 基类 `handler::read_time`（`sql/handler.h:4862`）＝ `ranges + rows`，**每行 1 个单位（隐含逐行回表的代价）**
> - 聚簇索引/全表扫描 → `ha_innobase::read_time`（`ha_innodb.cc:16850`）＝ `ranges + (rows/total_rows)×scan_time`，**按页分摊**（`scan_time` 见 `ha_innodb.cc:16816`）
>
> 一个"每行一单位"、一个"按页分摊"——匹配行占比一高，索引立刻输给全扫，这就是本篇所有场景的成本根源。

---

## 架构视角：为什么"要不要用索引"必须在 Server 层决策
```
      Server 层(不存数据, 但管决策): best_access_path (sql_planner.cc:980)
              ▲ 引擎经 handler 上报成本: read_time(handler.h:4862)/scan_time
      InnoDB(数据在这, 但不懂 SQL): 报出"扫这段索引+回表"和"全表顺序读"的代价
```
- **分层决定了分工**：数据怎么摆只有引擎知道（所以成本必须由引擎上报）；但 SQL 语义、LIMIT、连接顺序只有 Server 懂（所以"用不用索引"只能 Server 裁决）
- 优化器误判 = 这套"上报-决策"链路的输入失真：统计信息过期（场景四）、开关被关（场景五）——先修输入，再上 hint（[007 篇](./007.索引提示.md)）
- 总架构图见 README 的「MySQL分层架构与查询优化的关系」一节

## 场景一：回表太贵——选择性差的大范围查询
```
二级索引 + 需要回表:
  idx(country) 扫描 → 匹配 80% 的行 → 每行回表(随机IO×N) ──▶ 成本 ≈ N 次随机IO
全表扫描:
  聚簇索引顺序读一遍(顺序IO, 页数固定) ──────────────────▶ 成本 ≈ 表页数
  ⇒ 匹配行数/总行数 越大, 索引越不划算 → best_access_path 选全扫
```
- 为什么贵（代码级）：二级索引访问成本 = `ranges + rows`（`sql/handler.h:4862`，每行 1 单位），全表扫描 = 按页分摊的 `scan_time`（`ha_innodb.cc:16850`）——两者量纲差就是"回表随机 IO"的代价；MRR（[004 篇](./004.MySQL之Multi-Range%20Read.md)）能把随机读变成顺序读，但不能消除每行的计费
- 反推优化手法：**覆盖索引**（`need_to_access_clustered=false`，[001 篇](./001.InnoDB覆盖索引使用之延迟关联.md)）或**把范围缩小**

## 场景二：违反最左前缀——索引根本"接不上"
```
联合索引 idx(a,b):
  WHERE b=1      → a 未知, b 在 B+ 树中不连续 → 无法定位区间
  WHERE a=1 AND b>1 → ✓ 可用
```
- 原理见 [002 篇](./002.InnoDB覆盖索引使用之使用索引扫描来排序.md)的 B+ 树图：b 只在"每个 a 分段内"有序
- 8.0 新增的 Skip Scan 可部分缓解（见 [009 篇](./009.GroupBy-Or-Distinct.md)），但代价仍常高于普通索引

## 场景三：列上套了函数/隐式类型转换——无法构造扫描区间
```sql
WHERE DATE(created) = '2024-01-01'   -- 列上套函数
WHERE phone = 13800138000            -- phone 是 varchar, 值是数字 → 隐式转换
```
- 原理：range 优化器需要把条件翻译成"索引上的连续区间"（`sql/range_optimizer/` 的 range 分析）；对"列的函数"无法翻译 → 退化为全扫
- 优化：改写为区间条件 `created >= '2024-01-01' AND created < '2024-01-02'`；类型保持一致

## 场景四：统计信息过期——优化器"看错了"
- 优化器按持久化统计信息估算行数/区分度；数据大量变化后估算失真 → 该用没用/不该用乱用
- 处理：`ANALYZE TABLE t;`；参数 `innodb_stats_persistent_sample_pages`（采样页数）

## 场景五：优化器开关被关
- `optimizer_switch` 中的 `index_condition_pushdown`、`mrr`、`index_merge`、`skip_scan` 等被 session/global 关闭（对应 [003 ICP](./003.InnoDB之索引下推.md)、[004 MRR](./004.MySQL之Multi-Range%20Read.md)、[006 索引合并](./006.索引合并优化.md) 的开关位）

## 排查工具链
| 工具 | 用法 |
|---|---|
| `EXPLAIN` / `EXPLAIN ANALYZE` | 看 `key`/`rows`/`Extra`（`Using filesort`、`Using index condition`、`Using MRR`…） |
| `optimizer_trace` | `SET optimizer_trace=on;` 执行后查 `information_schema.OPTIMIZER_TRACE`，能看到 `best_access_path` 的候选索引与各自代价 |
| `ANALYZE TABLE` | 刷新统计信息后复测 |
| 索引提示 | 最后手段，见 [007 篇](./007.索引提示.md) |

## 小结
&nbsp;&nbsp;"不用索引"的每种情况，本质都是 **best_access_path（sql/sql_planner.cc:980）算出：全表顺序扫描 < 索引区间扫描 + 回表随机 IO**。DBA 的优化方向因此只有三条：让覆盖索引消灭回表、让条件可构造索引区间、让统计信息真实。
