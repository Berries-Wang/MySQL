# 覆盖索引使用之使用索引扫描来排序
## 概念
&nbsp;&nbsp;MySQL可以使用同一个索引既满足排序，又用于查找行，因此，如果可能，设计索引时应该尽可能地满足这两种任务。
- 满足的条件
    1. 索引的列顺序和ORDER BY子句的顺序完全一致
    2. 索引列的排序方向（倒序或正序）都一样

&nbsp;&nbsp;如此，就可以在覆盖索引上进行排序，而不用回表查询数据了。当需要获取数据行的数据时，结合MRR就可以很快的返回数据(因为基于覆盖索引进行排序就可以获取数据行的主键值了)

&nbsp;&nbsp; 联合索引的好处是已经对第二个键值进行了排序处理。

## 多个键值的B+树是什么样子的?
```sql
  # 表结构
   CREATE TABLE t(
    a INT , 
    b INT,
    PRIMARY KEY(a),
    KEY idx_a_b(a,b)
   ) ENGINE=INNODB
```

&nbsp;&nbsp;通过上图的可以看到，联合索引的数据是按照(a,b)的方式存储的：(1,1)、(1,2)、(2,1)、(2,4)、(3,1)、(3,2)

### 联合索引使用情况如何?
1. SELECT * FROM t WHERE  a=xxx and b=xxx; 可以使用(a,b)这个联合索引
2. SELECT * FROM t WHERE  a=xxx ; 可以使用(a,b)这个联合索引
3. SELECT * FROM t WHERE  b=xxx; 不可以使用(a,b)这棵B+树索引，因为抛开字段a，b列在这棵B+树中并不是连续的.

## 实践一下
### 环境 && 数据准备
```sql
  # MySQL-Version: 8.0.30-debug
  CREATE TABLE buy_log(
    id bigint unsigned primary key auto_increment,
    user_id int unsigned not null,
    buy_date date
  );

  insert into buy_log(user_id,buy_date) values(1,'2009-01-01');
  insert into buy_log(user_id,buy_date) values(2,'2009-01-01');
  insert into buy_log(user_id,buy_date) values(3,'2009-01-01');
  insert into buy_log(user_id,buy_date) values(1,'2009-02-01');
  insert into buy_log(user_id,buy_date) values(3,'2009-02-01');
  insert into buy_log(user_id,buy_date) values(1,'2009-03-01');
  insert into buy_log(user_id,buy_date) values(1,'2009-04-01');

  alter table buy_log add key(user_id); # 索引名称: user_id
  alter table buy_log add key(user_id,buy_date); # 索引名称: user_id_2
 
```

## 优化原理（源码视角，基于 8.0.30）
### 架构视角：排序是 Server 的事，"有序"只能由引擎跨层送上来
```
      Server 层: 执行器收到"已按 buy_date 有序的行流" → 不需要 filesort ✓
      filesort 是 Server 自留地组件 (sql/filesort.cc:366) —— 引擎不认识 ORDER BY,
      "有序"只能作为行流跨层送上来, Server 才能免排序
                        ▲ 有序行流
      InnoDB:  联合索引叶子链(正扫/反扫) —— 天然有序
```
- ORDER BY/GROUP BY 的语义在 Server 层，引擎层根本不知道有"排序"这回事；引擎能给的最大配合就是**让行流天然有序**
- 反过来，凡是 Extra 出现 `Using filesort`/`Using temporary`，都代表这批数据已经"全部进了 Server"才能处理——成本台阶就在跨层边界上

### 原理根源：B+ 树叶子层天然有序
&nbsp;&nbsp;联合索引 (user_id, buy_date) 的叶子页按该序排列、页间双向链表——**沿链正扫/反扫就是 ORDER BY 的结果，"排序"这一步直接消失**。

```
ORDER BY buy_date DESC LIMIT 3 (user_id=1)  的两条路:
方案A filesort: 匹配行全部回表 ──▶ 装入排序缓冲 ──▶ 排序(可能落盘归并) ──▶ 取 3 行
方案B 索引反扫: 从 (1, max_date) 沿叶子链向前走 3 步 ──▶ 只回表 3 次 ✓
```
### 优化器在代码里怎么"选"
| 步骤 | 源码 | 作用 |
|---|---|---|
| 判断"索引即序" | `int test_if_order_by_key`（`sql/sql_optimizer.cc:1735`） | ORDER BY 列是否恰为某索引的连续前缀序 |
| 代价比较 | `bool test_if_cheaper_ordering`（`sql/sql_select.cc:4863`） | "索引扫描(可能多扫几行)" vs "filesort" 谁便宜 |
| 真要排序时 | `bool filesort`（`sql/filesort.cc:366`） | 排序缓冲/外排归并——EXPLAIN 的 `Using filesort` 即走到这里 |
| 反向扫描 | `ReverseIndexRangeScanIterator`（`sql/range_optimizer/reverse_index_range_scan.cc:34`，`Init` :70、`Read` :122） | 对应 EXPLAIN 的 `Backward index scan`（字符串见 `sql/opt_explain_traditional.cc:77`） |

> 场景2 里优化器弃 `user_id` 选 `user_id_2`，就是 `test_if_cheaper_ordering` 的裁决：多扫 3 个索引项 ≪ 一次 filesort；`force index(user_id)` 后索引序与 ORDER BY 无关 → 退回方案 A（`Using filesort`）。

> 场景3 的 `count(*)` 选小索引：辅助索引行小页密，扫"目录"远比扫数据便宜——本质是 [001 篇](./001.InnoDB覆盖索引使用之延迟关联.md) 的 `need_to_access_clustered=false`（查询列全在索引里，引擎层不碰聚簇索引，`ha_innodb.cc:8393`）。

### 为什么索引扫更省
1. **免排序**：省掉 filesort 的排序缓冲/O(N log N) 比较，大结果集还可能溢出到磁盘
2. **免无效回表**：LIMIT 场景索引序扫描天然"取够即停"
3. **反扫也是顺序读**：`ReverseIndexRangeScanIterator` 沿叶子链回走，不是随机跳页
