# "覆盖索引"使用之延迟关联
## 概念
&nbsp;&nbsp;通过使用覆盖索引先获取满足条件的数据行的主键值，再根据主键值关联原表获取需要的行，可以避免MySQL扫描那些不符合条件的行
> 参考: [004.MySQL执行流程/001.SQL语句执行顺序.md](../004.MySQL执行流程/001.SQL语句执行顺序.md) 通过该文档可以知晓MySQL的执行流程

## SQL示例
```sql
   // 覆盖索引 (actor , title , prod_id)
   EXPLAIN SELECT * FROM products INNER JOIN 
     (SELECT prod_id FROM products WHERE actor='SEAN CARREY' AND title LIKE '%APOLLO%') AS t1 
   ON (t1.prod_id = products.prod_id);
```

## 应用示例
### 1. ORDER BY column_a LIMIT offset,size;
```sql
  # 表结构
   {
      tid bigint primary key,
      type varchar(50) not null,
      seller_nick varchar(50),
      created datetime not null,
      modified datetime not null,
      paytime datetime,
      jdp_response text // 订单大json，空间占当前行数据所占空间的87%
      index_sellerNick_created(`seller_nick`,`created`)
   }
  # 优化前的SQL:
  SELECT * FROM trade_info where seller_nick = #{sellerNick} and created >= #{createdStart} and created <=  #{createdEnd}  order by created asc limit #{offset},#{size};
  // 当进行深度分页时，该SQL语句就会非常慢。

  # 优化后的SQL
  SELECT trade.* from trade_info as trade inner join(select tid from trade_info where seller_nick = #{sellerNick} and created >= #{createdStart} and created <=  #{createdEnd}  order by created asc limit #{offset},#{size}) as tids on tids.tid = trade.tid;
  > 优化后，SQL执行速度提升了100+倍。
  > 解析： 两条SQL，都可以使用到索引index_sellerNick_created，但是性能为什么相差这么多呢?
  >> 通过SQL执行流程可以发现，order by limit 操作是将数据全部查询出来，放到一张临时表内，再进行limit,
     即先将符合where条件的数据查询出来，再取需要的数据，其他数据就舍弃了。前一条SQL是查出了全部字段，
     每行数据都需要回表查询，且所需要内存空间较大。而后一条SQL语句则是先查询出tid(主键)，
     再统一进行回表查询所有字段，这样就大大减少了随机IO，也减少了内存的消耗。所以执行速度更快。
```

## 优化原理（源码视角，基于 8.0.30）
### 架构视角：这条优化横跨两层（先读 README 的「MySQL分层架构与查询优化的关系」一节）
```
      Server 层: 优化器选索引(best_access_path, sql_planner.cc:980) → 执行器逐行接收
                        ▲ 延迟关联后: 只收最终 10 行
                        │ 默认: 引擎返回多少行, Server 就收多少行(逐行+格式转换)
      InnoDB:  二级索引(seller_nick,created,+tid)
                        │ 回表 = 引擎层内部的二级索引→聚簇索引随机读, Server 完全不感知
                        ▼
                 聚簇索引(整行数据)
```
- **"回表"是引擎层私有行为**——所以"减少回表"的优化只能动引擎层的访问路径（覆盖索引/延迟关联/MRR），Server 只能改写 SQL 来引导
- "回表/延迟关联"这些词**只对 InnoDB 有意义**（MyISAM 没有聚簇索引）——这就是分层带来的方言差异
- 延迟关联的本质：把 WHERE/ORDER BY/LIMIT 全部留在**引擎层的覆盖索引**上消化完，跨层边界只剩最终行数——动作①（跨层行传输）和②（回表）同时被砍

### 原理根源：二级索引叶子记录 = 索引列 + 主键值（自动附加）
&nbsp;&nbsp;这不是参数开关，而是 InnoDB 的结构性事实——建二级索引时主键列被自动塞进索引：
- `storage/innobase/dict/dict0dict.cc:215` `dict_index_build_internal_non_clust`（建表时对每个二级索引调用，`dict0dict.cc:2454`），把主键列追加进二级索引
- 于是 `(seller_nick, created)` 的二级索引本质上是一张含 `tid` 的"小表"：**只查 `tid` 的查询，根本不需要回表**

### 引擎层怎么决定"要不要回表"
```
ha_innobase::build_template (ha_innodb.cc:8345)  语句开始时逐列检查
   ├─ 查询列不在当前二级索引上 → prebuilt->need_to_access_clustered = true (:8288)
   └─ 列全部被二级索引覆盖     → = false (:8393，用聚簇索引或 whole_row 时恒 true)
        │
        ▼
row_search_mvcc (row0sel.cc:4363) 扫二级索引
   └─ need_to_access_clustered == false → 整条语句不发生任何回表
      需要回表时: :5401 调用回表辅助类 Row_sel_get_clust_rec_for_mysql
      (定义 row0sel.cc:3064，带聚簇记录缓存，避免重复回表)
```
### 为什么"延迟关联"快（对照图）
```
原 SQL(深分页):  SELECT * ... ORDER BY created LIMIT 100000,10
  二级索引扫 100010 行 ──▶ 每行都回表(随机IO×100010) ──▶ Server 层丢弃前 10 万行
                                    ✗ 99% 的回表是白做的

延迟关联:  ① 内层: 二级索引上按序扫, 只取 tid ──▶ LIMIT 在索引上直接截止(零回表)
           ② 外层: 仅对最终 10 条 tid 回表(随机IO×10)
```
&nbsp;&nbsp;三条收益，全部对应上面的代码点：
1. **LIMIT 提前终止**：分页截断发生在覆盖索引扫描阶段（`row_search_mvcc` 循环里），不再为被丢弃的行付回表成本
2. **回表次数 N → 10**：`Row_sel_get_clust_rec_for_mysql` 只被最终行集触发（随机 IO 骤减；回表为什么贵见 [004.MRR 篇](./004.MySQL之Multi-Range%20Read.md)）
3. **覆盖索引页密度高**：二级索引行小、一页放得多，扫描本身读的页更少
