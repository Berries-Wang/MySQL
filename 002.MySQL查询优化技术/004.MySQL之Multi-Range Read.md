# Multi-Range Read (多范围读取优化)
## 总结
1. MRR 是针对于辅助索引进行的优化技术
2. 如果查询能够使用覆盖索引，那么MRR不会带来优化的收益
3. MRR能带来优化是因为将随机I/O转换为了顺序I/O

## MRR介绍
&nbsp;&nbsp;当表很大且未存储在存储引擎的缓存中时，使用**二级索引**上的范围扫描读取行可能会导致对基表的许多随机磁盘访问。通过磁盘扫描多范围读取(MRR)优化，MySQL通过首先仅扫描索引并收集相关行的键来尝试减少范围扫描的随机磁盘访问次数。然后对键进行排序，最后使用主键的顺序从基表中检索行。即Disk-Sweep MRR的目标是减少随机磁盘访问的次数，实现对基表数据的顺序访问。

&nbsp;&nbsp;MRR优化有如下几个好处：
1. MRR使数据访问变得较为顺序。在查询辅助索引时，首先会根据得到的查询结果，按照主键进行排序，并按照主键的顺序进行书签查找。
   - 书签查找： 即通过聚集索引，然后利用聚集索引或RID定位到数据。
2. 减少缓冲池中页被替换的次数
3. 批量处理对键值的查询操作


&nbsp;&nbsp;对于InnoDB和MyISAM存储引擎的范围查询和JOIN查询操作，MRR的工作方式如下：
1. 将查询到的辅助索引键值放到一个缓存中，这时缓存中的数据是根据辅助索引键值排序的。
2. 将缓存中的键值根据RowID进行排序
3. 根据RowID的排序顺序来访问实际的数据文件。

### MRR带来的其他性能提升
#### 减少缓冲池中页被替换的次数（待理解）
&nbsp;&nbsp;InnoDB存储引擎或者MyISAM存储引擎的缓冲池不是足够大，即不能存放下一张表中的所有数据，此时频繁的离散读操作还会导致缓存中的页被替换出缓冲池，然后又不断地读入缓冲池。若是按主键顺序进行访问，则可以将此重复行为降为最低。
   - 理解:因为是顺序I/O,所以在读取数据是读取完上一页，再去读取下一页。即不用在读取第二页之后还需要将第一页替换回来

#### 先拆分查询条件，再进行数据查询（待理解）
&nbsp;&nbsp;若开启了MRR优化，优化器会先将查询条件进行拆分，然后再进行数据查询。
   - 即：避免不符合条件的数据被查询出来，减少磁盘I/O。如下SQL，会对条件进行拆分
      ```sql
        #前提: 在字段salary上有索引
         SELECT
	      * 
         FROM
            salaeies 
         WHERE (from_date BETWEEN '1986-01-01' AND '1995-01-01' )  AND ( salary BETWEEN 38000 AND 40000 );
      ```
      - 拆分为: (38000,('1986-01-01','1995-01-01'))、(38001,('1986-01-01','1995-01-01')).........(40000,('1986-01-01','1995-01-01'))

## 思考
1. 优化的方向： 将随机IO转换为顺序IO，因为随机IO慢于顺序IO

## 优化原理（源码视角，基于 8.0.30）
### 架构视角：MRR 在 handler 接口上包了一层"排序缓冲"
```
      Server 层: 优化器决定启用 MRR → DsMrr_impl(sql/handler.h:6913) 包装 handler 调用
                        │  上送: 按 rowid(主键)排序后的回表行流
      InnoDB:  二级索引扫描 → rowid 收进缓冲 → 缓冲内按主键排序 → 按序回表
```
- 回表是引擎层内部行为（[README·架构篇·动作②](./README.md)），Server 管不了它，但可以**在 handler 接口处改变它的访问模式**——把"边扫边回表"改成"攒一批、排序、批量回表"
- 这就是分层接口的价值：Server 不需要懂 B+ 树，也能重组引擎的读法

### MRR 做了什么（对照图）
```
未开 MRR:
  二级索引范围扫描(按索引列序) ──▶ 每条立即回表 ──▶ 主键乱序 → 聚簇索引随机跳页 ✗

开 MRR:
  ① 扫二级索引, 把 rowid(主键)收进 read_rnd_buffer
  ② buffer 内按主键排序
  ③ 按主键升序回表 ──▶ 聚簇索引顺序推进(顺序IO) ✓
```
### 代码落点（谁在排序、谁决定用不用）
| 环节 | 源码 | 作用 |
|---|---|---|
| 引擎接口入口 | `ha_innobase::multi_range_read_init`（`ha_innodb.cc:23381`，:23386 委托）/ `multi_range_read_next`（:23389） | MRR 的 handler 接口 |
| 通用实现 | `DsMrr_impl`（`sql/handler.h:6913`），核心 `DsMrr_impl::dsmrr_init`（`sql/handler.cc:6406`） | **估计随机读代价**，决定是否值得 DS-MRR；管理 rowid 缓冲与排序 |
| 优化器开关 | `optimizer_switch='mrr=on,mrr_cost_based=on'` | `mrr_cost_based` 让优化器按代价自行取舍 |
| 计划标志 | EXPLAIN Extra `Using MRR` | 生效标识 |

### 为什么快：随机 IO → 顺序 IO
- 聚簇索引按主键物理有序——**按主键序回表 = 沿 B+ 树顺序推进**，机械盘少寻道、SSD 少 4K 随机读
- 缓冲池友好：某页的数据被连续消费完后自然淘汰，不再"读入→逐出→又要读入"反复横跳（原文"减少页被替换次数"的机理）
- 回表次数不变的，变的是**访问模式**——所以原文总结第 2 条成立：**覆盖索引没有回表环节，MRR 无处发力**（`need_to_access_clustered=false`，见 [001 篇](./001.InnoDB覆盖索引使用之延迟关联.md)）
