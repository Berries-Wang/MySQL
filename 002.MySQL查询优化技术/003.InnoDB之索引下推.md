# MySQL之索引下推(Index Condition Pushdown,ICP)
## 小结
+ 索引下推是指将WHERE过滤从服务层下推到存储引擎层
+ 读过《003.索引和锁.md》以及 《010.MySQL查询优化技术.md》 ， 使用索引下推其实也是为了服务器层能够尽可能地少处理些数据，从而提高性能(少处理数据，即更少的磁盘I/O,更少的锁数据行)

## 简介
&nbsp;&nbsp;ICP是MySQL5.6 开始支持的一种根据索进行查询的优化方式。
+ 之前的MySQL版本不支持ICP，当进行索引查询的时候，首先根据索引来查找记录，然后再根据WHERE条件的来过滤记录。
+ 在支持ICP之后，MySQL数据库会在取出索引的同时，判断是否可以进行WHERE条件的过滤，即将WHERE的部分过滤操作放在了存储引擎层。
   - 即索引下推： **从《003.索引和锁.md》看出，下推是指将WHERE过滤从服务器层下推到了存储引擎层**

&nbsp;&nbsp;在某些查询中，ICP会大大减少上层SQL层对于记录的索取，从而提高数据库的整体性能

&nbsp;&nbsp;ICP支持range、ref、eq_ref、ref_or_null类型的查询，当前支持MyISAM 和 InnoDB存储引擎。当优化器选择ICP优化时，可在执行计划的Extra列看到Using index condition提示

## 示例
&nbsp;&nbsp;假设某张表中有联合索引(zip_code , last_name , first_name),并且查询语句如下:
```sql
   SELECT * FROM people WHERE zip_code = '95054' AND last_name LIKE '%etrunia%' AND address LIKE '%Main Street%';
```

&nbsp;&nbsp;对于上述语句，MySQL数据库可以通过查询索引来定位zip_code 等于 95054 的记录，但是索引对WHERE条件的 last_name LIKE '%etrunia%' AND address LIKE '%Main Street%' 没有任何帮助。若不支持ICP优化，则数据库需要先通过索引取出所有zip_code 等于 95054的记录，然后再过滤WHERE之后的两个条件。

&nbsp;&nbsp; 若支持ICP优化，则在取出索引时，就会进行WHERE条件的过滤，然后再去获取记录，这将极大提高查询的效率。当然，**WHERE可以过滤的条件是该索引可以覆盖到的范围**（发挥作用的条件）

## 思考
1. 优化的方向: 减少返回到Server层的数据量，减少IO，减少被加锁的数据量
---
## 优化原理（源码视角，基于 8.0.30）
### 架构视角：ICP 是"打破分层默认"的典型
```
默认(无 ICP):  InnoDB: 按索引取行 → 逐行回表 → 整行跨层上送
                        ▼
              Server:  用 WHERE 过滤 ← 分层设计的默认: 过滤在 Server 层做, 大量行白跑

ICP:          Server:  把条件对象经 handler::idx_cond_push (handler.h:5821) 跨层下推
              InnoDB:  扫索引时就地评估 → 不匹配的行根本不出引擎层
```
- 分层架构的默认契约是"引擎交行、Server 过滤"；ICP 利用 handler 的**能力协商接口**（`idx_cond_push`）把一部分 WHERE 语义"教会"给引擎——这是接口设计留给的优化空间
- 收益自然发生在跨层边界上：跨层行数、回表次数、锁范围同时下降

### 下推的完整链路
```
Server 优化器: 把"只依赖当前索引列"的 WHERE 条件通过接口推给引擎
   handler::idx_cond_push (sql/handler.h:5821 虚函数)
        │
        ▼
InnoDB 接住: ha_innobase::idx_cond_push (ha_innodb.cc:23733) 保存待评估条件
        │
        ▼
row_search_mvcc (row0sel.cc:4363) 扫二级索引, 每条索引记录:
   row_search_idx_cond_check (row0sel.cc:3731 定义)
     调用点 :4629 / :5306 / :5367 —— 都在回表动作之前
        │ 内部回调 innobase_index_cond (ha_innodb.cc:23419) 执行表达式
        ├─ ICP_MATCH        → 继续: 回表取整行, 上送 Server
        ├─ ICP_NO_MATCH     → 跳到下一条索引记录: 不回表、不上送
        └─ ICP_OUT_OF_RANGE → 扫描结束
```
### 为什么快：把"白回的表"砍在引擎层
- 回表 = 按主键查聚簇索引 = **一次随机 IO**（`row0sel.cc:5401` 的回表调用）；`ICP_NO_MATCH` 让不匹配的行连这次 IO 都不发生
- 连带省掉：不必要的一致性读/MVCC 版本回溯（`row_vers_build_for_consistent_read`，见 [MVCC 篇 §7](../003.MySQL事务/007.InnoDB之MVCC实现原理(基于8.0.30源码).md)）、行锁尝试、Server 层行传输
- **减少被锁的行**：锁定读场景下 ICP 过滤掉的行不参与加锁——正是"减少访问量 → 减少锁范围 → 提高并发"的通路
- 适用类型 range/ref/eq_ref/ref_or_null；二级索引收益最大（聚簇索引记录即整行，无处可省）；EXPLAIN 标志 `Using index condition`
