# 索引提示
&nbsp;&nbsp;什么是索引提示优化?

&nbsp;&nbsp;&nbsp;&nbsp; 即 由开发告诉MySQL去使用那个索引进行查询

&nbsp;&nbsp;MySQL数据库支持索引提示(INDEX HINT),显式地告诉优化器使用哪个索引。
- USE INDEX
   + ```sql
       # USE INDEX 只是告诉优化器可以选择该索引，实际上优化器还是会根据自己的判断进行选择
       SELECT * FROM T USE INDEX(a) WHERE A = 1 AND B=2;
      ```
- FORCE INDEX
   + ```sql
         # 强制使用指定索引
         SELECT * FROM T FORCE INDEX(a) WHERE A = 1 AND B=2;
      ```
- IGNORE INDEX
   + ```sql
         # 排除指定索引(常用于"逼"优化器放弃某个坏索引)
         SELECT * FROM T IGNORE INDEX(a) WHERE A = 1 AND B=2;
      ```

---
## 优化原理（源码视角，基于 8.0.30）
### 架构视角：hint 全程发生在 Server 层优化器内部
```
      Server 层: process_index_hints(table.cc:6335) → 改候选索引集
                      → best_access_path(sql_planner.cc:980) 重新决策
      InnoDB:  对 hint 一无所知 —— 它只是被告知"用哪个索引扫"
```
- 优化决策与数据存储分属两层，所以"告诉优化器用哪个索引"只能是 Server 层的事；引擎收到的永远只是既定事实
- 也因此 hint 只能纠偏 Server 的**代价误判**，管不了引擎层的物理成本（回表该贵还是贵）

### hint 的本质：改写优化器的"候选索引集合"
```
解析: hint 存进 TABLE_LIST
   ▼
TABLE_LIST::process_index_hints (sql/table.cc:6335)
   把 USE/FORCE/IGNORE INDEX 归并进表的索引使用集合
   (keys_in_use_for_query / keys_in_use_for_group_by ...)
   ▼
优化器: make_join_statistics 里以该集合为候选池
   (sql_select.cc:2991 先 set_all, 再被 hint 收缩)
   ▼
Optimize_table_order::best_access_path (sql/sql_planner.cc:980)
   在候选索引访问 vs 全表扫描之间按代价二选一
   ├─ USE INDEX(a)    → 候选池只含 a, 但仍可能与全表扫描比价
   ├─ FORCE INDEX(a)  → 排除全表扫描选项, 必须用 a(除非 a 根本用不上)
   └─ IGNORE INDEX(a) → 从候选池剔除 a
```
### 为什么能"优化"，以及风险
- **收益场景**：统计信息过期/代价模型误判时人工纠偏（如优化器选了大范围索引而不走覆盖索引）
- **风险**：hint 把"代价决策"固化成了"人工决策"——索引重建、数据分布变化后可能从优化变成枷锁；FORCE 甚至会阻止优化器选择更优的新索引
- DBA 实践：先用 `optimizer_trace` 看优化器为什么没选你期望的索引（[008 篇](./008.优化器选择不使用索引的情况.md)），hint 只做最后手段
