# 索引合并优化
&nbsp;&nbsp;索引合并访问方法使用对多个范围扫描来检索行，并将这些检索到的行合并在一起。此访问方法仅合并来自单个表的索引扫描，而不能来自跨多个表扫描。在这些基础扫描获取的行集基础上，合并可以产生并集、交集或交集后并集。

## 局限性
<pre>

## 注意事项
> 单表优化，不能跨表

## 优化原理（源码视角，基于 8.0.30）
### 架构视角：索引合并是纯 Server 侧的执行策略
```
      Server 层: 执行器 IndexMergeIterator(sql/range_optimizer/index_merge.cc:55)
                 同时驱动多个引擎扫描迭代器, 在 Server 里合并/去重行集
                        ▲            ▲
      InnoDB:  idx_a 范围扫描     idx_b 范围扫描  (引擎只负责"按索引扫区间")
```
- 引擎不认识 OR/AND 的跨索引语义——它只会"按你给的索引扫区间"；**"两个结果集怎么合并"是 Server 执行器的活**
- 所以合并的代价（rowid 排序/去重）天然落在 Server 侧，这也是它常常不如联合索引的原因

### 三种合并的工作方式（对照图）
```
union(OR):      idx_a 扫描 ──┐
                idx_b 扫描 ──┴→ 行集合并去重 ─────────────▶ 回表
intersect(AND): idx_a 扫描 ──┐  两边都按 rowid 有序(ROR)
                idx_b 扫描 ──┴→ 归并求交集 ─────────────▶ 回表
sort_union:     两边无法按 rowid 排序 → 先合并主键去重 → 统一按主键回表
```
### 代码落点（8.0.30 已迭代器化）
| 实现 | 源码 | 对应 EXPLAIN |
|---|---|---|
| 索引合并主迭代器 | `IndexMergeIterator`（`sql/range_optimizer/index_merge.cc:55`，`Init` :102） | `Using union(...)` / `Using sort_union(...)` |
| rowid 有序交集 | `RowIDIntersectionIterator`（`sql/range_optimizer/rowid_ordered_retrieval.cc:197` Init，:321 Read） | `Using intersect(...)` |
| rowid 有序并集 | `RowIDUnionIterator`（同文件 :240 Init） | `Using union(...)` 的 ROR 形态 |

### 为什么可能更快、又为什么常常不是最优
- **快的情形**：WHERE 是 OR/AND 且各条件**分属不同索引、各自选择性都好**——多个小范围扫描的总代价 < 单索引大范围扫描 + 海量过滤
- **代价所在**：合并需要 rowid 排序/去重、多棵树同时打开；`intersect` 还要求两边都是 ROR（rowid 有序）扫描，条件苛刻
- 所以实战里**优先建联合索引**（一次扫描解决），索引合并常是"无法建联合索引时的兜底"；可用 `EXPLAIN` Extra 与 `optimizer_trace` 观察是否真的划算
- 局限（原文已列）：仅单表、不支持全文索引
