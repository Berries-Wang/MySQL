# Range优化器源码解析（sql/range_optimizer/，基于8.0.30）
&nbsp;&nbsp;**核心认知：range 优化的本质是"把 WHERE 翻译成索引上的连续区间集合，再为每个候选索引估算行数与成本"。入口 `test_quick_select`（range_optimizer/range_optimizer.cc:523）：条件先经 `get_mm_tree` 变成 `SEL_TREE/SEL_ARG` 红黑区间树，再逐索引比价，胜者以 `AccessPath` 形式返回。行数估算走 index dive（InnoDB 真实下潜 B+ 树估页数），等值区间过多时退回统计值。**

> ⚠️ 本源码树中 **`opt_range.cc` 已被拆分**：入口在 `range_optimizer.cc`、条件→区间在 `range_analysis.cc`、`SEL_ARG` 数据结构在 `tree.cc/tree.h`。旧资料里的 `QUICK_SELECT_I` 类族也已不存在，改为"计划期 AccessPath + 执行期 RowIterator"双层（第三节映射表）。关联阅读：[008.优化器选择不使用索引的情况](../008.优化器选择不使用索引的情况.md)、[006.索引合并优化](../006.索引合并优化.md)。

## 二、条件 → 区间：get_mm_tree 与 SEL_ARG 世界（range_analysis.cc）

### 2.1 转换流程

```
WHERE a=5 AND (b>1 AND b<10 OR c='x')
        │
        ▼
get_mm_tree (:842)  递归遍历条件树, "宽松布尔代数"(relaxed boolean
│                   algebra, 注释:795-841): 区间可以是行的超集,
│                   多捞的行靠回表后过滤——这是"能翻就翻"的底气
├─ AND 子树 → tree_and (tree.cc:502)
├─ OR  子树 → tree_or  (tree.cc:679; 不可直接合并时合成 index_merge 备选)
├─ 常量条件 → ALWAYS / IMPOSSIBLE (:878-887)
└─ 单谓词 → get_mm_parts (:1071)
      遍历所有索引的所有 keypart, 找覆盖该字段的
      → get_mm_leaf (:1367) 生成单区间
        (IS NULL/类型转换溢出/DATE截断改写比较符
         /字符集校对/空间MBR 都在这处理)
```

### 2.2 数据结构（tree.h）

```
class SEL_TREE (:870)                     ── 查询整体
  └─ keys[索引数]: SEL_ROOT*              每个索引一棵候选区间树
  └─ merges: SEL_IMERGE 列表              OR 跨索引 → index_merge 备选
  └─ inexact (:919)                       区间是超集, 需回表过滤

class SEL_ROOT (:67)                      ── 单索引的区间集合
  Type{IMPOSSIBLE, MAYBE_KEY, KEY_RANGE} (:74-92)

class SEL_ARG (:464)                      ── 红黑树节点 = 一个keypart上的区间
  ├─ left/right (:515)                    RB树子节点(按区间端点排)
  ├─ next/prev (:516)   ★同keypart的OR关系: 双向区间链表
  └─ next_key_part (:522) ★AND关系: 指向后续keypart的SEL_ROOT

  语义(tree.h:334注释): next/prev是OR, next_key_part是AND
  即联合索引(a,b)上 a IN(1,2) AND b>5 表示为:
    SEL_ARG[1,1]──next──▶SEL_ARG[2,2]        (a的OR链)
        └next_key_part──▶SEL_ROOT(b>5)       (各自的b约束)
```

| 函数 | 行号 | 语义 |
|---|---|---|
| `tree_and` | :502 | 两棵 SEL_TREE 逐索引 AND → `key_and` |

## 四、行数估算：index dive 与 eq_range_index_dive_limit

### 4.1 eq_range_index_dive_limit 是什么

**「index dive（索引下潜）」**：优化器把等值条件变成区间端点，真实调用引擎的 `records_in_range()` 下潜到 B+ 树定位端点页来估算行数——精确，但**每个区间要两次树下降**。`WHERE c IN (上千个值)` 时光估算就可能花掉几百毫秒。`eq_range_index_dive_limit` 就是这里的限流开关：

**「每个区间要两次树下降」解剖**：一个区间有两个端点，Server 层把两个都传给引擎——`records_in_range(keyno, min_endp, max_endp)`（sql/handler.cc:6141）；InnoDB 转成两个元组（ha_innodb.cc:16709 起点 `range_start` / :16716 终点 `range_end`）后，在 `btr_estimate_n_rows_in_range_low`（storage/innobase/btr/btr0cur.cc:4993）里做**两次独立的树下降**：

```
idx_c 叶子页链:      [页A] ── [页B] ── [页C] ──
WHERE c BETWEEN 5 AND 9000
  第1次下降(PAGE_CUR_GE, 5):    根→枝→页A 槽i  ← "第一个 ≥5"     btr0cur.cc:5023
  第2次下降(PAGE_CUR_LE, 9000): 根→枝→页C 槽j  ← "最后一个 ≤9000" btr0cur.cc:5059
  估算 = (A页i之后的行) + (B页按平均行数) + (C页j之前的行)
       ← 页级插值, 不逐行数; 两个端点都不下潜就无法算"跨度"
```

为什么一次不行：要估的是**跨度**，一次下降只落在**一个**端点上——只知"区间从哪开始"，不知"到哪结束"。等值区间（`c=5`）也逃不掉两次：起点是"第一个 ≥5"（GE）、终点是"最后一个 ≤5"（LE），**重复值可能跨页**（第一个 5 在 A 页尾、最后一个 5 在 B 页）。真正"零次下降"的是**唯一索引等值**：Server 层直接短路 `rows=1`（handler.cc:6119-6121 `UNIQUE_RANGE`），根本不 dive。成本账：`IN (N 个值)` ≈ **2N 次下降**，每次 3~4 层页访问（buffer pool 内也是页解析成本）——这就是"几百毫秒"与 limit 限流的由来。

- 定义：**sql/sys_vars.cc:3877** `Sys_eq_range_index_dive_limit`，**DEFAULT(200)**，VALID_RANGE(0, UINT_MAX32)，SESSION 级、**HINT_UPDATEABLE**（可用 `/*+ SET_VAR(eq_range_index_dive_limit=0) */` 语句级覆写）
- 语义（定义处描述原文）：**等值区间数 ≥ limit 时，改用现有索引统计代替 index dive；设为 0 则永远 dive**
- 两个极端：`0` = 最准最慢（永远下潜）；`1` = 只要有等值区间就用统计（最快最糙）

```
WHERE c IN (c1, c2, ..., c500)          ← 500 个等值区间
  未超限: 500 × 2 次 B+ 树下降, 每个值的行数都精确
  超过 200 (默认): 不再下潜, 每个值用 records_per_key 平均区分度估算
      → 快, 但数据倾斜时估算严重失真
      → EXPLAIN rows 突变 / 计划抖动的常见根源
```

### 4.2 切换判定：eq_ranges_exceeds_limit（index_range_scan_plan.cc:1217）

调用点在 check_quick_select（:602-604）：`param->use_index_statistics = eq_ranges_exceeds_limit(tree, &range_count, thd->variables.eq_range_index_dive_limit)`。「怎么数等值区间」（:1217-1260 实现要点）：
- `limit==0` → 恒 false（永远 dive）；`limit==1` → 恒 true
- 沿 SEL_ARG 的 next 链（同 keypart 的 OR 区间）逐个判定，同时满足三条才算一个"等值区间"：
  1. min_flag/max_flag 无开区间标志（排除 `>`、`>=` 等）
  2. `cmp_max_to_min(自身)==0`，即上下界同值（排除 `BETWEEN a AND b`）
  3. **非 NULL 区间——`x IS NULL` 特意不计数**（源码注释：NULL 值的个数在索引统计里大概率失真）
- 联合索引沿 `next_key_part` 递归（仅当后一 keypart 恰为索引下一列），只有"一路等值走到叶子 keypart"的路径才计 1 个
- 计数达到 limit 即短路返回 true（不数完）

### 4.3 超限之后：从 dive 退回统计（records_per_key）

```
check_quick_select 置 use_index_statistics (:603)
  → 物化 QUICK 区间时 range->range_flag |= SKIP_RECORDS_IN_RANGE
     (index_range_scan_plan.cc:522-523)
  → handler::multi_range_read_info_const (sql/handler.cc:6045) 消费:

     for 每个区间 (:6062):
       UNIQUE_RANGE 且非NULL_RANGE  → rows = 1              (:6119-6121)
       SKIP_RECORDS_IN_RANGE 且非NULL_RANGE:
         EQ_RANGE 且该前缀有统计    → rows = records_per_key(keyparts_used-1)
                                       (:6122-6129) ★统计回退
         否则                       → rows = 1 (:6130-6135, 注释: FORCE INDEX
                                      时成本值反正会被忽略)
       其余                          → records_in_range() 下潜 (:6141)
       成本累计 (:6151-6166)
```

即回退后行数 = **该索引前缀的平均每键行数**（全表行数÷前缀区分度），精度从"这个值真实有多少行"降级为"这列平均分布"。另有一条旁路也置 SKIP_RECORDS_IN_RANGE：`get_quick_record_count`（sql/sql_optimizer.cc:6052-6054）经 `check_skip_records_in_range_qualification` 设 `tab->skip_records_in_range`，传播到 index_range_scan_plan.cc:562——**FORCE INDEX 场景**。`optimizer_trace` 里每个索引的对象可直接看到这次切换（index_range_scan_plan.cc:890-897）：
- `"index_dives_for_eq_ranges": false` ← 因超过 limit 改用了统计
- `"index_dives_for_range_access": "skipped_due_to_force_index"` ← FORCE INDEX 路径

## 五、ICP 与 MRR 的挂接点

**ICP（Index Condition Pushdown）**——决策不在 range_optimizer 而在 `QEP_TAB::push_index_cond`（sql/sql_select.cc:2710，调用点 :3119 ref / :3177 range）：
- 前置（:2775-2783）：引擎能力 `HA_DO_INDEX_COND_PUSHDOWN` + `index_condition_pushdown` 开关 + 非多表 UPDATE/DELETE + 非 CONST/SYSTEM + 非聚集主键
- `make_cond_for_index`（:2787）从表条件中抽取"仅引用本索引列"的子条件
- **实际下推：:2834 `tbl->file->idx_cond_push(keyno, idx_cond)`**（handler.h:5821 虚函数；InnoDB 实现 ha_innodb.cc:23733）；剩余条件留在 Server 层
- 效果与排查详见 [003.InnoDB之索引下推](../003.InnoDB之索引下推.md)

**MRR（Multi-Range Read）**——计划期以 `mrr_flags` 内嵌在 range 路径里（check_quick_select :608-624 组装；`multi_range_read_info_const` 末尾 :6155 置 `HA_MRR_USE_DEFAULT_IMPL|HA_MRR_SUPPORT_SORTED`），执行期在 `IndexRangeScanIterator::shared_reset`（index_range_scan.cc:302-349）：按 `mrr_buf_size` 分配缓冲（:312-330）、**:340 `file->multi_range_read_init`** 启动 DS-MRR（rowid 排序批读，随机 IO 变顺序 IO）。BKA 的可用性判断也在其信息接口上（`multi_range_read_info` handler.cc:6204；sql_optimizer.cc:3559-3570）。详见 [004.MySQL之Multi-Range Read](../004.MySQL之Multi-Range%20Read.md)。

## 小结
&nbsp;&nbsp;range 优化器回答的是"这一张表怎么读最省"。三个源码锚点值得记住：`get_mm_tree`（range_analysis.cc:842，宽松布尔代数翻译器——SQL 条件与 B+ 树区间不是一一对应，靠"多捞再滤"扩大可翻译范围）、`check_quick_select`（index_range_scan_plan.cc:567，index dive 与统计切换的开关在 :602-604）、`btr_estimate_n_rows_in_range`（btr0cur.h:535，行数估计的真实底牌是页插值不是数行）。优化器的"看错行数"几乎都发生在这条链上——统计过期、dive 被限流、生成列/函数条件翻不成区间，分别对应 [008 篇](../008.优化器选择不使用索引的情况.md)的场景四、本篇 4.1、场景三。
