# 实战案例：IN 列表超过 200 导致主键计划翻转（基于8.0.30源码）
&nbsp;&nbsp;**结论：按主键 ID 列表批量回查的 SQL，当 IN 列表个数超过 `eq_range_index_dive_limit`（默认 200）时，优化器的行数估算从"逐值精确探测（index dive）"退化为"索引统计"，主键 range 与二级索引 ref 的成本比较天平翻转，执行计划翻到 `idx_user_biz(user_id, biz_id)` 上倒序扫该业务标识下的全部记录、逐条比对 id——大标识几十万行直接超时。修复：id 列表查询强制 `FORCE INDEX (PRIMARY)`（N 次主键点查是可证明的最优，与数据总量无关）。**

> 源码机制详见 [06 篇第四节](./06.Range优化器源码解析.md)（dive→统计切换）与 [09 篇](./09.优化器如何决定用哪个索引.md)（索引选择五级漏斗）。本篇为脱敏实战复盘，表名/链路均为示意。

---

## 一、场景（脱敏示意）

- 表：`t_user_record_{0..31}`（用户参与类记录表，按用户维度分 32 张），主键 `id`，二级索引 `idx_user_biz(user_id, biz_id)`
- 链路：导出任务先按 id 范围分批捞记录（单批 ≤500），再把**本批 id 列表回塞**给通用查询入口重查一遍——回查 SQL 形如：

```sql
SELECT * FROM t_user_record_7
WHERE id IN (?, ?, ... /* 单批最多 500 个 */)
  AND user_id = ? AND biz_id = ?
ORDER BY id DESC
LIMIT ?, ?;
```

现象：该 SQL 间歇性超时；同形 SQL 有时毫秒级返回。

## 二、定位过程（三步）

**实验 1**：EXPLAIN，IN 恰好 200 个 → `type=range, key=PRIMARY, rows=200`，一切正常（当时无法解释线上超时）。

**实验 2**：248 个 id、去掉 `ORDER BY`/`LIMIT` → 仍翻到 `idx_user_biz`——**触发条件不是排序分页，是 IN 个数**。

**边界实验**：同一 SQL 分别取前 200 / 前 201 个 id 各 EXPLAIN 一次——**计划恰好在第 201 个时翻过去**。边界精确落在系统变量 `eq_range_index_dive_limit`（默认 200）上，根因锁定。

## 三、根因（结合源码）

```
IN 个数 > eq_range_index_dive_limit(默认200, sql/sys_vars.cc:3877)
  → eq_ranges_exceeds_limit 计数达标
    (sql/range_optimizer/index_range_scan_plan.cc:1217, 调用 :603)
  → 区间打上 SKIP_RECORDS_IN_RANGE, 不再逐值下潜
    (:522-523; 唯一索引等值区间仍短路 rows=1, handler.cc:6119-6135)
  → 主键 range 与二级索引 ref 的比较整体进入"统计/估算口径"
     (idx 侧行数来自 records_per_key, sql_planner.cc:460-461)
  → 加分项: idx_user_biz 等值命中后, 索引项=(user_id,biz_id,id...),
     叶子内天然按 id 有序 → 倒序扫免掉 ORDER BY id DESC 的 filesort
     (排序成本惩罚见 consider_plan, sql_planner.cc:2501-2507)
  ⇒ 计划翻到 idx_user_biz: 倒序扫该 (user_id,biz_id) 的全部记录,
     在索引项上逐条比对 id(不回表但扫描量=该标识总记录数) → 超时
```

两个放大因素：① 单批 id 个数落在 200~500 区间（恰好在退化区间）；② 该标识下记录量大（只决定"翻错之后的代价"——计划正确时成本与总量无关）。

## 四、修复（已实施）

应用层通用查询入口按 id 列表查询时，动态拼接 `FORCE INDEX (PRIMARY)`：

```sql
SELECT * FROM t_user_record_7 FORCE INDEX (PRIMARY)
WHERE id IN (...) AND user_id=? AND biz_id=?
ORDER BY id DESC LIMIT ?, ?;
```

1. **只在传 id 列表时生效**，其他查询路径计划不受影响；
2. **正确性可证**：按主键列表查询 ≤ N 次点查，不存在更优访问路径，不存在"强制错"的风险；
3. **`ORDER BY id DESC`/`LIMIT` 可保留**：主键按 id 有序，range 倒序读即满足排序（无 filesort），结果上限 = N 行，任何 offset 都不会引发深扫——业务侧无需改传参；
4. FORCE INDEX 的生效点共三处（range 侧禁全表扫 range_optimizer.cc:549、dive 退统计 sql_optimizer.cc:5999、访问路径短路 sql_planner.cc:1128），见 [09 篇第五节](./09.优化器如何决定用哪个索引.md)。

## 五、被排除/不适用的方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 延迟关联（子查询先取 id 再回表） | 不适用 | 它优化的是"跳过的行也回表"；本例 `id IN` 判断在索引项上完成，坏计划本就不回表；内层子查询形状与原 SQL 相同，>200 的估算退化照旧 |
| 去掉 ORDER BY / LIMIT | 无效 | 实验 2 证实触发条件是 IN 个数 |
| "数据量太大" | 只是放大器 | 计划正确时成本与总量无关（≤N 次点查） |
| 调大 `eq_range_index_dive_limit`（或 0=永远 dive） | 实例级兜底 | 动态变量，可根治全实例大 IN 查询，代价是优化阶段多几次 B+ 树下降（微秒级/值，两次下降的解剖见 [06 篇 4.1](./06.Range优化器源码解析.md)）；需 DBA 变更，建议作配合手段 |

## 六、验证清单

1. 原参数（>200 个 id）EXPLAIN：`key=PRIMARY`、`type=range`、Extra 无 `Using filesort`；
2. 实际执行毫秒级；
3. 复跑导出任务，该 SQL 不再进慢日志；
4. 若仍超时且计划正确，看慢日志 `Rows_examined`（约等于 id 个数说明计划没错，超时来自实例负载/锁，另案处理）。

## 七、一句话复盘

&nbsp;&nbsp;大 IN + 多条件 + 排序的查询，计划翻转的开关往往不是数据量而是**估算口径的切换**——`eq_range_index_dive_limit`（200）就是那条看不见的分界线；排查手法就是"沿 IN 个数做二分边界实验"，修复首选"可证明最优路径上的 FORCE INDEX"，实例级再评估调大 limit。通用启示：凡"按唯一键列表回查"的 SQL，都可以无脑钉死主键。
