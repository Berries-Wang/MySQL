# 优化器如何决定用哪个索引（基于8.0.30源码）
&nbsp;&nbsp;**核心认知：优化器对索引的选择不是"某个函数拍板"，而是一条五级漏斗——①候选集（哪些索引有资格参赛）→ ②单表初估（range 分析给每个索引算行数与成本）→ ③连接顺序中比价（`best_access_path` 在 ref/扫描之间裁决）→ ④排序与聚合偏好（索引序能否替代 filesort）→ ⑤计划修正（内表重检/ICP/覆盖/执行器替换）。DBA 看到的"该用没用、不该用乱用"，几乎都能定位到漏斗的某一关。**

> 本篇是 [05](./05.连接顺序搜索与访问路径选择源码解析.md)/[06](./06.Range优化器源码解析.md)/[07](./07.成本模型源码解析.md) 三篇的综合应用视图。场景化的"为什么不用索引"见 [008.优化器选择不使用索引的情况](../008.优化器选择不使用索引的情况.md)；人为干预手段见 [007.索引提示](../007.索引提示.md)。

## 一、全景图：一个索引从存在到被使用，要过五关

```
CREATE INDEX idx_a ON t(a)        ← 索引只是"存在"
        │
┌───────▼─────────────────────────────────────────────────────┐
│ 第一关: 候选集(资格赛)          possible_keys 的由来           │
│   TABLE::init 位图清零          sql/table.cc:2878-2882       │
│   ∩ 可见索引                    TABLE_SHARE::usable_indexes   │
│                                  sql/table.cc:496-499         │
│   ∩ 索引提示 USE/FORCE/IGNORE   process_index_hints           │
│                                  sql/table.cc:6335 (resolver  │
│                                  :1197 调用)                  │
│   过不了 ⇒ EXPLAIN possible_keys 直接没有它                    │
├───────▼─────────────────────────────────────────────────────┤
│ 第二关: 单表初估(test_quick_select, range_optimizer.cc:523)   │
│   WHERE → SEL_TREE 区间树(get_mm_tree) → 逐索引估行数          │
│   (index dive / records_per_key 统计) → 每索引一个成本数字     │
│   候选: 单索引range / index_merge / ROR / loose scan /        │
│         skip scan; 全表扫是它们的共同对手(:541-560 基准)      │
│   行数写入 table->quick_rows[] ← 第三关直接复用               │
├───────▼─────────────────────────────────────────────────────┤
│ 第三关: 连接顺序中比价(best_access_path, sql_planner.cc:980)  │
│   ref 系(find_best_ref:206, 从keyuse出发) 与扫描系比价        │
│   (calculate_scan_cost:769) —— 索引好不好取决于它是首表还是    │
│   内表(prefix_rowcount 放大)、条件过滤折减(filter_effect)     │
│   ★ 大多数"索引没被选"发生在这一关                            │
├───────▼─────────────────────────────────────────────────────┤
│ 第四关: 排序/聚合偏好                                         │
│   get_sort_by_table(:538) → test_if_skip_sort_order(def      │
│   sql_optimizer.cc:2117): 用索引序免 filesort? loose index   │
│   scan 免分组扫描? → 有时"贵一点的索引"因免排序而胜出          │
├───────▼─────────────────────────────────────────────────────┤
│ 第五关: 计划修正                                              │
│   内表 range 重检(:9468-9732) / ICP 下推(sql_select.cc:2834) │
│   / 覆盖索引免回表 / BNL→hash join 执行器替换                 │
└─────────────────────────────────────────────────────────────┘
```

## 二、第一关：候选集——possible_keys 的源码来源

一个物理索引要进入优化器视野，经过三层位图裁剪：

1. **表打开时**：`TABLE::init` 把 `quick_keys / possible_quick_keys / covering_keys / merge_keys / keys_in_use_for_query` 全部清零（sql/table.cc:2878-2882）
2. **基准位图**：`keys_in_use_for_query = TABLE_SHARE::usable_indexes(thd)`（sql/table.cc:496-499，`keys_in_use ∩ visible_indexes`）——**不可见索引（`ALTER INDEX ... INVISIBLE`）在这里就被过滤**，等价于"对优化器不存在"但仍维护写入
3. **索引提示编译**：`TABLE_LIST::process_index_hints`（sql/table.cc:6335，prepare 阶段 sql_resolver.cc:1197 调用）按 USE/IGNORE/FORCE 调整三个位图并置 `force_index / force_index_order / force_index_group` 标志（:6337 起）：
   - `IGNORE INDEX(i)` → 位图清掉 i
   - `USE INDEX(i)` → 位图只剩 i（但不强制——全表扫仍可能胜出）
   - `FORCE INDEX(i)` → 位图只剩 i **且** force_index 置位（后面三处生效点见第五节）

此后两条路各自再筛一遍：
- **range 路**：`keys_to_use ∩ keys_in_use_for_query`（range_optimizer.cc:568）
- **ref 路**：`update_ref_and_keys`（声明 sql_optimizer.cc:130、**定义 :8090**、调用 :5204）——`add_key_fields`（:7248）从 WHERE/ON 里挖 sargable 等值条件，`add_key_part`（:7589）逐 keypart 落成 `Key_use`（keyuse 数组），只收"列=常量/列=先读表列"且索引在位图里的组合

**EXPLAIN 的 `possible_keys` 就是这两个位图的并集**：单表上下文取 `table->possible_quick_keys`（opt_explain.cc:523），连接上下文再并入 `tab->keys()`（:1318-1319）；`possible_quick_keys` 由 check_quick_select（index_range_scan_plan.cc:637）与 skip scan 分析（index_skip_scan_plan.cc:343）回填。

> 推论：`possible_keys` 里没有某索引 ≠ 索引坏，而是它连第一关都没过（被 IGNORE/INVISIBLE/位图裁掉），或条件根本翻不成它的区间/keyuse（函数包裹、隐式转换、违反最左前缀——对应 [008 篇](../008.优化器选择不使用索引的情况.md)场景二/三，源码锚点是 `get_mm_tree` 返回 nullptr，range_analysis.cc:842）。

## 三、第二关：单表初估——test_quick_select 给每个索引算账

详见 [06 篇](./06.Range优化器源码解析.md)。对本篇最重要的三点：

- **每个候选索引独立比价**：`get_key_scans_params`（index_range_scan_plan.cc:819）逐索引调 `check_quick_select`（:567）——行数来自 index dive（InnoDB 页插值，btr0cur.h:535）或 `records_per_key` 统计（超 `eq_range_index_dive_limit` 默认 200 时，sys_vars.cc:3877）
- **胜者只是"暂存"**：结果写进 `table->quick_rows[] / quick_keys`（index_range_scan_plan.cc:629-637），**真正用不用由第三关在连接顺序里重新裁决**——首表估好的 range 计划，换到内表位置可能全变
- **全表扫是隐形参赛者**：`table_scan_cost + 1.1` 的基准（range_optimizer.cc:541-560）；如果最优索引计划的成本 ≤2.0 与全表扫相当，range 直接放弃（:559-560）

```
WHERE a=5 AND b>1         idx_a(a) idx_b(b) idx_ab(a,b)  全表扫
  逐索引: quick_rows[a]=3, cost 4.1   ← dive 出来的
          quick_rows[b]=9000, cost ...  quick_rows[ab]=3, 覆盖
  test_quick_select 胜者: idx_ab(覆盖) → 暂存 quick_keys
  (注意: 这一步还没有"别的表"的任何信息)
```

## 四、第三关：best_access_path——真正的裁决

`Optimize_table_order::best_access_path`（sql_planner.cc:980）在**连接顺序搜索的每一层**为当前表在两类候选间比价：

| 候选 | 来源 | 行数估算 | 成本口径 |
|---|---|---|---|
| ref / eq_ref / ref_or_null | keyuse（第一关产物）经 `find_best_ref`（:206） | `records_per_key`（:460-461）+ **三处复用第二关的 quick_rows**（:451-452/:484-491/~:515-535） | `find_cost_for_ref`（:143）：覆盖走 `index_scan_cost`（:153）、聚集主键走 `read_cost`（:159）、否则 `page_read_cost`（:162） |
| range | 第二关的 quick | `quick_rows` | `calculate_scan_cost`（:769）：`prefix_rowcount × (quick->cost + 过滤成本)`（:831-834） |
| table scan | 无索引 | `stats.records × filter_effect` | `file->table_scan_cost()`（:844） |
| index scan | FORCE INDEX 无 ref 时（:841-843） | `file->read_cost(key,1,records)` | 同左 |

裁决要点（都是"索引输掉"的高频原因）：
- **ref vs 扫描的最终比较**（:1158-1161）：`扫描总成本 < ref成本 + row_evaluate_cost(前缀行数×该表捞出行数)` 才选扫描——所以**同一索引当首表赢、当内表输**（前缀行数放大了 ref 的触发次数），反之亦然
- **内表 range 的 join buffer 降权**（:885-887）：内表用 join buffer 时成本 ×buffer_count——range 计划在内存表位置被系统性看轻
- **四条"扫描必输"短路**（:1086-1132）：其中 (3) InnoDB 聚集索引覆盖扫描（`HA_TABLE_SCAN_ON_INDEX`，:1113-1121）——这就是 InnoDB 上 `type=ALL` 有时其实走聚集索引的原因
- **条件过滤折减 filter_effect**：`calculate_condition_filter`（:1244）把没参与索引的 WHERE 条件按选择性折减行数（开关 `condition_fanout_filter`；直方图提升的就是这一步的精度）
- **LIMIT 的杠杆**：`test_quick_select` 里 `limit < records` 时按索引口径估算（range_optimizer.cc:553-558）；连接序后优化的 LOW_LIMIT 重检见第六节

> [008 篇](../008.优化器选择不使用索引的情况.md)的五个场景，源码落点分别是：回表太贵→两个 read_time 量纲（[07 篇](./07.成本模型源码解析.md)）；最左前缀/函数包裹→第一关 get_mm_tree；统计过期→第二关 dive/records_per_key 输入失真；开关被关→第五节汇总；FORCE INDEX 反噬→下节三处生效点。

## 五、第四关：排序与聚合的偏好——索引序也是成本

- **`get_sort_by_table`**（声明 sql_optimizer.cc:127，调用 :538）：找出"其索引序能满足 ORDER BY/GROUP BY 的表"，作为后续判断的锚
- **`test_if_skip_sort_order`**（def sql_optimizer.cc:2117，由 `optimize_distinct_group_order` :725 与 `test_skip_sort` :966 驱动）：判断"放弃当前访问方式、改用排序索引扫描"是否更省。关键细节（函数体内）：
  - **重跑 range 分析**评估目标索引（:2325/:2437 两处 test_quick_select 调用）
  - `FORCE INDEX FOR ORDER BY / GROUP BY` 优先尊重（`force_index_order/force_index_group` 判定 :2369-2371）
  - **`prefer_ordering_index` 开关**（:2374，默认开）：允许优化器为省 filesort 而"偏爱"排序索引——`LIMIT + ORDER BY` 大表误走索引扫慢查询的常见嫌疑（8.0.21+ 可 `SET optimizer_switch='prefer_ordering_index=off'`）
  - 非 FORCE 且 `select_limit >= table_records`（LIMIT 覆盖全表）时**不**为排序换索引（:2408）——LIMIT 才是这套偏好的前提
- **连接顺序也考虑排序**：`consider_plan` 给"排序表不是首表"的计划加一笔临时表成本（sql_planner.cc:2501-2507）——排序需求间接影响连接顺序，进而影响首表（及其索引）的选择
- **聚合免排序**：loose index scan（`get_best_group_min_max`，group_index_skip_scan_plan.cc:286）用 B+ 树序直接跳读分组；skip scan（index_skip_scan_plan.cc:165）救"缺最左前缀"的等值查询（[009.GroupBy-Or-Distinct](../009.GroupBy-Or-Distinct.md)、006 索引合并的取舍同在第二关发生）

```
SELECT ... FROM t WHERE c BETWEEN 1 AND 100 ORDER BY c LIMIT 10
  第二关: idx_c range cost=50 行; 全表扫 cost=80 → range 暂存
  第四关: ORDER BY c 恰好=idx_c 序 → 免 filesort
          + LIMIT 10 < 100 行 → range_optimizer.cc:553-558 按索引口径
  ⇒ 索引赢得毫无悬念
  反例: ORDER BY 非 c 列 → range+filesort vs 全扫+filesort, 排序成本
        相同 → 回到纯 IO 比较, 大范围 range 可能输给全扫
```

## 六、第五关：计划修正——选定之后的再平衡

- **内表 range 重检**（make_join_query_block，sql_optimizer.cc:9468-9732）：成为内表（`NOT_FIRST_TABLE` :9504）或 `LIMIT < rows_fetched×filter_effect`（`LOW_LIMIT` :9510-9516）时**重跑 test_quick_select**（:9630，无 ON 条件再跑 :9660）——首表的计划到了内表位置会被重新定价，`filter_effect` 置 STALE（:9731）
- **ICP 下推**（`QEP_TAB::push_index_cond`，sql_select.cc:2710；实际下推 `idx_cond_push` :2834）：不改变"选哪个索引"，但把索引列上的剩余条件交给引擎在回表前过滤——等于变相降低该索引的回表成本（[003.InnoDB之索引下推](../003.InnoDB之索引下推.md)）
- **覆盖索引**：`read_index_only`（index_range_scan_plan.cc:858-861）与 `HA_MRR_INDEX_ONLY`（:616-619）让"索引内扫描"与"回表扫描"价差显式化（[001.延迟关联](../001.InnoDB覆盖索引使用之延迟关联.md)）
- **FORCE INDEX 的三个生效点**（全部生效 = 全表扫被禁止，但**不保证用你认为的那个索引**）：
  1. range 侧：`ignore_table_scan` 把全表扫成本置无穷（range_optimizer.cc:549）
  2. 行数侧：`check_skip_records_in_range_qualification`（sql_optimizer.cc:5999，get_quick_record_count :6053-6054 调用）→ dive 退化为统计，trace 显示 `index_dives_for_range_access="skipped_due_to_force_index"`（index_range_scan_plan.cc:890-892）
  3. 访问路径侧：短路启发 (4)（sql_planner.cc:1128）与"FORCE INDEX 无 ref 时按 index scan 计价"（:841-843）
- **hash join 兜底**：BNL 规划被执行器无条件替换为 hash join（sql_executor.cc:2676）——无索引的等值连接不再必然慢，这是"加索引才快"结论的时代边界（[05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)第五节）

## 八、DBA 排障判定流程图：从"索引用得不对"到关口定位

&nbsp;&nbsp;第一节的五关漏斗是"正向"视角（索引怎么被选上），这张图是**逆向排障**视角——从现象出发，每个 ◇ 的答案把问题定位到唯一的一关，再沿锚点直达源码：

```
现象: "这条 SQL 的索引用得不对" (慢 / 全表扫 / 计划抖动)
        │
        ▼
◇ 1. EXPLAIN 的 possible_keys 里有这个索引吗?
   │
   ├─ 没有 ──▶ 【第一关出局】三查:
   │     a. 索引提示?        IGNORE INDEX / USE(别的)
   │                        → process_index_hints (table.cc:6335)
   │     b. 不可见索引?      SHOW INDEXES 看 Visible=NO
   │                        → usable_indexes (table.cc:496-499)
   │     c. 条件翻不成区间/等值?  函数包裹·隐式转换·违反最左前缀
   │                        → get_mm_tree 拿不到区间 (range_analysis.cc:842,
   │                          → 06 篇 2.4 流程图)
   │
   └─ 有 ↓
◇ 2. key 里有它吗?
   │
   ├─ 没有 ──▶ 【第二/三关失真】开 optimizer_trace 看数字:
   │     a. range_analysis 行数 vs 实际行数
   │          rows 偏差大 → 统计过期 → ANALYZE TABLE
   │          大 IN 后 rows 突变 → eq_range_index_dive_limit(200) 降档
   │                        (sys_vars.cc:3877, → 06 篇第四节 / 10 篇实战)
   │     b. best_access_path 的 ref vs scan 比分
   │          回表成本量纲 → 两个 read_time (→ 07 篇第三节)
   │          内表位置被 join buffer 降权 → sql_planner.cc:885
   │     c. 表序不对导致放大? → JOIN_ORDER hint
   │                        (apply_join_order_hints, sql_optimizer.cc:5240)
   │
   └─ 有但慢 ↓
◇ 3. 慢在哪个环节?
   ├─ 回表行数多 ──────▶ 覆盖索引/延迟关联; ICP 生效了吗
   │                     (push_index_cond, sql_select.cc:2834)
   ├─ Using filesort ──▶ 【第四关】排序索引偏好是否误判
   │                     prefer_ordering_index (sql_optimizer.cc:2374)
   ├─ type=ALL 却不太慢 ▶ 正常: 短路(3) InnoDB 聚集索引即"表"
   │                     (sql_planner.cc:1113-1121)
   └─ Using join buffer ▶ 名实不符: 实际执行是 hash join
                         (sql_executor.cc:2676, → 05 篇第五节)
```

> 用法：先跑 `EXPLAIN`（答案 1）→ 再开 `optimizer_trace`（答案 2）→ 最后看 `Extra`（答案 3）。三个观测手段各回答一层问题，顺序不要乱——跳过 possible_keys 直接看 trace，常常在第二三关白忙半天，其实索引根本没进候选。

## 小结
&nbsp;&nbsp;索引选择的完整责任链：**位图（第一关）决定"看得见"，range 分析（第二关）决定"值多少行钱"，best_access_path（第三关）结合表序决定"值不值得"，排序偏好（第四关）偶尔反败为胜，重检与下推（第五关）做最后微调**。排查"索引选择异常"的顺序因此应该是：先看 `possible_keys` 有没有它（没有→第一关，查提示/可见性/条件可翻译性），再看 `key` 有没有它（没有→第二三关，用 optimizer_trace 看行数与成本谁失真），最后看 `Extra`（ICP/MRR/临时表）确认第五关的形态——每一步都有上面这张锚点表可直达源码。
