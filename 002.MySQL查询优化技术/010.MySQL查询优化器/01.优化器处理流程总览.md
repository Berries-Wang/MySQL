# 优化器处理流程总览（基于8.0.30源码）
&nbsp;&nbsp;**核心认知：MySQL 优化器不是一个函数，而是一条"两级流水线"——先做与代价无关的逻辑优化（`Query_block::prepare`，sql/sql_resolver.cc:173，改写查询结构），再做与代价相关的物理优化（`JOIN::optimize`，sql/sql_optimizer.cc:281，搜索表序与索引）。两级之间以 `Query_expression`（UNION 单位）为骨架串联。**

三个关键点：
- **优化与执行彻底分离**：`optimize` 只产出 `AccessPath` 树（计划），`Iterator` 树由 `Query_expression::optimize` 末尾统一创建，执行只是 `Init + 循环 Read` 的火山模型驱动
- **每个 `Query_block` 一个 `JOIN`**：UNION 有几个分支就优化几次；派生表/子查询作为内部 query_block 被递归优化（sql_select.cc:1827-1829）
- **EXPLAIN 不执行**：`explain_query` 在 `unit->execute` 之前返回，看到的就是 `PLAN_READY` 状态的计划

## 二、两级优化的分工

| | 逻辑优化（Resolver/Prepare） | 物理优化（Optimizer） |
|---|---|---|
| 入口 | `Query_block::prepare` sql_resolver.cc:173 | `JOIN::optimize` sql_optimizer.cc:281 |
| 决策依据 | **规则**（可合并就合并、可下推就下推） | **代价**（连接顺序、索引选择、临时表） |
| 输入→输出 | AST → 改写后的 AST（表合并进来了、子查询扁平化了） | 改写后 AST → AccessPath 树 |
| 典型动作 | 视图/派生表合并、外连接转内连接、semi-join 化、IN→EXISTS、条件下推 | 常量表检测、range 分析、连接顺序搜索、ICP、排序消除、临时表规划 |
| 详细拆解 | [02 篇](./02.逻辑优化源码解析-Prepare阶段.md) / [03 篇](./03.子查询优化源码解析.md) | [04 篇](./04.物理优化源码解析-JOIN之optimize.md) / [05 篇](./05.连接顺序搜索与访问路径选择源码解析.md) / [06 篇](./06.Range优化器源码解析.md) |

```
        逻辑优化                                物理优化
┌─────────────────────────────┐    ┌─────────────────────────────────┐
│ "这句话在说什么"               │    │ "这句话怎么执行最省"              │
```

## 三、Prepared Statement：为什么第二次执行更快，re-prepare 何时发生

&nbsp;&nbsp;PS（`PREPARE stmt FROM '...'`）的执行走 `mysql_sql_stmt_execute`（sql/sql_prepare.cc:1935）→ `Prepared_statement::execute_loop`（sql/sql_prepare.cc:2974）→ `Prepared_statement::execute`（:3359）→ `mysql_execute_command`（调用点 :3540），最终仍汇入 `Sql_cmd_dml::execute`。

**重复执行的省略与不省**：
- **省**：解析、`prepare`（语义分析/逻辑改写整套）——靠 `is_prepared()` 标志（sql_select.cc:532/535）跳过
- **不省**：`optimize` 每次都重跑。因为 `Query_expression::optimize` 前置断言 `!is_optimized()`（sql_union.cc:685），而每次执行尾部 `lex->cleanup` 会复位该状态；且表统计信息可能已变，代价搜索必须重来
- PS 的 prepare 产物（AST、Item 树）存在语句 arena 中；`Prepared_statement::execute` 内的 `Statement_backup`（sql_prepare.cc:3425）负责把 THD 切到 PS arena、退出时还原，执行期绑参（`set_parameters` :1958）

**re-prepare 的三个触发点**（`execute_loop`，sql/sql_prepare.cc:2974）：
1. 语句含 UDF：无条件 reprepare（:3001）
2. 绑定参数类型漂移（如 INT→DECIMAL，`check_parameter_types()` :3012-3025）
3. **元数据变更**：对 `CF_REEXECUTION_FRAGILE` 命令装 `Reprepare_observer`（:3034-3041）；表定义版本变化时触发 `ER_NEED_REPREPARE`（机制见 `ask_to_reprepare` :2198）→ `reprepare()`（:3180，经 `swap_prepared_statement` 换新 arena 后重新走完整 prepare :3217）

```
PREPARE s FROM 'SELECT ...'         第一次 EXECUTE           后续 EXECUTE
       │                                │                      │
  parse+prepare(逻辑优化) ──缓存AST──▶ cleanup→重绑表 ──▶ cleanup→重绑表
  (resolve/改写只做一次)              lock_tables              │
                                     optimize(物理优化) ◀─────┤ 每次都重新
                                     create_iterators         │ 代价搜索!
                                     execute(逐行) ◀──────────┘
                                     │
                     期间表结构变了(DDL) ─▶ ER_NEED_REPREPARE ─▶ 自动 reprepare 重来
```

## 四、优化器的两条并行路线：传统优化器 vs Hypergraph（8.0.30 现状）

- **传统优化器**（默认）：`JOIN::optimize` 主线 → `make_join_plan`（sql_optimizer.cc:5168）→ 贪心+受限穷举搜索（[05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)）
- **Hypergraph 新优化器**（试验特性）：`Sql_cmd_dml::prepare`（sql_select.cc:333-345）置 `lex->using_hypergraph_optimizer`；`JOIN::optimize` 在 **sql_optimizer.cc:551** 分叉：
  ```
  :552 remove_in2exists_conds
  :560 FindBestQueryPlan     (sql/join_optimizer/join_optimizer.cc:5834)
       └─ :5867 MakeJoinHypergraph (make_join_hypergraph.cc:3131)
          + DPhyp 动态规划 (subgraph_enumeration.h:666)
  :562 FinalizePlanForQueryBlock (join_optimizer/finalize_plan.cc)
  :614 set_plan_state(PLAN_READY) → return（跳过传统主线全部阶段）
  ```
  sql_optimizer.cc:619-621 的注释直言："All of this is never called for the hypergraph join optimizer!"
- 开关：`SET optimizer_switch='hypergraph_optimizer=on'`（定义 sys_vars.cc:3424）。8.0.30 默认关闭，详见 [08 篇](./08.Hypergraph新优化器与迭代器执行器.md)

## 五、一次完整优化里各阶段的产物变化

```
阶段             数据形态                       载体
─────────────────────────────────────────────────────────────────
解析完成          LEX + Query_block(AST)         thd->lex
逻辑优化后        AST(结构已变): 视图消失/子查询   Query_block 树
                 扁平化为 sj-nest/外连接转内连接
make_join_plan前  JOIN_TAB 数组(best_ref)         join->best_ref
  ├ range分析     每表 quick_rows/AccessPath       tab->range_scan()
  ├ 连接顺序搜索  best_positions[]                 join->best_positions
  └ get_best_combination  固定表序的 JOIN_TAB/QEP_TAB  join->qep_tab
make_tmp_tables_info  临时表管线(DISTINCT/窗口/排序) qep_tab 后段
create_access_paths   ★AccessPath 树               join->m_root_access_path
CreateIteratorFromAccessPath  ★Iterator 树        unit->m_root_iterator
ExecuteIteratorQuery   Init/Read 逐行流            (执行)
```

> EXPLAIN 看到的 `type/key/rows/Extra` 分别来自：访问方式（POSITION.key + type）、行数估算（POSITION.prefix_rowcount）、Extra 标志（如 `Using index condition` 来自 ICP 下推 sql_select.cc:2834、`Using index for skip scan` 见 opt_explain_traditional.cc:61）。想看优化器决策过程用 `optimizer_trace`，`SET optimizer_trace='enabled=on'` 后查 `information_schema.OPTIMIZER_TRACE`，能看到 `best_access_path` 的候选与代价、`pruned_by_cost/heuristic` 剪枝记录（sql_planner.cc:2822-2859 的 trace 点）。

## 小结
&nbsp;&nbsp;记住三级骨架就能在源码里不迷路：**`Sql_cmd_dml::execute`（sql_select.cc:490）管调度 → `Query_block::prepare`（sql_resolver.cc:173）做逻辑改写 → `JOIN::optimize`（sql_optimizer.cc:281）做代价搜索并产出 AccessPath**；执行交给 `Query_expression` 层创建的 Iterator 树（sql_union.cc:833/1185）。PS 只缓存前两级，代价搜索每次执行都重做。
