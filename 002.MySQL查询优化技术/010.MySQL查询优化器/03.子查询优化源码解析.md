# 子查询优化源码解析（基于8.0.30）
&nbsp;&nbsp;**核心认知：子查询优化的决策链是"三选一"——`Query_block::resolve_subquery`（sql/sql_resolver.cc:1342）在 prepare 阶段判定候选，`flatten_subqueries`（:3760）落地：能转 semi-join 就转（并入主查询一起做代价搜索），不能转就 IN→EXISTS（注入触发器条件逐行探测）或物化（一次性建哈希索引表）。semi-join 的 5 种执行策略则推迟到 optimize 阶段，在连接顺序搜索中逐前缀比价选出（`advance_sj_state`，sql_planner.cc:4108）。**

## 二、resolve_subquery：候选判定（sql_resolver.cc:1342）

- **semi-join 候选的 16 条要求**（:1435-1484，注释逐条列出）：IN 或 EXISTS 子查询、非 UNION、内层无聚合/HAVING/窗口、谓词位于 WHERE 或 ON 的 AND 顶层（`OR` 里不行！）、外层不是单表 UPDATE/DELETE、双方都有表、无 STRAIGHT_JOIN、LHS 表达式确定性、LIMIT 语义合法（`is_row_count_valid_for_semi_join` :1310）等
- **antijoin 例外**（:1417-1423）：**保持子查询、不转 antijoin** 的是——非相关的 `NOT EXISTS`、以及 LHS 为常量的非相关 `NOT IN`（这两类在优化期一次求值更划算，见 :1408-1416 注释）；secondary engine 不支持 antijoin 转换。即能转 antijoin 的典型是 **LHS 非常量的 NOT IN**
- **转派生表候选**（:1531-1553）：`try_convert_to_derived`，受 `optimizer_switch=subquery_to_derived`（sql_const.h:226，8.0.21+ 默认 off）
- 都不满足 → :1555 `subq_predicate->select_transformer(thd, this)` 兜底改写

`flatten_subqueries`（:3760）的落地顺序：候选排序（相关子查询优先、表多优先，:3815-3836）→ 转派生表（:3850）→ 已转换谓词替换为 TRUE/FALSE（:3912-3921）→ `convert_subquery_to_semijoin`（:3934）→ 对未定型的补做 IN→EXISTS（:3951）。

`convert_subquery_to_semijoin`（:2928）做了什么：确定插入点 WHERE 或 ON（:2956-3050）；NOT IN 改写成 LEFT JOIN + aj-nest（:3053-3115）；创建 `(sj-nest)`/`(aj-nest)` 并入父表链（:3120-3199）；`build_sj_exprs` 构造外层列=内层列等值（:3206-3208）；`Semijoin_decorrelation` 去相关（:3245）。

## 三、IN→EXISTS：到底注入了什么条件

入口链：`Item_in_subselect::select_transformer`（item_subselect.cc:2389）→ `select_in_like_transformer`（:2416，:2446-2451 创建包装器 `Item_in_optimizer`，item_cmpfunc.h:485）→ `single_value_transformer`（:1706，内含 ALL/ANY→MIN/MAX 改写 :1751-1826）/ `row_value_transformer`（:2133）。

**`single_value_in_to_exists_transformer`（item_subselect.cc:1914）注入的条件**：

| 子查询形态 | 注入到内层 WHERE | 注入到内层 HAVING | 何时包触发器 |
|---|---|---|---|
| 普通（无聚合/无GROUP BY） | `(left_expr = inner) OR inner IS NULL` | `Item_is_not_null_test(inner)` | `left_expr` 可空且允许 null 时包 `Item_func_trig_cond` |
| 有 GROUP BY/HAVING/聚合/窗口 | —（WHERE 不动） | `left_expr = Item_ref_null_helper(...)` | 必要时包触发器 |
| 无表单行子查询 | 直接归约为等式 `RES_REDUCE`（:2101-2125） | | |

**为什么注入 `OR inner IS NULL` 和 `IS NOT NULL` 测试**：IN 的三值逻辑要求"能区分 `NULL IN (空集)`（→NULL）与 `FALSE`"。内层一旦扫到一行 `inner IS NULL` 且 `left_expr` 为 NULL，IN 结果是 NULL 不是 FALSE——所以必须让内层"多捞一行 NULL 比对行"再由外层判空。多列版本 `row_value_in_to_exists_transformer`（:2200）同模式逐列注入（:2250-2353）。

**`Item_func_trig_cond`**（item_cmpfunc.h:811）：守卫谓词 `guard ? cond : TRUE`，触发类型枚举 `enum_trig_type`（:813-838）：
- `OUTER_FIELD_IS_NOT_NULL`：IN→EXISTS 专用（本篇，guard=外层左表达式当前行非 NULL）
- `FOUND_MATCH`：外连接 WHERE 下推时"匹配到才判定"
- `IS_NOT_NULL_COMPL`：外连接执行时 NULL 补齐行关闭下推条件

```
SELECT * FROM t1 WHERE t1.a IN (SELECT b FROM t2 WHERE t2.c>5)
                    │ 改写后
SELECT * FROM t1 WHERE <Item_in_optimizer>(
   t1.a <INJECTED>,
   SELECT b FROM t2 WHERE t2.c>5
     AND (t1.a = t2.b OR t2.b IS NULL)   ← 注入的WHERE(相关条件!)
     HAVING <t2.b IS NOT NULL>            ← 注入的HAVING(判空测试)
)
-- 优点: 子查询能用上 t2.b 的索引做相关查找(逐行嵌套循环)
-- 缺点: 外层多少行, 内层就探测多少次(相关)
-- 物化就是它的竞争对手: 一次建表+哈希查找, 换掉 N 次相关探测
```

## 四、子查询物化（SUBQ_MATERIALIZATION）

定案点：`Item_in_subselect::finalize_materialization_transform`（item_subselect.cc:438）——**在 optimize 阶段由 `JOIN::decide_subquery_strategy`（sql_optimizer.cc:10793，调用点 :5262）触发**，即物化 vs IN→EXISTS 是运行前的最后一刻二选一：
- :448 置策略 `SUBQ_MATERIALIZATION`
- :459-461 `remove_in2exists_conds` 撤销 IN→EXISTS 注入的条件（两套改写互斥）
- :478-490 创建 `subselect_hash_sj_engine`（item_subselect.h:858，继承 `subselect_indexsubquery_engine` :798）——内层结果物化成带哈希索引的临时表

策略枚举 `Subquery_strategy`（item_subselect.h:390-410）：UNSPECIFIED / CANDIDATE_FOR_IN2EXISTS_OR_MAT / CANDIDATE_FOR_SEMIJOIN / CANDIDATE_FOR_DERIVED_TABLE / SEMIJOIN / DERIVED_TABLE / SUBQ_EXISTS / SUBQ_MATERIALIZATION / DELETED。

**倾向物化的典型形态**：外层行数大、子查询不相关（物化一次够用）、内层结果集不大——`x IN (SELECT c FROM t2)` 变成"建临时表(哈希索引) + 每外表行 O(1) 探测"。EXPLAIN 里表现为 `SELECT ... SUBQUERY` 型行 + `auto_key`（临时表自动索引）。

## 五、semi-join 的 5 种执行策略：搜索中怎么选

策略常量（8.0.30 是宏，非 enum）：**sql/sql_select.h:307-312**

```
SJ_OPT_NONE               0   未定
SJ_OPT_DUPS_WEEDOUT       1   重复剔除(行ID去重临时表)
SJ_OPT_LOOSE_SCAN         2   松散扫描(跳过重复索引前缀)
SJ_OPT_FIRST_MATCH        3   首个匹配即短路
SJ_OPT_MATERIALIZE_LOOKUP 4   物化+索引查找
SJ_OPT_MATERIALIZE_SCAN   5   物化+全表扫连接
```

**选择发生在连接顺序搜索过程中**（不是独立的 `JOIN::optimize_semijoin_nests`——该名字在 8.0.30 不存在；物化预估函数 `optimize_semijoin_nests_for_materialization` 在 sql_optimizer.cc:6421，调用点 :5251）：

- **`Optimize_table_order::advance_sj_state`（sql_planner.cc:4108）**：`best_extension_by_limited_search`（:2812 调用）每把一张表放进前缀，就增量维护并就地比价 5 种策略：

```
advance_sj_state (sql_planner.cc:4108) 逐前缀评估:
├─ FirstMatch        :4173-4284   内表链上"首匹配短路"是否成立
│                                 (找 inner 顺序满足则跳过该外层行剩余内表)
├─ LooseScan         :4285-4412   驱动表可用索引跳重复
│                    (fill_driving_table_position :1604)
├─ MaterializeLookup :4455-4474   先物化 sj 整体再按索引探测
│                    (order_allows_materialization :2204;
│                     mat_lookup_access_paths :3905)
├─ MaterializeScan   :4477-4519   物化后全扫连接 (mat_scan :3823)
└─ DuplicatesWeedout :4522-4582   兜底策略: 无其他可用时强制选它
                     (dupsweedout_access_paths :3950; 调用 :4554,
                      兜底条件 dups_producing_tables :4565-4572)
选中 → pos->sj_strategy = 最佳; 前缀成本随之调整
```

- 定稿回填：`fix_semijoin_strategies`（sql_planner.cc:3365，choose_table_order 末尾 :2034 调用）从右往左扫 `best_positions` 落地各策略的 POSITION
- 执行结构搭建：`setup_semijoin_dups_elimination`（sql_select.cc:1335，5 种策略的表序模式文档在 :1275-1333）；物化 nest 的内表挪位在 `get_best_combination`（sql_optimizer.cc:3014-3026）
- 开关：`semijoin` / `materialization` / `loosescan` / `firstmatch` / `duplicateweedout`（sql_const.h:214-218），对应 optimizer_switch 位

五种策略直觉对比（表序中 outer=外表行、inner=sj 内表）：

```
FirstMatch:    outer → i1 →(短路回outer)        匹配到第一行就跳下一个外层行
LooseScan:     索引跳读 inner 去重 → outer       内表索引前缀去重,重复值只读一次
MaterializeLookup: [物化inner成临时表] → outer → 探测(hash索引)
MaterializeScan:   [物化inner成临时表] → outer → (整表扫)   物化表小到全扫更便宜时
DuplicatesWeedout: 原序连接(允许重复) → 行ID去重   保序兜底: 先照常连,再用rowid临时表剔除重复
```

## 六、子查询类型 × 可用策略矩阵

| 子查询类型 | semi/anti-join | 转派生表连接 | IN→EXISTS | 物化 | 专属改写 |
|---|---|---|---|---|---|
| `expr IN (subq)` | ✅（:1465-1484；NOT IN→antijoin） | ✅（:1531-1553） | ✅（:1914） | ✅（:438） | 无表单行→等式归约（:2101-2125） |
| `[NOT] EXISTS` | ✅（同上条件） | ✅（仅无聚合 :1509） | 天然即 EXISTS | ❌ | — |
| 标量子查询 | ❌ | ✅（transform_scalar_subqueries… :7471，默认关） | 不适用 | （经派生表间接物化） | 平凡归约（:1114） |
| `> ANY / < ALL` | ❌ | ❌ | ✅（:2697→:2416，比较符取反） | ❌ | **MIN/MAX 改写**（:1751-1826） |
| UNION 子查询 | ❌（is_part_of_union 否决） | ❌ | ✅（逐成员 :2071-2100） | ❌ | — |

> **`> ANY / < ALL` 的 MIN/MAX 改写**（single_value_transformer 内 :1751-1826）：`x > ALL (SELECT v ...)` 且内层有 `v` 上可用索引时改写为 `x > (SELECT MAX(v) ...)`——把逐行全比较变成一次 MAX 查找，EXPLAIN 显示 `SELECT ... UNCACHEABLE SUBQUERY` 消失、变成可缓存的标量。

## 七、优化器怎么暴露这些选择

- EXPLAIN 的 `select_type`：`SUBQUERY`（IN→EXISTS/标量，相关或未定）vs `DEPENDENT SUBQUERY`（相关）vs `MATERIALIZED`（物化，SQL 层看到的独立行）vs semi-join 化后**子查询行消失**（并入主查询表序，这是 semi-join 的标志）
- `optimizer_trace` 能看到 `join_optimization` 中 `semijoin_strategy_choice` 各策略的成本比较
- 常见调优方向（对应本篇机制）：
  - `WHERE id IN (SELECT ...)` 想走 semi-join：别把 IN 放进 `OR`（:1435 条件之一被破坏）；别在子查询里塞无意义 LIMIT
  - 物化 vs IN→EXISTS 失控：`optimizer_switch` 的 `materialization=off/on` 直接干预（定案在 decide_subquery_strategy :10793）
  - semi-join 策略误选：分别有 `firstmatch/loosescan/duplicateweedout` 开关位（sql_const.h:214-218）

---

## 小结
&nbsp;&nbsp;子查询优化分两级：**prepare 期定"形态"**（resolve_subquery/flatten_subqueries：semi-join 化、IN→EXISTS 注入、派生表化），**optimize 期定"执行方式"**（advance_sj_state 在表序搜索中逐前缀比价 5 种 semi-join 策略；decide_subquery_strategy 在 IN→EXISTS 与物化间二选一）。理解两条注入条件（`OR inner IS NULL` / `IS NOT NULL`）就理解了为什么改写后的子查询有时反而变慢——多捞的那一行 NULL 与逐行相关探测都是改写的代价，物化与 semi-join 就是为消灭它们而生。
