# 连接顺序搜索与访问路径选择源码解析（sql/sql_planner.cc，基于8.0.30）
&nbsp;&nbsp;**核心认知：传统优化器的连接顺序搜索是"贪心 + 深度受限穷举"的混合算法——外层 `greedy_search`（sql_planner.cc:2322）每轮只固定一张表，内层 `best_extension_by_limited_search`（:2723）在 `optimizer_search_depth` 深度内做 DFS 穷举并剪枝；≤7 张表退化为纯穷举。每张表进前缀时由 `best_access_path`（:980）在 ref/eq_ref/range/全扫/索引扫等候选中按成本选访问路径。**

> 入口：`JOIN::make_join_plan`（sql_optimizer.cc:5168）在 **:5255** 调 `Optimize_table_order(thd, this, nullptr).choose_table_order()`（类声明 sql_planner.h:74）。8.0.30 已无 `JOIN::choose_plan` 旧名。

## 一、choose_table_order 总控（sql_planner.cc:1945）

```
choose_table_order() (:1945)
├─ :1951 const 表前缀成本清零（已由 extract_const_tables 定死）
├─ :1955 全部是 const 表 → best_positions=positions 直接返回
├─ :1964 reset_nj_counters（嵌套连接交织状态复位）
├─ :1966 STRAIGHT_JOIN 判定
├─ :1974-1992 best_ref[] 预排序:
│     ├─ 有 sj-mat nest: 内表嵌到最前 (Join_tab_compare_embedded_first)
│     ├─ STRAIGHT_JOIN: 按书写依赖序 (Join_tab_compare_straight)
│     └─ 默认: 启发式按记录数升序 (Join_tab_compare_default) ← 小表优先
├─ :2002 cond_fanout_filter 开启时预置条件过滤位图
├─ :2016 recalculate_lateral_deps（lateral 依赖重算）
├─ :2020 STRAIGHT_JOIN ? optimize_straight_join(:2112)
│                    : greedy_search(:2322)          ★主线
└─ :2034 fix_semijoin_strategies(:3365)   定稿回填 sj 策略
```

`optimize_straight_join`（:2112）不重排表：按 best_ref 顺序逐表 `best_access_path`（:2142）；若 `sort_by_table` 不是首表，成本补一笔排序（`cost += rowcount`，:2160-2162）；末尾 `best_read = cost - 0.001`（:2172，减 0.001 保证浮点比较可复现）。

## 二、greedy_search：外层贪心（:2322）

```
greedy_search(remaining_tables) (:2322)
do {
  best_read = DBL_MAX (:2344)                    每轮重置最优
  best_extension_by_limited_search(remaining,    ★深度受限穷举一轮
      idx, search_depth) (:2347)
  if (size_remain <= search_depth) return        最后一轮已得完整计划
                                                (:2355-2368)
  best_table = best_positions[idx].table         取本轮最优扩展的
  positions[idx] = best_pos (:2371-2378)         第一张表 ★固定进前缀
  check_interleaving_with_nj (:2392)             嵌套连接交织合法性
  best_table 移到 best_ref[idx]（memmove 保序 :2398-2409）
  remaining_tables &= ~best_table->map (:2411)
} while (true)
```

**混合语义**：每轮穷举虽然探索了 depth 张表的深度，但**只采纳第一张表**，剩余表放回池子重新搜索——前缀选择是贪心的，前缀内部是穷举的。这样复杂度从 O(N!) 降为 **O(N·N^depth/depth)**（注释 :2634-2636）。

## 三、best_extension_by_limited_search：深度受限 DFS（:2723）

```
best_extension_by_limited_search(remaining_tables, idx, depth) (:2723)
│
├─ :2756 保存 best_ref[idx..]（返回前恢复）
├─ :2764 for 每张候选表 s（best_ref 按#rows升序）:
│   ├─ :2773 std::swap(best_ref[idx], *pos)      无条件换位保序
│   ├─ :2775-2778 过滤: s∈remaining && ∉eq_ref串
│   │            && 依赖已满足 && 嵌套连接交织合法
│   ├─ :2792 best_access_path(s, position)       ★选访问路径(第四节)
│   ├─ :2796 position->set_prefix_join_cost(idx) 累计前缀成本/行数
│   ├─ :2812 has_sj ? advance_sj_state(...) : no_semijoin()
│   │            ★semi-join 5策略就地比价(→03篇第五节)
│   ├─ ✂ 剪枝① 成本剪枝 (:2822-2831)
│   │    prefix_cost >= join->best_read → trace "pruned_by_cost" 弃
│   ├─ ✂ 剪枝② 启发式剪枝 (prune_level==1 时, :2837-2859)
│   │    本层已有 (rowcount,cost) 双更优的候选 && 当前无优势
│   │    && s 非排序表 → trace "pruned_by_heuristic" 弃
│   ├─ :2865 depth>1 且还有剩余表?
│   │   ├─ :2874 eq_ref 启发式: 唯一索引1::1表(rows<=1)
│   │   │   → eq_ref_extension_by_limited_search(:3070)
│   │   │     一口气串多张 eq_ref 表, 不逐层展开
│   │   └─ :2913 递归 (remaining-s, idx+1, depth-1)
│   └─ :2918 depth 用尽/表排完 → consider_plan(idx) 完整计划落账
└─ :2928 backout_nj_state 回滚嵌套连接状态（回溯）
```

### 深度与剪枝参数

- `optimizer_search_depth`（sys_vars.cc:3275-3284，**默认 62 = MAX_TABLES+1**；MAX_TABLES = 64−3 = 61，见 sql/sql_const.h:104-107）与 `optimizer_prune_level`（:3265-3273，**默认 1**）
- `determine_search_depth`（:2072-2089）的第一条就是 `if (search_depth > 0) return search_depth;`——**用户给了非零值就直接采用**；仅显式设 0（"自动"）时才：表数 ≤7 → 表数+1（穷举）；>7 → 7（贪心）
- 所以**默认行为：62 ≥ 任何查询的表数上限（61）⇒ greedy_search 第一轮就把所有表排完，等价于全量穷举**；表多时搜索空间靠 prune_level=1 的启发式剪枝压住——这正是"剪枝②"存在的意义

### consider_plan：完整计划落账（:2485）

```
cost = positions[idx].prefix_cost
+ 排序成本: sort_by_table 存在且非首表 → cost += prefix_rowcount (:2501-2507)
+ sj 策略合法性检查 (:2519-2531)
chosen = cost < join->best_read (:2533-2535)
  （完整连接序时还会询问二级引擎 compare_secondary_engine_cost :2544-2559）
if chosen: memcpy(best_positions, positions) (:2566)
           + 窗口排序成本 Window::compute_cost (:2569-2575)
           best_read = cost - 0.001 (:2582)     ← 0.001 的用途同上
```

## 四、best_access_path：单表访问路径决策（:980）

候选与决策顺序（简化伪代码）：

```
best_access_path(tab, pos, ...) (:980)
│
├─ ① join buffer(BNL) 可用性 (:1003-1007)
│     首表 / BNL开关关 / lateral依赖 → disable_jbuf
│
├─ ② ref 系候选: find_best_ref (:206, 调用 :1024)
│     逐 keyuse 累积可用 keypart (:283-365)
│     ├─ 唯一索引+全keypart等值 → eq_ref (:394-405, fanout=1)
│     ├─ KEY_OPTIMIZE_REF_OR_NULL 位 → ref_or_null (:361)
│     ├─ fulltext → FT keypart (:276)
│     ├─ fanout: records_per_key统计(:461) / distinct_keys_est启发(:238)
│     │   ★三处复用range优化器的行数估算(读table->quick_rows)
│     │     (:453-454 / :485-492 / :524-536)
│     └─ 成本: find_cost_for_ref(:143-163)
│         = min(file->index_scan_cost|read_cost|page_read_cost, worst_seeks)
│
├─ ③ 四条"扫描必然更差"短路启发 (:1086-1132)
│     (1a)(1b) ref行数更少且单次成本≤tab->read_time
│     (2)   range与ref同索引且ref keypart不少于range (:1103)
│     (3)   HA_TABLE_SCAN_ON_INDEX+覆盖索引(InnoDB聚集索引)
│     (4)   FORCE INDEX 且有 ref (:1128)
│
├─ ④ 扫描类成本: calculate_scan_cost (:769, 调用 :1141)
│     ├─ range: prefix_rowcount × (quick->cost + row_evaluate_cost(...)) (:832)
│     ├─ table scan: file->table_scan_cost() (:845)
│     ├─ index scan(FORCE INDEX无ref): file->read_cost(key,1,records)(:841)
│     ├─ BNL建模: buffer_count = 1+cache_len×prefix_rowcount/join_buff_size
│     │           (:885-887)  成本×buffer_count (:889-892)
│     └─ 条件过滤: calculate_condition_filter(:1244)
│         (filter_effect: 剩余条件下推后的行数折减; 开关关闭时
│          退化启发 found_records×0.75, :799-813)
│
├─ ⑤ ref vs 扫描最终比较 (:1158-1185)
│     scan_total < ref_cost + row_evaluate_cost(prefix_rowcount×rows_fetched)
│     → 选扫描, best_uses_jbuf = !disable_jbuf (:1187)
│
└─ ⑥ 写入 pos->{rows_fetched, read_cost, filter_effect, key, table,
        ref_depend_map, use_join_buffer, ...} (:1219-1226)
      外连接空表 rows_fetched=1.0 (:1201)
```

**这组接口就是 Server 层与存储引擎的成本协商点**（详见 [07 篇](./07.成本模型源码解析.md)）：`file->table_scan_cost` / `read_cost` / `index_scan_cost` / `page_read_cost` / `records_in_range`（行数在 range 阶段已存进 `table->quick_rows[]`，planner 只读）。

## 五、hash join 的真实生成位置（8.0.30）

关键事实：**传统优化器的计划搜索里没有 hash join 候选**（sql_planner.cc、sql_optimizer.cc 中 grep "hash_join" 零命中）。它建模的是 BNL（join buffer），然后在**执行器构建期无条件替换**：

```
规划期: best_access_path 置 use_join_buffer (:1187)
   → make_join_readinfo (sql_select.cc:3071)
     → QEP_TAB::init_join_cache (:3038) 置 op_type=OT_BNL (:3045)
执行器构建期: JOIN::create_access_paths (sql_executor.cc:2904)
   → UseHashJoin(qep_tab) ≡ op_type==OT_BNL (:2135-2137)
   → replace_with_hash_join = UseHashJoin && !QueryMixesOuterBKAAndBNL
                                                     (:2676-2677) ★无成本比较
   → SplitConditions/ExtractJoinConditions 拆等值与非等值 (:2692/:2720)
   → CreateHashJoinAccessPath (:2812-2821)
       build侧=行数估计更小的QEP_TAB (:2813-2814)
       非等值条件作join后filter (:2824)
   → 未替换则 CreateNestedLoopAccessPath (:2827)
```

迭代器实现：`HashJoinIterator`（sql/iterators/hash_join_iterator.cc:63；`Init` :148、`BuildHashTable` :411、超内存走 grace 风格分块 `ReadNextHashJoinChunk` :568，块上限 `kMaxChunks` :57）。真正按成本提出 hash join 候选的是 Hypergraph 新优化器的 `ProposeHashJoin`（join_optimizer/graph_simplification.cc:463 注释提及），8.0.30 默认未启用。

## 七、整段算法速记（默认参数下）

```
search_depth = optimizer_search_depth 默认62(≥任何表数⇒全量穷举;
              仅设0时才自动: 表数≤7 ? 表数+1 : 7)   (:2072)
prune_level  = 1 (optimizer_prune_level 默认1)

对每个前缀(贪心每轮固定1张表):
    DFS depth 层:
        每层对每张候选表: best_access_path 选访问路径(:980)
        成本剪枝: prefix_cost >= best_read → 弃 (:2822)
        启发剪枝: 同层已有双优 → 弃 (:2837)
        eq_ref 1::1 链 → 专道快速串联 (:3070)
        depth 用尽 → consider_plan 落账 (:2485)
表序定 → fix_semijoin_strategies 回填 sj 策略 (:3365)
      → get_best_combination 生成 qep_tab (:2967)
      → make_join_readinfo: BNL标记 (:3045)
执行器期: OT_BNL 一律替换为 hash join (:2676)
```

## 小结
&nbsp;&nbsp;三个实用结论：① 默认（search_depth=62 ≥ 任何表数）下连接顺序搜索是**全量穷举**——慢查询别归咎于"贪心不准"，先查统计信息与剪枝效果；把 `optimizer_search_depth` 显式调小（或 0=自动、≤表数）才进入深度受限的贪心模式，此时该参数与 JOIN_ORDER hint（生效点 sql_optimizer.cc:5240 `apply_join_order_hints`）才是有效干预手段。② `best_access_path` 里 ref 与扫描的成本比较，输入全部来自 handler 上报（[07 篇](./07.成本模型源码解析.md)），统计失真 = 比较失真。③ EXPLAIN 里 `Using join buffer (Block Nested Loop)` 的字样在 8.0.30 内表扫描连接下基本都会实际执行为 hash join（等值条件存在时），计划名与执行名不同源，读执行计划时要记得这层"隐名替换"。
