# 物理优化源码解析——JOIN::optimize（sql/sql_optimizer.cc，基于8.0.30）
&nbsp;&nbsp;**核心认知：`JOIN::optimize`（sql/sql_optimizer.cc:281）是单条 query_block 的代价优化总控，按"逻辑改写(A) → 成本搜索(C: make_join_plan) → 连接序后优化(D) → 计划落地(E)"四大阶段推进，最终产出 `m_root_access_path`（AccessPath 树）。函数开头注释（:247-280）就是官方自述的四个阶段清单。**

> 前置阅读：[01.处理流程总览](./01.优化器处理流程总览.md)（JOIN 怎么被创建和调用）。连接顺序搜索的算法细节在 [05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)，range 分析在 [06 篇](./06.Range优化器源码解析.md)，本篇聚焦**阶段编排**。

## 一、官方注释的四阶段（sql_optimizer.cc:247-280 摘译）

```
1. Logical transformations（逻辑改写）
   - 外连接转内连接 / 等值与常量传播 / 分区裁剪
   - COUNT(*),MIN(),MAX() 常量替换 / ORDER BY 优化
2. Cost-based optimization（成本搜索）
   - 表连接顺序与访问路径选择 → JOIN::make_join_plan()
3. Post-join-order optimization（连接序后优化）
   - 从 WHERE/ON 生成各表最优条件 / 注入外连接守卫条件
   - 多次调整访问方式 / ORDER BY、DISTINCT 优化
4. Code generation（计划落地）
   - 设置数据访问方式 / 尝试消除排序与 DISTINCT
   - 为分组排序规划临时表
```

防重入：:292 `if (optimized) return false;`，:329 `set_optimized()`——EXPLAIN 不会二次初始化；"重新优化"即整个 JOIN 重建重跑（PS 每次执行都如此，见 [01 篇](./01.优化器处理流程总览.md)）。

## 三、阶段 A 关键点

**`optimize_cond`（WHERE :415 / HAVING :429，def :10062）**：条件上的逻辑改写——等式传播生成 `cond_equal`（等值类，`a=b AND b=c` 推出 `a=c` 供选索引）、常量折叠；返回 `COND_FALSE` 时直接得出 "Impossible WHERE"。

**`optimize_aggregated_query`（:458）**：隐式分组（无 GROUP BY 的聚合）时：
- `SELECT MIN(a)...` 且 `a` 上有索引 → 计划读一行即成（`AGGR_COMPLETE` → :481 `NewFakeSingleRowAccessPath` + :482 挂 HAVING/LIMIT，直接出计划）
- COUNT(*) 走 `AGGR_DELAYED` → `select_count=true`，由执行器计数

**`TABLE_LIST::optimize_derived`（:345 循环、调用 :348，定义 sql_derived.cc:1521）**：物化派生表/表函数在这里被优化（递归进内层 query_block 的 JOIN::optimize）——这就是"外层先优化、内层在被扫到时优化"的锚点。

## 四、阶段 C：make_join_plan（:5168）——旧名 make_join_statistics

### 4.1 常量表检测与读取（:5223/:5226）

**`JOIN::extract_const_tables`（:5484）**，判定规则：
- 位于嵌套连接/semi-join nest → 不提取（:5499-5509）
- 外连接唯一内表 → 仅当引擎统计精确（`HA_STATS_RECORDS_IS_EXACT`）且 records==0 时按空表提取（:5518-5523）
- 其余表：`(system 表 || records<=1 || 全分区被裁剪) && 无依赖 && 统计精确 && 非全文检索` → `mark_const_table`（:5532-5537）

**`mark_const_table`（:8306）**：区分 `JT_SYSTEM`（整表单行）与 `JT_CONST`（按键查找，:8328 `key ? JT_CONST : JT_SYSTEM`）——EXPLAIN 的 `type=system/const` 之源；表搬进 `best_ref[const_tables]` 前部、置位 `const_table_map`（:8330）。

**读取**：每个 const 表调 `join_read_const_table`（:5548，def sql_executor.cc:3439；JT_SYSTEM→read_system / 其他→read_const :3477-3488）。**读完后立即做条件定值**（:3507-3522 `update_const_equal_items`）：把条件中该表字段替换成实际读到的值。

**`extract_func_dependent_tables`（:5578）二次提取**：
- 外连接内表 keyuse 全为 const 且 null_rejecting → 直接 `set_null_row()` 置空表（:5610-5620）
- 依赖全落 const_table_map + records<=1 → system 化（:5642-5654）
- **唯一索引全前缀引用 const 值**（`eq_part.is_prefix` + `HA_NOSAME`，:5691-5697）→ `create_ref_for_key`(:5702) + 立即读取（:5706）
- `do{...}while` 不动点迭代（:5720-5725）——A 变常量表后 B 的条件也随之变常量，循环到没有新常量表为止

```
SELECT * FROM t1 JOIN t2 ON t1.id=t2.id WHERE t1.id=5
   t1: 主键等值 const → 先读出 t1 整行(读取时定值)
   t2: t2.id 依赖 t1.id(现已是常量5) + 唯一索引 → 也成 const ← 不动点第二轮
   EXPLAIN: 两行都是 type=const
   若 const 表读出 0 行: :5290 "no matching row in const table" → Empty set
```

### 4.2 estimate_rowcount（:5771）与 range 分析衔接

非 const 表逐个调 `get_quick_record_count`（sql_optimizer.cc:6047，调用点 :5825）→ `test_quick_select`（[06 篇](./06.Range优化器源码解析.md)）：
- FORCE INDEX 在此生效：第 14 参 `ignore_table_scan = tab->table()->force_index`（:6070）
- 返回 `HA_POS_ERROR` → `impossible_range` → 反向提升为常量空表（:5843 `mark_const_table` + JT_CONST）

### 4.3 get_best_combination（:2967）

`best_positions`（搜索产物）定格为执行结构：按 GROUP BY/DISTINCT/ORDER BY/窗口数分配 qep_tab 后段的临时表槽位（:2988-3003）；Materialize 策略的 sj 内表挪到独立区段（:3013-3024）；`make_outerjoin_info`（:3171，def :8335）构建外连接 `first_inner/last_inner` 链（执行时判 NULL 补齐的依据）。

## 五、阶段 D：make_join_query_block（:9319）——旧名 make_join_select

把优化期条件（WHERE + ON）**分配到具体表**上：

1. `add_not_null_conds`（:9327，def :6223）：注入 `x IS NOT NULL`
2. 常量条件求值（:9348-9384）：`make_cond_for_table(const_table_map)` 抽常量表条件，`evaluate_during_optimization` 后求值——false 则 "Impossible WHERE noticed after reading const tables"（上层 :713）
3. **逐表分配循环（:9401-9736）**：
   - `make_cond_for_table(thd, cond, prefix_tables, added_tables)`（:9415，def :9232）：条件挂到"引用列刚凑齐的第一个表"上；剔除 ref 访问已保证为真的等值条件
   - 外连接内表条件包 `FOUND_MATCH` 触发器（`add_found_match_trigcond` :9445）
   - **range 重检**（:9468-9732）：非首表（`NOT_FIRST_TABLE` :9504）或 `LIMIT < rows_fetched×filter_effect`（`LOW_LIMIT` :9510-9516）时**重跑 `test_quick_select`**（:9630，无 ON 条件时再跑一次 :9660）——首表估好的 range 计划，作为内表可能不再最优
4. `attach_join_conditions`（:9735，def :8586）：外连接 last_inner 处拆分下推 join 条件、SJ 物化 nest 条件下推、反连接补 IS NULL

## 六、阶段 E：make_join_readinfo 与 make_tmp_tables_info

### 6.1 make_join_readinfo（sql_select.cc:3071，调用点 :971）

- `setup_semijoin_dups_elimination`（sql_select.cc:1335，调用 :3085）：5 种 sj 策略中 DuplicatesWeedout 的去重表在此搭建
- `QEP_TAB::init_join_cache`（:3038，调用 :3107）：join buffer 决策，内表扫描连接置 `OT_BNL`（:3045）——执行器期被替换为 hash join（[05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)第七节）
- **ICP 触发点 `QEP_TAB::push_index_cond`（sql_select.cc:2710，调用 :3119 ref / :3177 range）**：条件 `HA_DO_INDEX_COND_PUSHDOWN` + `index_condition_pushdown` 开关 + 非多表 UPDATE/DELETE + 非 CONST/SYSTEM + 非聚集主键（:2775-2783）；`make_cond_for_index`(:2787) 抽取仅含本索引列的子条件 → **:2834 `tbl->file->idx_cond_push(keyno, idx_cond)` 真正下推**（引擎侧 ha_innodb.cc:23733）
- EXPLAIN 的 rows/filter_effect 重整（:3137-3148）

### 6.2 make_tmp_tables_info（sql_select.cc:4139，调用点 :974）

最终确定**临时表管线**——什么情况建中间表（`create_intermediate_table` :4239/:4380/:4621 三处）：
- 非简单 DISTINCT / GROUP BY 与 ORDER BY 不同序 / ROLLUP（判定注释 :919 (1)）/ **窗口函数**（逐窗口再建表 :4621，窗口输出回写 :4088-4101）/ SQL_BUFFER_RESULT（:950 (7)）
- GROUP BY 聚合管线：第二张中间表（:4380）+ `make_group_fields`（:4393）
- `JOIN::add_sorting_to_table`（def :4769；旧名 `create_sort_index` 在 8.0.30 已不存在，仅注释残留）：构造 Filesort；Duplicate Weedout 场景强制按 rowid 排序、禁用 addon fields（force_sort_rowids，:4778-4796——weedout 去重需要指向原表的行引用）
- 注意：**派生表物化**不在此（由 `Query_expression::optimize`→`setup_materialization` sql_union.cc:800 处理）；**semi-join 物化**在阶段 C

```
SELECT DISTINCT a, SUM(b) FROM t GROUP BY a ORDER BY SUM(b)
 → 中间表1: 聚合(GROUP BY a) → 中间表2: DISTINCT/ORDER BY
   EXPLAIN Extra: Using temporary; Using filesort
```

### 6.3 create_access_paths（sql_executor.cc:2904，调用点 :988）

QEP_TAB → AccessPath：`create_root_access_path_for_join`（:2934）核心 `ConnectJoins`（:2986）把表串成嵌套循环/hash join AccessPath → `attach_access_paths_for_having_and_limit`（:3268）→ UPDATE/DELETE 再包一层（:2868）。产出 `join->m_root_access_path`。之后 `push_to_engines`（:1009）询问 handlerton 是否整体下推（如 HeatWave），最后 `set_plan_state(PLAN_READY)`（:1012）。

Iterator 树不在此建——由上层 `Query_expression::optimize`（sql_union.cc:833）统一调 `CreateIteratorFromAccessPath`（join_optimizer/access_path.cc:333），见 [08 篇](./08.Hypergraph新优化器与迭代器执行器.md)。

## 小结
&nbsp;&nbsp;`JOIN::optimize` 的骨架可以压缩成一句话：**先把"条件"和"常量"收拾干净（A），然后让 `make_join_plan` 在给定候选（keyuse + range 计划）上搜索表序（C），搜索完把条件精确挂到每张表、消掉能消的排序（D），最后把决策翻译成 AccessPath（E）**。四个最容易被问到的点各有一个函数锚点：type=const 的来源 `extract_const_tables`(:5484)、range 二次决策 `make_join_query_block`(:9319 内 :9468-9732)、ICP 落点 `push_index_cond`(sql_select.cc:2834)、Using temporary 的来源 `make_tmp_tables_info`(sql_select.cc:4139)。
