# 成本模型源码解析（基于8.0.30）
&nbsp;&nbsp;**核心认知：MySQL 的代价 = 一组可调常量 × 引擎/Server 各自上报的 IO 量。常量分两级（`Server_cost_constants` 管 CPU 类操作、`SE_cost_constants` 管引擎 IO，分别来自 `mysql.server_cost`/`mysql.engine_cost` 表），会话通过 `Cost_model_server` 便捷接口取用；IO 量（一个 range 扫多少行、全表扫多少页）由 handler 虚函数 `read_time`/`scan_time`/`records_in_range` 上报。优化器所有"选择"，最终都是这套模型算出来的数字比较。**

## 二、成本常量默认值（opt_costconstants.cc，grep 验证）

### Server_cost_constants（h:63，构造 h:70-75）

| 常量 | 默认值 | 赋值行 | 含义 |
|---|---|---|---|
| `ROW_EVALUATE_COST` | **0.1** | cc:55 | 每行条件求值（不是 0.2——0.2 是 5.7 旧手工模型的值） |
| `KEY_COMPARE_COST` | 0.05 | cc:58 | 每次键比较（filesort/归并的成本来源） |
| `MEMORY_TEMPTABLE_CREATE_COST` | 1.0 | cc:64 | 内存临时表创建 |
| `MEMORY_TEMPTABLE_ROW_COST` | 0.1 | cc:70 | 内存临时表每行 |
| `DISK_TEMPTABLE_CREATE_COST` | 20.0 | cc:75 | 磁盘临时表创建（昂贵 20 倍，TempTable 转 InnoDB 临时表的代价感来源） |
| `DISK_TEMPTABLE_ROW_COST` | 0.5 | cc:84 | 磁盘临时表每行 |

### SE_cost_constants（h:196；按"引擎 × 设备类型"取值）

| 常量 | 默认值 | 赋值行 | 含义 |
|---|---|---|---|
| `MEMORY_BLOCK_READ_COST` | 0.25 | cc:148 | 内存页读（buffer pool 命中） |
| `IO_BLOCK_READ_COST` | 1.0 | cc:151 | 磁盘页读 |

名称解析在 cc:167-175（`server_cost`/`engine_cost` 表里的字符串 → 常量）。

### 动态修改

```

     → reload_optimizer_cost_constants() (opt_costconstantcache.cc:456)
```

## 三、handler 层 IO 上报：两个 read_time 的量纲差异

这是 [008.优化器选择不使用索引的情况](../008.优化器选择不使用索引的情况.md) 的成本根源，此处给源码定位：

- **基类 `handler::read_time`（handler.h:4862）**＝ `ranges + rows`——**每行 1 个单位**，隐含"逐行回表"的代价口径，用于二级索引访问
- **InnoDB 覆盖改写 `ha_innobase::read_time`（ha_innodb.cc:16850）**＝ `ranges + (rows/total_rows)×scan_time`——**按页分摊**（`scan_time` 见 :16816），用于聚集索引/覆盖索引扫描
- 调用点：`best_access_path` 的 `find_cost_for_ref`（sql_planner.cc:143-163：覆盖走 `index_scan_cost` :153、聚集主键走 `read_cost` :159、其余 `page_read_cost` :162）；`calculate_scan_cost`（:769）的 `file->read_cost`（:842）/`table_scan_cost`（:845）

```
匹配行占比一高:
  二级索引: rows × 1.0/行 (隐含每行随机回表)
  全表扫:   页数 × IO_BLOCK_READ_COST (顺序读整棵聚簇树)
  ⇒ 80% 命中率时索引必输——不是优化器"笨", 是量纲如实反映随机IO
```

## 五、统计信息：成本模型的另一个输入

常量×IO 量之外，**行数本身**来自统计：
- 表级：`records`（InnoDB 持久化统计，`innodb_stats_persistent_*` 控制，详见 [008 篇](../008.优化器选择不使用索引的情况.md)场景四）
- 索引级：`records_per_key`（区分度，`best_access_path` 的 ref fanout 用，sql_planner.cc:461）
- 区间级：`records_in_range` dive / `eq_range_index_dive_limit` 切换（[06 篇](./06.Range优化器源码解析.md) 4.1）
- 直方图（8.0+，sql/histograms/）：`statistics` 表上的列统计，补区分度信息——它影响的正是 `calculate_condition_filter`（sql_planner.cc:1244）里 filter_effect 的精度

`EXPLAIN FORMAT=TREE` / `EXPLAIN ANALYZE` 的 `cost=… rows=…` 就是这套模型的输出快照（estimated cost 来自 `accumulate_statement_cost`，sql_select.cc:776 调用）。

### 同类参数一览：估算精度 vs 优化耗时/维护成本

与 `eq_range_index_dive_limit` 同属"**用精度换优化耗时（或统计维护成本）**"的一类参数（前 8 个影响估算输入，后 3 个影响搜索空间；行数估算三种来源的精度档位：**dive ＞ 表/索引统计 ＞ 默认启发**）：

| 参数 | 默认值 | 定义位置 | 权衡什么 |
|---|---|---|---|
| `eq_range_index_dive_limit` | 200 | sql/sys_vars.cc:3877 | 等值区间数 ≥N：index dive（精确/慢）→ `records_per_key` 统计（粗/快）。专题见 [06 篇第四节](./06.Range优化器源码解析.md) |
| `innodb_stats_persistent_sample_pages` | 20 | storage/innobase/handler/ha_innodb.cc:22128 | 持久化统计（ANALYZE TABLE）采样叶页数：多→records/区分度更准，ANALYZE 更慢 |
| `innodb_stats_transient_sample_pages` | 8 | ha_innodb.cc:22107 | 瞬时统计（未启用持久化时）的采样页数 |
| `innodb_stats_persistent` | ON | ha_innodb.cc:22114 | 持久化统计 vs 瞬时统计 |
| `innodb_stats_auto_recalc` | ON | ha_innodb.cc:22120 | 表变更超阈值（约 10%）后自动重算持久化统计 |
| `innodb_stats_method` | nulls_equal | ha_innodb.cc:22888 | 统计中 NULL 的计法（nulls_equal/nulls_unequal/nulls_ignored） |
| `innodb_stats_on_metadata` | OFF | ha_innodb.cc:22100 | `SHOW TABLE STATUS` 等元数据命令是否触发瞬时统计刷新 |
| `histogram_generation_max_mem_size` | 20000000 | sql/sys_vars.cc:3329 | 直方图生成可用内存：决定采样行数与最终桶数（精度上限） |
| `optimizer_search_depth` | 62（=MAX_TABLES+1） | sql/sys_vars.cc:3275 | 连接序搜索深度：默认 ≥ 任何表数即全量穷举，靠剪枝兜底（[05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)） |
| `optimizer_prune_level` | 1 | sql/sys_vars.cc:3265 | 连接序搜索的启发式剪枝开关 |
| `optimizer_max_subgraph_pairs` | 100000 | sql/sys_vars.cc:3285 | Hypergraph 优化器子图对上限，超限转启发式削减搜索空间（仅 HG 优化器生效） |

> 注：`eq_range_index_dive_offset`（8.0.31 新增）、`EQ_RANGE_KEY_DIVES_POINT_LOOKUP` 系 hint、`analyze_sample_percentage` 为更高版本引入，5.7 与本 8.0.30 源码树中均不存在（已全树 grep 确认）。

> 排错心法：**cost 数字可疑时，沿这条流水线逆向找**——先问行数（输入①，统计/dive 是否失真），再问页数量纲（输入②，是否隐含逐行回表），最后才轮到常量（输入③，最不可能错也最难调）。

## 小结
&nbsp;&nbsp;一句话模型：**cost = IO(引擎上报的页/行量 × SE 常量) + CPU(行数/比较次数 × Server 常量) + 临时表/排序加价**。所有优化器决策——用不用索引、谁先谁后、建不建临时表、ref 还是扫——都是这个公式在候选集上的比较结果。理解了 [05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)的 `best_access_path` 与本篇的取数来源，`optimizer_trace` 里的每个数字都能对上源码。
