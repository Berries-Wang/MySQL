# 逻辑优化源码解析——Prepare阶段（sql/sql_resolver.cc，基于8.0.30）
&nbsp;&nbsp;**核心认知：逻辑优化 = `Query_block::prepare`（sql_resolver.cc:173）。它按固定顺序做语义解析（fix_fields）和结构改写（视图合并、子查询扁平化、外连接转内连接、条件下推），全部是"规则能改就改"，不看统计信息、不算成本。改写发生在外层块自下而上、递归进行的两个时机：`prepare` 主体（解析到哪改到哪）和收尾的 `apply_local_transforms`（sql_resolver.cc:725，所有块解析完后的全局变换）。**

> 子查询的改写（semi-join / IN→EXISTS / 物化）逻辑量大，单独成篇：[03.子查询优化源码解析](./03.子查询优化源码解析.md)。本篇聚焦"表结构层面"的改写。

## 三、视图/派生表：合并（merge）还是物化（materialize）？

入口在 `resolve_placeholder_tables`（:1258）：每个派生表/视图先试 `merge_derived`（:1283），失败则 `setup_materialized_derived`（:1292，物化占位，真正物化在执行期）。

### merge_derived 的放行条件（sql_resolver.cc:3416，按出现顺序）

| 行号 | 条件 | 备注 |
|---|---|---|
| :3419 | 未被合并过 | |
| :3431 | `lex->can_use_merged()` 允许 | |
| :3447 | 视图非 `ALGORITHM=TEMPTABLE` 且内层 `Query_expression::is_mergeable()`（sql_lex.cc:3782） | is_mergeable 逐条否决：UNION / 有 GROUP BY / 有 HAVING / 有 DISTINCT / 无表 / 有 LIMIT / 有窗口函数 |
| :3451 | 启发式 `merge_heuristic`（sql_lex.cc:3811：SELECT 列表无相关子查询、无 set_var_list）+ `derived_merge` 开关/hint | sql_const.h:222 |
| :3466 | 外层 STRAIGHT_JOIN 时内层不能含 sj/aj nest | |
| :3471 | 表数上限：`leaf_table_count + 内层表数 - 1 <= MAX_TABLES` | 位图空间限制 |

合并动作（:3474-3653）：`merge_underlying_list`(:3492) → 嵌套 join 对象(:3517) → `merge_underlying_tables`(:3521) → `merge_where`(:3563)（内层 WHERE 并入外层）→ `exclude_level`(:3569)（拆掉派生表壳）→ `merge_contexts`(:3575) → `remap_tables`(:3580) → `fix_tables_after_pullout`(:3583)；内层 ORDER BY 上提或丢弃（:3587-3640，带 LIMIT 的 ORDER BY 语义必须保住）。

```
合并成功 (derived_merge=on 默认):                合并失败 → 物化:
SELECT * FROM (                                  SELECT * FROM (
  SELECT a,b FROM t WHERE c=1                      SELECT a,COUNT(*) cnt ...
  GROUP BY a          ←有GROUP BY,                  GROUP BY a ... LIMIT 10
) d WHERE d.b>0         is_mergeable()=false      ) d WHERE d.cnt>0
  改写为:                                          执行期: 先把内层结果
SELECT a,b FROM t                                  落临时表(带索引可被
WHERE c=1 AND b>0 GROUP BY a                       下推条件利用),再当普通表读
（少一层物化,外层条件还能直接用索引）
```

> 物化派生表的更多执行细节：`setup_materialized_derived`（sql/sql_derived.cc）；物化时机/条件见 [04 篇](./04.物理优化源码解析-JOIN之optimize.md) 的 `JOIN::optimize` 中 `TABLE_LIST::optimize_derived`（循环于 sql_optimizer.cc:345、调用 :348，定义 sql_derived.cc:1521）。

## 四、条件下推到派生表（Derived Condition Pushdown，8.0.22+）

**准确函数名：`Query_block::push_conditions_to_derived_tables`（sql_resolver.cc:597，注意无 "the"）**，从 `apply_local_transforms` :815 调用，仅最外层触发。

前提（:598-601 + `TABLE_LIST::can_push_condition_to_derived`，声明 table.h:3174、定义 sql_derived.cc:965）：
1. `optimizer_switch=derived_condition_pushdown` 开启（sql_const.h:229）
2. 派生表**无任何 LIMIT**（推下去会改变 LIMIT 语义）
3. 派生表不是外连接的内表
4. 非多处引用的派生表/递归 CTE（推多份条件代价/语义都有问题）
5. 无用户变量赋值

下推管线（`make_cond_for_derived`，sql_derived.cc:984）：

```
外层 WHERE: d.b>0 AND d.a<5          派生表: SELECT a,b,COUNT(*) ... GROUP BY a
        │
        ▼
extract_cond_for_table (:1099)   AND 可拆分逐个试/OR 必须整体通过
        │                        （只引用该派生表列的条件才能走）
        ▼
push_past_window_functions(:1212) 有窗口函数时: 仅引用 PARTITION 列的
        │                        谓词允许进内层 HAVING
        ▼
push_past_group_by (:1249)       GROUP BY 分流规则:
        │    ├─ 非分组列        → 不能推(聚合结果未定)
        │    ├─ 普通分组        → 只引用 GROUP BY 列的谓词进内层 WHERE ★
        │    ├─ 隐式分组(无GROUP BY,有聚合) → 留在内层 HAVING
        │    └─ ROLLUP          → 留在内层 HAVING
        ▼
replace_columns_in_cond (:1333)  d.a → 内层表达式 t.a
        ▼
attach_cond_to_derived (调用:1055/:1058, def:1479)   挂进内层 WHERE/HAVING
结果: 内层变 SELECT a,b,COUNT(*) ... WHERE a<5 GROUP BY a
      （分组前先过滤,分组行数变少——这正是该优化的收益）
```

> EXPLAIN 不直接显示这次下推，但内层计划会变（`WHERE` 生效于内层访问）；开关关闭则恢复。

## 五、外连接转内连接与嵌套连接展平：simplify_joins（sql_resolver.cc:1880）

变更位图（:1888-1894）：`OUTER_JOIN_TO_INNER` / `JOIN_COND_TO_WHERE` / `PAREN_REMOVAL` / `SEMIJOIN`。

**OUTER_JOIN_TO_INNER 的判定（:1980-1988）**：内层表上存在**拒绝 NULL 的谓词**（如 `t2.b IS NOT NULL`、`t2.b = 5`——对 NULL 行必为假/未知），则 NULL 补齐行必被 WHERE 过滤，外连接的"保行"语义无用 → 转 inner join：
- :1972 `(*cond)->not_null_tables()` 收集"哪些表上出现 NULL 就必为假"的表集合
- WHERE 与上层 ON 都参与对抗判定（:1904-1927 注释解释了为什么要看两层）

```
SELECT * FROM t1 LEFT JOIN t2 ON t1.a=t2.a WHERE t2.b > 0
                                    └─ t2.b>0 拒绝 NULL
        ⇒ 等价于 INNER JOIN（NULL 补齐行全被 WHERE 滤掉）
        ⇒ t2 也可以当内表参与连接顺序自由重排（这是转换的真正收益：
           外连接内表的连接位置受语义约束，转内连接后 planner 可自由交换）
```

- **JOIN_COND_TO_WHERE**（:1989-2022）：转换后 ON 条件 AND 进 WHERE/上层 ON（视图安全过滤器顺序保证 :1999-2001）
- 嵌套 join 的**递归下降**在 :1932-1967（sj/aj nest 经 :1953 的传参带入）；真正的**括号溶解（PAREN_REMOVAL）**在 :2075-2135（置位 :2118），sj nest 的溶解在 :2083-2113（SEMIJOIN 置位 :2104）
- 剩余不可转换的外连接表计算 `dep_tables`（:2034-2040，内表依赖外表，连接顺序搜索时要遵守）

## 六、其他 prepare 期化简（防呆但常被忽略）

- **`simplify_const_condition`**（HAVING 用在 :353；子查询 WHERE 用在 flatten_subqueries:3888）：常量子树直接求值折叠（`WHERE 1=1` → true）
- **`remove_redundant_subquery_clauses`**（:4101）：
  - 标量子查询：删 ORDER BY（有 LIMIT 保留，:4112-4114）
  - IN/EXISTS/ALL/ANY：删 ORDER BY(:4125)、删 DISTINCT(:4130)、删"无聚合无 HAVING 无 ROLLUP 无窗口"的 GROUP BY(:4140-4157)
  - **这就是为什么子查询里写 ORDER BY/DISTINCT 白写**——prepare 阶段直接删
- **`can_skip_distinct`**（sql_lex.h:1291，调用 :414）：SELECT 列表含主键等唯一列时 DISTINCT 无意义，直接删掉 SELECT_DISTINCT 标志
- **常量折叠**发生在各 `Item::fix_fields` 内（如 `WHERE a+1=2` 折成 `WHERE a=1`）——所以索引才能用于"计算后等于常量"的列

> 记忆口诀：**三道门全过才合并——结构挡（TEMPTABLE/GROUP BY/LIMIT/UNION…）、开关挡（derived_merge+启发式）、上限挡（MAX_TABLES 位图）**。任一不过 → 物化。

        │

◇ :1980 内表表位 ∩ not_null_tables 非空?
        │ 是                                  │ 否
        ▼                                     ▼
  OUTER_JOIN_TO_INNER 置位                 保持 OUTER JOIN

## 小结
&nbsp;&nbsp;prepare 阶段做完后，查询已经"定型"：视图消失（或占位为物化表）、子查询扁平化（或标记物化）、外连接尽可能转内连接、能下推的条件已进派生表、冗余子句已删。这些改写**全部不看数据分布**——`SELECT * FROM big_view WHERE x=1` 到底是合并还是物化，只由结构规则（GROUP BY/LIMIT/UNION…）决定。剩下的"怎么执行最省"，全部交给下一级：[`JOIN::optimize`](./04.物理优化源码解析-JOIN之optimize.md)。
