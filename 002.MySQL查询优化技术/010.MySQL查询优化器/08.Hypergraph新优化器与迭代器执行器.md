# Hypergraph新优化器与迭代器执行器（基于8.0.30）
&nbsp;&nbsp;**核心认知：8.0 里有两套优化器。传统优化器（默认）带着 20 年历史包袱，连接顺序只能"线性嵌套循环"式建模（hash join 是执行器期硬替换，见 [05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)）；Hypergraph 新优化器（`sql/join_optimizer/`，试验特性）把查询建成"表=节点、谓词=超边"的超图，用 DPhyp 动态规划**系统性**枚举连接顺序（含 hash join 候选），产出统一的 `AccessPath` 树。而执行器在 8.0 已彻底换代：无论哪套优化器，最终都经 `CreateIteratorFromAccessPath` 变成 Iterator（火山模型）树，由 `ExecuteIteratorQuery` 驱动。**

---

### 1.3 搜索：DPhyp 动态规划（subgraph_enumeration.h，header-only）

实现即 Moerkotte/Neumann 论文中的 DPhyp（注释逐函数对应）：

| 函数 | 行号 | 论文对应/职责 |
|---|---|---|
| `EnumerateAllConnectedPartitions` | :666 | 主循环：自底向上枚举连通子图对 |
| `ExpandSubgraph` | :424 | EnumerateCsgRec：递归生长连通子图 csg |
| `EnumerateComplementsTo` | :350 | EmitCsg：枚举补图种子 |
| `ExpandComplement` | :579 | EnumerateCmpRec：生长补图 |
| `TryConnecting` | :531 | **ccp（csg-cmp-pair）判定**：命中即回调 `FoundSubgraphPair` |

与 [05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)贪心的本质区别：DPhyp 对每个**连通子图对**记最优计划，组合成全局最优——表多也不会指数劣化（配合图简化），且超边建模天然支持外连接的顺序约束。

### 1.3.1 DPhyp 搜索流程图（建图 → 枚举子图对 → DP 比价 → 落地）

```
开启 hypergraph_optimizer 后 (JOIN::optimize :551 分叉)
        │
        ▼
① 建图 MakeJoinHypergraph (make_join_hypergraph.cc:3131)
     FROM/JOIN 列表 → 关系代数树 (:76/:227)
     → FlattenInnerJoins 内连接拍平 (:380)
     → 逐谓词 AddPredicate / PushDownCondition 尽量下压 (:1397)
     → 超图: 节点=表, 超边=谓词涉及的表集合
       (外连接冲突规则约束哪些表子集不能拆开)
        │
        ▼
② 枚举 EnumerateAllConnectedPartitions (subgraph_enumeration.h:666,
     调用点 join_optimizer.cc:5962/:5992)   自底向上:
     for 每个种子节点 (表号从小到大):
       ExpandSubgraph (:424)      递归生长连通子图 csg
         │
         ▼
       EnumerateComplementsTo (:350)  找 csg 的补图种子
         │
         ▼
       ExpandComplement (:579)    生长补图 cmp
         │
         ▼
       TryConnecting (:531) ◇ csg 与 cmp 之间有边相连?
         │ 是 → 一个 csg-cmp-pair 诞生, 回调
         │      CostingReceiver::FoundSubgraphPair (join_optimizer.cc:2779)
         │        对该子图对逐连接方式比价:
         │          nested loop / hash join(一等候选!) / …
         │          每种再叠加两侧子图各自的最优 access path
         │        DP 表记录: 该表集合组合 → 当前最优计划
         │ 否 → 继续枚举下一个
         │
         ▼
◇ csg-cmp-pair 数超 optimizer_max_subgraph_pairs (默认 100000,
  sys_vars.cc:3285)?
   │ 是 → SimplifyQueryGraph (graph_simplification.cc:919)
   │        合并相邻超边缩小图 → 重启枚举
   │        找到计划后 UndoSimplificationStep (:889) 逐步还原细化
   │ 否
        │
        ▼
③ 终局: 某个子图对左右两侧的并集 = 全部表
     → DP 表里记录的就是全局最优连接树
        │
        ▼
④ FinalizePlanForQueryBlock (finalize_plan.cc:532) 落地 AccessPath
     (range 分析/临时表/锁策略/排序在此补全)
```

> 与 [05 篇](./05.连接顺序搜索与访问路径选择源码解析.md)对照着读：贪心每轮**丢弃**深层探索结果只留第一张表；DPhyp 每个**子图对**的最优都留在 DP 表里供上层组合——"记忆"取代"重搜"，这就是动态规划对贪心的本质优势。hash join 也从"执行器硬替换"（sql_executor.cc:2676）变成 FoundSubgraphPair 里**按成本参与竞争**的一等候选。

### 1.4 图简化与成本估算

- **graph_simplification.cc**：表太多时削减搜索空间——`SimplifyQueryGraph`（:919，超过 `optimizer_max_subgraph_pairs` 后由 join_optimizer.cc:5964 调用后重启枚举）；`GraphSimplifier`（h:86）逐步合并"相邻且不违反外连接冲突规则"的超边（`EdgesAreNeighboring` :649、`CombiningWouldViolateConflictRules` :84），找到计划后再 `UndoSimplificationStep`（:889）还原细化
- **成本**：`EstimateCostForRefAccess`（cost_model.cc:54）、`EstimateSortCost`（:87）、连接行数 `FindOutputRowsForJoin`（cost_model.h:104）、选择性 `EstimateSelectivity`（estimate_selectivity.cc:135）
- **有趣序**（interesting_orders.cc + build_interesting_orders.cc）：跟踪各算子产出的排序属性，供用索引序消排序（传统优化器只有零散的 `test_if_skip_sort_order`）
- **hash join 是一等候选**：`ProposeHashJoin`（graph_simplification.cc:463 注释提及）按成本与 nested loop 竞争——不像传统优化器的执行器期硬替换

## 三、新旧对照与现状判断

| | 传统优化器 | Hypergraph 优化器 |
|---|---|---|
| 状态 | 默认 | 试验（8.0.30 需显式开 `hypergraph_optimizer`） |
| 连接建模 | 线性表序（POSITION 前缀） | 超图 + 超边（外连接/半连接约束显式建模） |
| 搜索 | 贪心+深度受限穷举（O(N·N^d/d)） | DPhyp 动态规划 + 图简化 |
| hash join | 无候选；执行器期替换 BNL（sql_executor.cc:2676） | `ProposeHashJoin` 按成本竞争 |
| 排序利用 | `test_if_skip_sort_order`（sql_optimizer.cc:2117）零散判定 | 有趣序框架系统性传播 |
| 产出 | `create_access_paths`（sql_executor.cc:2904）→ AccessPath | `FinalizePlanForQueryBlock` → AccessPath |
| 执行 | 同一套 `CreateIteratorFromAccessPath` + Iterator 树 | 同左 |

8.0.30 的合理姿势：**生产读传统优化器代码，方向看 Hypergraph**——后者是官方重构方向（9.x 逐步默认），`AccessPath`/`Iterator`/`explain_access_path` 这些公共层已经是两套优化器共用的地基，学它不亏。

## 小结
&nbsp;&nbsp;两套优化器、一个执行器：不管计划从 `make_join_plan` 的贪心搜索还是 DPhyp 的动态规划里来，都汇成 `AccessPath` 树（access_path.h:188），再由 `CreateIteratorFromAccessPath`（access_path.cc:333）翻译成 Iterator 树，`ExecuteIteratorQuery`（sql_union.cc:1185）一个 `Init` + `Read` 循环跑完。读执行计划时（`EXPLAIN FORMAT=TREE` / `EXPLAIN ANALYZE`）看到的算子名几乎能与 `iterators/` 的类名一一对应——这是 8.0 执行器换代带来的最大可读性红利。
