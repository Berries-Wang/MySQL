# DELETE 执行流程（基于 MySQL 8.0.30 源码）
&nbsp;&nbsp;**DELETE 是"软删除"：InnoDB 只在聚簇记录上打一个删除标记（delete-mark），真正物理删除由后台 purge 线程异步完成。这解释了 DBA 最熟悉的三个现象：删除后空间不释放、行数统计不立刻下降、删除大量数据后表"虚胖"。**

## 2. 关键点展开

### 2.1 为什么要打标记而不是直接删
- **MVCC 需要**：删除后、purge 前，别的长事务的快照读可能仍需要"看见"这行——删了就没得回溯（undo 版本链，[MVCC 篇 §7](../003.MySQL事务/007.InnoDB之MVCC实现原理(基于8.0.30源码).md)）
- **回滚需要**：事务还没提交就 ROLLBACK 时，只需清掉删除标记恢复原样（`row0undo.cc:301 row_undo_mod`），比"重新找回数据"便宜得多
- **并发友好**：物理删除推迟到后台，purge 自己决定节奏（[004.purge.md](../003.MySQL事务/006.InnoDB事务日志/004.purge.md)）

### 2.2 与 MVCC/WAL 的配合
- 打标记后 `DB_TRX_ID` 更新为当前事务——其他事务的 ReadView 判断该版本不可见，回溯 undo 得到"还存在"的旧版本，快照读因此不受影响
- 同一行的"删除"对 RR 事务 A 不可见（快照里有），对提交后的事务 B 不可见但查不到——**幻读在快照读下天然规避**；当前读（FOR UPDATE）则靠 Next-Key Lock 挡住新插入
- 与 INSERT 的 undo 对称：insert undo 提交即可复用；**delete/update undo 必须等 purge 确认无快照引用才能清**（`trx0undo.cc:1798` → `trx0purge.cc:317`）——这就是长事务导致 undo 膨胀的根源

## 3. DBA 视角：DELETE 常见问题对照
| 现象 | 根因（对应代码阶段） | 建议 |
|---|---|---|
| 删了几千万行，磁盘占用没降 | 只是打标记（`btr0cur.cc:4242`），物理删除等 purge | 空间还给页内复用；彻底回收需 `OPTIMIZE TABLE`/重建表 |
| `information_schema` 行数和实际对不上 | 统计信息与删除标记/purge 进度差异 | `ANALYZE TABLE`；理解"逻辑删≠物理删" |
| 大批量 DELETE 把库拖垮 | 每行：加锁+写 undo+改页+redo，事务越大 purge 越追不上 | 拆小批（如每次 1k~1w 行）+ 间歇提交 |
| 删除后全库变慢、undo 暴涨 | 长事务/大事务让最老 ReadView 不动，purge 停滞（`trx0purge.cc:1596` 前的判断） | 杀长事务；关注 `rseg_history_len` |
| DELETE 比同条件 SELECT 慢很多 | 当前读加锁 + 间隙锁 + undo 写入 + 维护二级索引 | 确认走了主键；无索引条件会锁全表 |
| `TRUNCATE` 为什么快 | 不走 DELETE 路径，直接删表重建（DDL 语义） | 清空全表优先 TRUNCATE |
