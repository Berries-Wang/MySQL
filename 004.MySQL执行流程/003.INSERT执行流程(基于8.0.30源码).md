# INSERT 执行流程（基于 MySQL 8.0.30 源码）
&nbsp;&nbsp;**INSERT 是"从无到有"：不需要读旧版本，但要过三关——锁（插入意向/唯一冲突）、undo（让自己可回滚、可 MVCC）、页与 redo（WAL）。顺序固定：先锁 → 再 undo → 再改页（改页动作本身产生 redo）。**

## 2. 关键点展开

### 2.1 唯一键冲突与自增
- 唯一二级索引插入前必须读页做重复检查（`row_ins_scan_sec_index_for_duplicate`），这一步就把目标页读进了内存——所以**唯一索引享受不到 change buffer 的免读盘收益**（[010 篇 §3](../003.MySQL事务/006.InnoDB事务日志/010.Change-Buffer源码篇(基于8.0.30源码).md)）
- 自增列用表级 AUTO-INC 锁（`innodb_autoinc_lock_mode` 控制模式），批量并发插入的争用点
- 冲突行为差异：普通 INSERT 报 `Duplicate entry`；`REPLACE` = 删旧插新（会走 DELETE 路径）；`ON DUPLICATE KEY UPDATE` = 转 UPDATE 路径

### 2.2 与 MVCC 的关系
- 新插入的记录对**其他事务**天然不可见：其他事务回溯版本链时走到 insert undo 就"无版本可回溯"，该行被视为快照中不存在（`row0vers.cc:1303` `prev_version == nullptr` → 跳过）
- 本事务可见：`ReadView::changes_visible` 中 `id == m_creator_trx_id` 直接放行（`read0types.h:166`）
- 事务提交后 insert undo 立即可复用（`trx0undo.cc:1798 trx_undo_set_state_at_finish`），不需要等 purge——这是 insert undo 与 update undo 的核心区别

### 2.3 与 WAL 的关系
- "改页"动作全部包在 mtr 里，mtr 提交即写 log buffer 并分配 LSN（`mtr0mtr.cc:858`），后台 log_writer/log_flusher 异步落盘
- 事务必须等的是 COMMIT 时的 redo fsync（`trx0trx.cc:1730`），而不是数据页落盘——数据页可能几秒后才由 page cleaner 刷（且刷页前先等 redo，`buf0flu.cc:1201`）

## 3. DBA 视角：INSERT 常见问题对照
| 现象 | 根因（对应代码阶段） | 建议 |
|---|---|---|
| 并发插入报 `Lock wait timeout`（gap 锁） | `lock_rec_insert_check_and_lock` 被别的事务的间隙锁挡住 | RR 下留意范围查询的锁；必要时评估 RC |
| 批量导入慢、undo 涨 | 逐条 autocommit，每条都走完整提交链 | 显式事务批量提交；但别把事务开太大 |
| 提交阶段偶发慢 | redo/binlog fsync 抖动（组提交没摊薄） | 调 `binlog_group_commit_sync_delay*`；看磁盘 |
| 表在写入但磁盘上 `.ibd` 没动静 | 页还在 Buffer Pool 里，page cleaner 未刷 | 正常现象；关注脏页比例与 redo 压力 |
| 二级索引写延迟后读变慢 | ibuf 攒的账在读页时集中合并 | [010 篇 §4](../003.MySQL事务/006.InnoDB事务日志/010.Change-Buffer源码篇(基于8.0.30源码).md) |
| `Duplicate entry` 但主从数据看似一致 | REPLACE/ON DUP 的语义差异，binlog 是 ROW 时以主库为准 | 理解三种写法的不同路径 |
