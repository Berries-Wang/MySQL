# UPDATE 执行流程（基于 MySQL 8.0.30 源码）
&nbsp;&nbsp;**UPDATE = "当前读定位行 → 先记旧值到 undo → 尽量就地改聚簇记录 → 同步维护二级索引"。若改的是主键，就地更新不可行，退化为"打删除标记 + 重新插入"。**

## 2. 关键点展开

### 2.1 UPDATE 的行定位是"当前读"
- 与 SELECT 不同：UPDATE 定位行走 `row_search_mvcc` 的**锁定读分支**，拿到的是**最新记录**并加 X 锁——不可能基于历史版本去改数据
- RR 下若有别的事务持锁，等待队列 + 间隙锁由此产生（`lock_clust_rec_modify_check_and_lock`）
- RC 下有个特例——**半一致性读**：被锁住的行不等待，退化为读"最后已提交版本"先做 WHERE 判断（`row0vers.cc:1359 row_vers_build_for_semi_consistent_read`，详见 [MVCC 篇 §7.1](../003.MySQL事务/007.InnoDB之MVCC实现原理(基于8.0.30源码).md)）

### 2.2 undo 是旧值的来源 = MVCC 的资本
- undo 里记录的是**被改列的旧值**（不是整行，`trx0rec.cc:852 trx_undo_page_report_modify`）——这正是"只更新需要的列"能省 undo 的原因
- 其他事务的快照读读到"当前记录不可见"时，就靠这份 undo 反推旧版本（`row0vers.cc:1249` 循环回溯）
- 提交后该 undo 挂 history list 等 purge 决定去留（`trx0purge.cc:317`）——**长事务 = undo 永远删不掉 = 全库变慢**

### 2.3 什么时候不能"就地更新"
| 情况 | 结果 |
|---|---|
| 只改非主键列、页内放得下 | 就地更新（乐观路径，最快） |
| 行变大导致页放不下 | 悲观路径：可能页分裂/重组织 |
| **主键被修改** | 旧记录打删除标记 + 新主键重新插入（聚簇索引按主键组织，等价于挪行） |

> 二级索引同理：被更新列命中二级索引 → 旧条目打删除标记+插新条目（所以"频繁更新索引列"会显著放大索引维护成本）。

## 3. DBA 视角：UPDATE 常见问题对照
| 现象 | 根因（对应代码阶段） | 建议 |
|---|---|---|
| `Lock wait timeout exceeded` | 定位行时 `:3026` 加锁被堵 | 查 `data_lock_waits` 找持锁事务 |
| 更新很慢但没锁等待 | WHERE 走了二级索引逐行回表+加锁；或 undo 链长（semi-consistent 回溯） | 改用主键批量；拆小事务 |
| RR 下范围 UPDATE 影响并发 | 间隙锁/Next-Key Lock 范围大 | 缩小 WHERE；评估 RC |
| `Table is full`/undo 表空间暴涨 | 大事务：undo 不能提交清理 | 拆批 + 及时提交；监控 `rseg_history_len` |
| 更新主键的语句特别慢 | 等价于删一行插一行，双倍索引维护 | 尽量让主键不变 |
| 更新索引列导致写放大 | 二级索引 del-mark+insert | 评估该列是否需要索引 |
