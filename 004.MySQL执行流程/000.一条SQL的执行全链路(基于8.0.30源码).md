## 2. Server 层与 InnoDB 层的职责分界
| 阶段 | Server 层 | InnoDB 层 |
|---|---|---|
| 解析/优化 | 词法语法解析、代价估算、选索引、join 顺序 | 不参与 |
| 行存取 | 只认 handler 接口（`ha_rnd_next/ha_index_read/ha_write_row…`） | B+ 树、页、buffer pool |
| 并发控制 | 元数据锁(MDL) | 行锁/表意向锁/间隙锁 |
| 多版本 | 无 | MVCC（undo + ReadView） |
| 持久化 | binlog（逻辑日志） | redo/undo（物理/逻辑回滚日志） |
| 事务协调 | 两阶段提交协调者（binlog 作 TC） | 参与者（prepare/commit） |

> 对 DBA 的意义：**"扫了多少行"在 InnoDB（`Rows_examined`），"锁等在哪"看 InnoDB（data_locks），"提交慢不慢"看 redo/binlog 的 fsync。** 慢的层次不同，排查入口完全不同。

## 3. COMMIT：redo 与 binlog 的两阶段提交（内部 XA）
```
 用户线程                                后台/协调者
 ─────────                              ──────────
 ha_commit_trans (handler.cc:1487)
    │
    ├─① InnoDB PREPARE
    │    trx_prepare (trx0trx.cc:2945)
    │      写 prepare 记录到 redo 并 fsync
    │      (事务状态: TRX_STATE_PREPARED)
    │
    ├─② binlog 落盘 (Server 层作协调者)
    │    MYSQL_BIN_LOG::commit (binlog.cc:8041)
    │      └ ordered_commit (binlog.cc:8806) 三阶段:
    │         BINLOG_FLUSH_STAGE: 事务 binlog 排队 → 写入 binlog 文件(OS cache)
    │         SYNC 阶段:          组内一起 fsync(组提交)
    │         COMMIT 阶段:        依次调用各引擎 commit
    │
    └─③ InnoDB COMMIT
         innobase_commit (ha_innodb.cc:5735)
           └ trx_commit (trx0trx.cc:2197)
               └ trx_commit_in_memory (:1903)
                   ├ 摘出 rw_trx_ids / 关 ReadView (MVCC 文档 §5)
                   ├ 写 redo commit 记录
                   └ trx_flush_log_if_needed (:1730)
                       └ innodb_flush_log_at_trx_commit=1: 等 fsync 返回
```
- **为什么必须两阶段**：崩溃恢复时以 binlog 为准——binlog 里有该事务 → InnoDB 重做/提交；没有 → 回滚 InnoDB 里 prepared 的事务。若不分两步，"binlog 写了但 InnoDB 没提交"会导致主从不一致。
- **两个组提交串起来**：redo 侧 log_writer/log_flusher 批量落盘（[redo 篇 §4](../003.MySQL事务/006.InnoDB事务日志/008.redo.log源码篇(基于8.0.30源码).md)），binlog 侧 ordered_commit 三阶段排队（[group commit 篇](../003.MySQL事务/006.InnoDB事务日志/005.group-commit.md)）——高并发下 fsync 次数被摊薄，这就是"组提交"。
- 相关参数：`sync_binlog`、`binlog_group_commit_sync_delay*`、`innodb_flush_log_at_trx_commit`（半同步/主从一致性场景通常 1+1）。

## 4. MVCC 与 WAL 在链路中的触点地图
| 环节 | 触发的机制 | 源码入口 |
|---|---|---|
| SELECT 打开语句 | RC 下关闭旧 ReadView；RR 复用 | `ha_innodb.cc:18839` / `trx0trx.cc:2259` |
| SELECT 读行 | ReadView 可见性判断 → 不可见则回溯 undo | `row0sel.cc:5264` → `row0vers.cc:1249` |
| SELECT 二级索引扫描 | 页头 max_trx_id 粗判 | `lock0lock.cc:266` |
| 写语句开始 | 行定位即当前读（加锁，不看快照） | `row0sel.cc:4363`(锁定读分支) |
| 写操作落行前 | 先写 undo（记录旧镜像） | `trx0rec.cc:2105`（insert `btr0cur.cc:2607`；update/del `:3121/:4278`） |
| 页被修改 | mtr 生成 MLOG 记录 → 提交时进 log buffer | `mtr0mtr.cc:674/858` |
| 脏页产生 | 带 LSN 上 flush list | `mtr0mtr.cc:883` |
| 后台异步 | writer/flusher 落盘 redo；page cleaner 刷页(先等 redo)；purge 清 undo | `log0write.cc:2225/2490`、`buf0flu.cc:1201`、`trx0purge.cc:2577` |
| COMMIT | redo commit + binlog 2PC（§3） | `trx0trx.cc:2197`、`binlog.cc:8806` |

## 5. DBA 常见现象 → 代码阶段对照（排错入口）
| 现象 | 大概率发生的阶段 | 看哪里 |
|---|---|---|
| 提交慢（RT 抖动） | redo fsync / binlog fsync | `iostat`；`innodb_flush_log_at_trx_commit`、`sync_binlog` |
| `LOCK WAIT` 大量堆积 | 写语句定位行时的行锁 | `performance_schema.data_lock_waits`；[000.MySQL之锁](../000.MySQL之锁) |
| RR 下大范围 UPDATE 巨慢 | 回滚段长链 + 行锁 + undo 回溯 | [MVCC 篇 §7](../003.MySQL事务/007.InnoDB之MVCC实现原理(基于8.0.30源码).md)；拆小批量 |
| DELETE 后空间不释放 | delete 只是打标记，物理删除等 purge | [DELETE 篇](./005.DELETE执行流程(基于8.0.30源码).md) |
| 长事务导致 undo 膨胀、全库变慢 | ReadView 不推进 → purge 停滞 | [MVCC 篇 §8](../003.MySQL事务/007.InnoDB之MVCC实现原理(基于8.0.30源码).md) |
| 批量插入忽快忽慢 | change buffer 生效/失效、redo 容量、检查点压力 | [010.Change-Buffer源码篇](../003.MySQL事务/006.InnoDB事务日志/010.Change-Buffer源码篇(基于8.0.30源码).md)、log_free_check |
| 从库延迟 | binlog 单线程/并行度不足、大事务 | `binlog_transaction_dependency_tracking`；避免大事务 |
