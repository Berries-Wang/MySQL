# SELECT 执行流程（基于 MySQL 8.0.30 源码）
&nbsp;&nbsp;**普通 SELECT = 快照读：不加任何行锁，靠 MVCC 判断"哪个版本对当前事务可见"，不可见就沿 undo 回溯。写锁定读（FOR UPDATE）和 DML 的行定位走的是同一函数的另一条分支（当前读）。**

## 2. ReadView 在哪一步建立（RR vs RC）
```
语句开始: external_lock (ha_innodb.cc:18579)
   ├ RC: 关闭上一语句的 ReadView (:18839) → 本`语句第一条快照读时新建
   └ RR: 什么都不做(事务内已有视图就一直复用, trx0trx.cc:2259)
第一条快照读: row_search_mvcc 内 trx_assign_read_view (row0sel.cc:4772)
   └ 视图不存在 → MVCC::view_open → ReadView::prepare (read0read.cc:446)
```

## 3. 三种"读"的本质区别
| | 普通 SELECT(快照读) | LOCK IN SHARE MODE / FOR UPDATE | DML 的行定位 |
|---|---|---|---|
| 加锁 | 不加行锁 | S 锁 / X 锁(+间隙) | X 锁(+间隙) |
| 读哪个版本 | ReadView 可见的历史版本 | 最新已提交/当前记录 | 当前最新记录 |
| 实现入口 | `row_search_mvcc` 非锁定读分支 | `row_search_mvcc` 锁定读分支 | 同左（LOCK_X） |
| 幻读 | MVCC 快照天然规避 | Next-Key Lock 规避 | Next-Key Lock 规避 |

## 4. DBA 视角：SELECT 为什么慢
| 现象 | 根因（对应代码阶段） | 建议 |
|---|---|---|
| 计划对但巨慢，`Rows_examined` 远大于返回 | 索引选择性差/回表次数多 | 优化索引；覆盖索引减少回表 |
| 单行点查偶发慢 | 该行不可见需回溯很长的 undo 链（`row0vers.cc:1249` 循环） | 检查长事务/高频更新行 |
| RR 下越跑越慢 | 长事务 ReadView 固定，undo 越积越多 | 及时 COMMIT，别在大事务里闲逛 |
| 扫描二级索引反而快 | 页头 max_trx_id 粗判直接命中（`lock0lock.cc:290`） | 理解为正常优化 |
| `SHOW PROFILE` 卡在 Sending data | 行未返回给 Server，还在迭代器循环里逐行取 | 看执行计划 EXPLAIN ANALYZE |
